# ADR-016 — Specialized Market Event Model

* **Status:** Accepted
* **Date:** 2026-07-25

## Context

Trading OS currently represents real-time market information through a `MarketDataEvent`.

The current model mainly describes ticker data:

* symbol;
* bid price;
* ask price;
* last traded price;
* timestamp.

This was sufficient for the first real-time market-data increment.

However, Trading OS is expected to progressively consume additional market streams, including:

* OHLC candles;
* individual trades;
* order-book snapshots and updates;
* funding information;
* open interest;
* liquidation events.

These streams have substantially different structures and semantics.

Extending a single `MarketDataEvent` with fields for every possible stream would create a large model containing many nullable or irrelevant attributes.

For example, an order-book event does not need OHLC fields, while a candle does not need bid and ask collections.

Such a model would become:

* difficult to understand;
* difficult to validate;
* difficult to serialize safely;
* difficult for consumers to process;
* increasingly coupled to provider-specific payloads.

The next planned market-data increment includes historical and real-time price charts. A specialized candle model must therefore be introduced before expanding the current event contract.

## Decision

Trading OS introduces a common immutable `MarketEvent` abstraction with one specialized event type for each market-data stream.

The initial event hierarchy is:

```text
MarketEvent
├── TickerEvent
├── OhlcEvent
├── TradeEvent
└── OrderBookEvent
```

Only `TickerEvent` is required in the initial implementation.

The remaining event types will be introduced when their corresponding streams are implemented.

## Common Market Event Contract

Every market event must expose common market identity and traceability information.

The target contract is equivalent to:

```java
public sealed interface MarketEvent
        permits TickerEvent,
                OhlcEvent,
                TradeEvent,
                OrderBookEvent {

    UUID marketId();

    String provider();

    String symbol();

    MarketStreamType streamType();

    Instant occurredAt();
}
```

The exact use of a sealed interface may be adapted if framework constraints require a regular interface.

The architectural requirement is the specialized event hierarchy, not a specific Java language mechanism.

## Market Identity

Market events should carry both:

* a stable internal `marketId`;
* the provider-facing or display `symbol`.

The internal identifier is the preferred key for application logic.

The symbol remains useful for:

* display;
* logging;
* provider traceability;
* diagnostics.

This avoids making consumers depend exclusively on provider symbol conventions such as `BTC/USD` or `XBT/USD`.

## Ticker Event

The current `MarketDataEvent` should become a specialized `TickerEvent`.

A target model is equivalent to:

```java
public record TickerEvent(
        UUID marketId,
        String provider,
        String symbol,
        BigDecimal bid,
        BigDecimal ask,
        BigDecimal last,
        BigDecimal volume,
        Instant occurredAt
) implements MarketEvent {

    @Override
    public MarketStreamType streamType() {
        return MarketStreamType.TICKER;
    }
}
```

Fields should only be included when they represent normalized information consistently available to Trading OS.

Provider-specific fields must remain inside provider adapters.

## OHLC Event

The future OHLC stream should use a dedicated event contract.

A target model may include:

```java
public record OhlcEvent(
        UUID marketId,
        String provider,
        String symbol,
        OhlcInterval interval,
        Instant openTime,
        Instant closeTime,
        BigDecimal open,
        BigDecimal high,
        BigDecimal low,
        BigDecimal close,
        BigDecimal volume,
        boolean closed,
        Instant occurredAt
) implements MarketEvent {
}
```

The final contract will be defined when OHLC is implemented.

The distinction between the current candle and a completed candle must remain explicit.

## Trade Event

Individual market trades should later use a dedicated `TradeEvent`.

Typical information may include:

* trade identifier;
* price;
* quantity;
* aggressor side when deterministically available;
* execution time.

A trade must not be represented as a ticker update.

## Order-Book Event

Order-book data should later use a dedicated `OrderBookEvent`.

Typical information may include:

* bid levels;
* ask levels;
* depth;
* sequence or checksum information;
* snapshot or update semantics.

The precise order-book model requires a separate decision because snapshot reconstruction and incremental updates introduce additional consistency requirements.

## Provider Independence

Provider payloads must be converted by provider-specific adapters.

The processing pipeline becomes:

```text
Provider WebSocket payload
        ↓
Provider DTO
        ↓
Provider mapper
        ↓
Specialized MarketEvent
        ↓
Market Event Bus
        ↓
Application consumers
```

Kraken DTOs and Kraken-specific channel details must not leak into:

* scanners;
* frontend contracts;
* analytics;
* Trading Core;
* AI services.

## Market Event Bus

The existing publisher should progressively evolve from a ticker-specific publisher into a common market-event bus.

Its conceptual contract is:

```java
public interface MarketEventPublisher {

    void publish(MarketEvent event);

    Flux<MarketEvent> stream();
}
```

Typed or filtered streams may be exposed:

```java
<T extends MarketEvent> Flux<T> stream(Class<T> eventType);
```

or through explicit methods:

```java
Flux<TickerEvent> tickerStream();
Flux<OhlcEvent> ohlcStream();
```

The exact API should favor type safety and remain easy to understand.

A complex generic event-routing framework must not be introduced before multiple event types exist.

## Event, State and History Separation

Trading OS distinguishes three concepts.

### Real-Time Event

An immutable occurrence received or derived from a live market stream.

Examples:

* `TickerEvent`;
* `TradeEvent`;
* `OhlcEvent`;
* `OrderBookEvent`.

### Current Market State

A projection built from events.

Examples:

* latest ticker;
* current incomplete candle;
* reconstructed current order book.

This state may be cached for immediate access and frontend reconnection.

### Historical Market Data

Persisted or externally retrieved time-series information.

Examples:

* completed candles;
* historical trades;
* order-book snapshots.

A real-time event is not automatically persisted.

Persistence and retention policies remain separate responsibilities.

## Frontend Contracts

Frontend responses should reflect specialized stream types.

The frontend should not consume a universal object containing unrelated optional fields.

Examples include:

* `TickerEventResponse`;
* `OhlcEventResponse`;
* `TradeEventResponse`;
* `OrderBookEventResponse`.

The Market Detail page may combine several specialized streams without merging them into one generic response model.

## Scanner and AI Integration

Deterministic scanners consume specialized market events according to their needs.

Examples:

* lightweight passive monitoring may consume ticker and OHLC events;
* order-flow analysis may consume trades and order-book events;
* position monitoring may consume ticker and candle events.

The AI Engine should consume normalized analyses or selected market context rather than raw provider payloads.

This preserves the established rule that deterministic market calculations remain outside AI agents.

## Implementation Strategy

The migration should be incremental.

### First increment

1. Introduce `MarketEvent`.
2. Rename or replace `MarketDataEvent` with `TickerEvent`.
3. Adapt `KrakenTickerMapper`.
4. Adapt the event publisher and WebSocket handler.
5. Adapt the Angular ticker model.
6. Keep the existing real-time ticker behaviour unchanged.

### Second increment

1. Introduce an OHLC interval model.
2. Retrieve historical candles.
3. Introduce `OhlcEvent`.
4. Subscribe to real-time OHLC updates.
5. Display the chart on the Market Detail page.

Other event types should be added only when implemented.

## Consequences

### Advantages

* clear contracts for each market-data stream;
* fewer nullable and irrelevant fields;
* stronger type safety;
* easier validation and serialization;
* provider-independent consumers;
* cleaner frontend models;
* better support for charts, scanners and analytics;
* easier future AI-context construction.

### Trade-offs

* more domain types;
* additional mappers and response models;
* event-bus evolution;
* temporary migration work from `MarketDataEvent` to `TickerEvent`.

These trade-offs are accepted because the current ticker-centric model cannot scale cleanly to future market streams.

## Alternatives Considered

### Keep a Single MarketDataEvent

Rejected.

A universal event would progressively accumulate unrelated optional fields and unclear validation rules.

### Use a Generic Payload Map

Rejected.

A structure such as `Map<String, Object>` would reduce type safety, complicate consumers and allow provider details to leak into the domain.

### Expose Provider DTOs Directly

Rejected.

This would couple Trading OS to Kraken and make future providers difficult to integrate.

### Introduce All Event Types Immediately

Rejected.

Only event types backed by real implemented capabilities should be introduced. The abstraction is established now, while concrete models are added incrementally.

## References

Related decisions:

* Market Data Service owns public market-data retrieval and streaming.
* Provider-specific APIs are isolated behind adapters and mappers.
* Market-data collection is driven by measurable product and domain needs.
* Deterministic market analysis remains in Java services rather than AI agents.
* Active and passive scanners share persisted or cached market intelligence.
