# ADR-017 — Modélisation et diffusion déterministe de l’Order Book

## Statut

Proposé

## Date

2026-07-28

## Contexte

Trading OS doit compléter la page `Market Details` avec un carnet d’ordres exploitable en temps réel.

Kraken fournit les données de carnet d’ordres via WebSocket sous deux formes principales :

* un snapshot initial contenant l’état du carnet ;
* des mises à jour incrémentales contenant uniquement les niveaux modifiés.

Le frontend Angular ne doit pas avoir à connaître le protocole Kraken, reconstruire le carnet à partir de deltas, gérer les suppressions de niveaux ou résoudre les incohérences liées à l’ordre des messages.

Cette logique est déterministe et relève du domaine des données de marché. Elle doit donc être implémentée dans le service Java `market-data`, conformément aux principes existants de Trading OS :

* les traitements objectifs et déterministes restent dans les services Java ;
* les contrats externes Kraken restent confinés dans les adapters Kraken ;
* le frontend consomme des modèles métier indépendants du fournisseur ;
* les abonnements temps réel restent gérés par `MarketDataStreamProvider` ;
* les événements spécialisés remplacent l’ancien modèle générique `MarketDataEvent`, conformément à ADR-016.

L’objectif de la V1 est d’afficher un carnet d’ordres stable comprenant les niveaux bid et ask, le spread et un indicateur simple de déséquilibre.

## Décision

Trading OS reconstruira le carnet d’ordres complet côté backend à partir du snapshot initial et des mises à jour incrémentales Kraken.

Le frontend recevra des snapshots métier complets et cohérents, et non les deltas bruts de Kraken.

Le flux retenu est :

```text
Kraken WebSocket
        ↓
Kraken Order Book DTO
        ↓
KrakenOrderBookMapper
        ↓
OrderBook delta métier
        ↓
OrderBookStateService
        ↓
OrderBookSnapshot
        ↓
OrderBookEventPublisher
        ↓
WebSocket frontend
        ↓
Angular OrderBookComponent
```

## Modèle métier

### OrderBookLevel

Un niveau du carnet sera représenté par :

```java
public record OrderBookLevel(
        BigDecimal price,
        BigDecimal quantity
) {
}
```

Un niveau dont la quantité devient égale à zéro doit être supprimé du carnet.

### OrderBookSnapshot

L’état diffusé au frontend sera représenté par un snapshot immuable :

```java
public record OrderBookSnapshot(
        UUID marketId,
        MarketProvider provider,
        String symbol,
        int depth,
        List<OrderBookLevel> bids,
        List<OrderBookLevel> asks,
        BigDecimal bestBid,
        BigDecimal bestAsk,
        BigDecimal spread,
        BigDecimal bidVolume,
        BigDecimal askVolume,
        BigDecimal imbalance,
        Instant occurredAt
) {
}
```

Les listes `bids` et `asks` doivent être immuables.

Les bids sont triés par prix décroissant.

Les asks sont triés par prix croissant.

Le snapshot ne contient au maximum que le nombre de niveaux demandé par `depth`.

## Représentation interne du carnet

Le backend maintient un état interne distinct du snapshot diffusé.

L’état peut utiliser des structures ordonnées :

```java
NavigableMap<BigDecimal, BigDecimal> bids;
NavigableMap<BigDecimal, BigDecimal> asks;
```

Les bids utilisent un comparateur décroissant.

Les asks utilisent un comparateur croissant.

Cette représentation interne reste confinée au service responsable de la reconstruction du carnet et n’est pas exposée dans les contrats REST ou WebSocket.

## OrderBookStateService

Un service déterministe dédié sera responsable de :

* créer ou remplacer un carnet à partir d’un snapshot Kraken ;
* appliquer les mises à jour incrémentales ;
* supprimer les niveaux dont la quantité vaut zéro ;
* garantir le tri des niveaux ;
* limiter le snapshot à la profondeur demandée ;
* calculer les métriques dérivées ;
* produire un `OrderBookSnapshot` immuable ;
* supprimer l’état lorsqu’un abonnement n’est plus nécessaire.

Ce service ne dépend pas directement des DTO Kraken.

Il manipule uniquement des objets métier ou des commandes internes déjà mappées.

## Identité d’un carnet

Un carnet actif doit être identifié au minimum par :

```text
marketId + depth
```

Une clé dédiée pourra être utilisée :

```java
public record OrderBookKey(
        UUID marketId,
        int depth
) {
}
```

Cette distinction permet de maintenir plusieurs profondeurs si cela devient nécessaire.

Pour la V1, une seule profondeur active par marché est acceptable, à condition que le contrat reste extensible.

## Snapshot initial et deltas

Le premier message Kraken reçu après l’abonnement doit initialiser entièrement l’état du carnet.

Les messages suivants doivent être traités comme des mises à jour incrémentales.

Une mise à jour ne doit jamais être appliquée avant l’initialisation du snapshot.

Si une mise à jour arrive sans état initial valide, le service doit :

* ignorer la mise à jour ;
* journaliser une anomalie ;
* demander ou attendre une nouvelle initialisation selon les capacités du provider.

## Métriques déterministes

Les métriques suivantes seront calculées côté backend.

### Best bid

Prix le plus élevé disponible côté acheteur.

### Best ask

Prix le plus faible disponible côté vendeur.

### Spread

```text
bestAsk - bestBid
```

### Volume bid

Somme des quantités des niveaux bid présents dans le snapshot diffusé.

### Volume ask

Somme des quantités des niveaux ask présents dans le snapshot diffusé.

### Imbalance

```text
bidVolume / (bidVolume + askVolume)
```

La valeur est comprise entre `0` et `1`.

Une valeur supérieure à `0.5` indique une dominance du volume bid dans la profondeur observée.

Lorsque le volume total est nul, l’imbalance vaut `0.5`.

Ces calculs sont déterministes et doivent rester dans le backend Java.

Ils pourront plus tard être consommés par les scanners et l’AI Engine, sans être recalculés par le frontend.

## Contrat d’abonnement

L’abonnement continue d’utiliser `MarketStreamRequest`.

Exemple :

```json
{
  "type": "ORDER_BOOK",
  "parameters": {
    "interval": null,
    "depth": 10
  }
}
```

Le paramètre `depth` est obligatoire pour `ORDER_BOOK`.

Les profondeurs supportées doivent être validées avant l’appel Kraken.

Pour la V1, les profondeurs exposées au frontend seront limitées à un ensemble explicite, par exemple :

```text
10
25
```

Le service ne doit pas transmettre aveuglément une profondeur arbitraire au fournisseur.

## Provider WebSocket Kraken

`KrakenDataStreamProvider` reste responsable de :

* construire les commandes d’abonnement Kraken ;
* gérer la connexion WebSocket ;
* recevoir les messages ;
* identifier le channel `book` ;
* désérialiser les DTO Kraken ;
* mapper les messages Kraken vers un format interne indépendant du protocole ;
* transmettre les snapshots et deltas au service de reconstruction.

Il ne doit pas exposer directement les DTO Kraken aux autres couches.

## DTO Kraken

Les DTO Kraken dédiés au carnet restent dans le package de l’adapter Kraken.

Ils peuvent différer entre snapshot et update si les contrats JSON ne sont pas identiques.

La structure Kraken ne doit pas déterminer la structure de `OrderBookSnapshot`.

## Publication vers le frontend

Un `OrderBookEventPublisher` dédié sera introduit.

Il expose un flux filtré par marché et profondeur :

```java
Flux<OrderBookSnapshot> streamByMarketAndDepth(
        UUID marketId,
        int depth
);
```

Le publisher diffuse uniquement des snapshots complets et cohérents.

Le `MarketDataWebSocketHandler` sera étendu avec une branche `ORDER_BOOK`.

Les paramètres WebSocket frontend nécessaires sont :

```text
marketId
symbol
type=ORDER_BOOK
depth
```

Le handler ne reconstruit pas le carnet. Il choisit seulement le bon flux du publisher.

## Fréquence de publication

Le backend ne doit pas nécessairement envoyer un snapshot pour chaque micro-modification Kraken si le débit devient trop important.

Pour la première implémentation, chaque message Kraken valide peut produire un nouveau snapshot.

Une stratégie de limitation ou de regroupement pourra être ajoutée plus tard si les mesures montrent que le débit est excessif.

Toute optimisation future doit préserver :

* l’ordre des mises à jour ;
* la cohérence du carnet ;
* la fraîcheur suffisante pour l’usage humain ;
* l’absence de reconstruction côté frontend.

## Frontend Angular

Le frontend recevra directement un `OrderBookSnapshot`.

Le composant Angular sera purement présentatif et réactif.

Il affichera au minimum :

```text
Asks
Price | Quantity | Total

Spread

Bids
Price | Quantity | Total
```

Le frontend peut calculer des valeurs exclusivement visuelles comme la largeur relative d’une barre de profondeur.

Il ne doit pas :

* reconstruire les niveaux à partir de deltas ;
* supprimer lui-même les niveaux à quantité nulle ;
* trier les données Kraken ;
* recalculer les métriques métier principales ;
* dépendre des noms ou structures du protocole Kraken.

Les données seront consommées avec `Observable` et `async pipe`, conformément au standard réactif du frontend Trading OS.

## Cycle de vie

Lors du premier abonnement à un carnet :

```text
compteur 0 → 1
→ abonnement Kraken
→ initialisation du snapshot
→ diffusion frontend
```

Lorsqu’un consommateur supplémentaire demande la même clé :

```text
compteur N → N + 1
→ aucun nouvel abonnement Kraken
```

Lors du dernier désabonnement :

```text
compteur 1 → 0
→ désabonnement Kraken
→ suppression de l’état interne
→ arrêt de la diffusion
```

Le cycle de vie doit rester compatible avec `MarketSubscriptionService`.

## Gestion des erreurs

Les cas suivants doivent être gérés explicitement :

* profondeur non supportée ;
* snapshot Kraken invalide ;
* update reçu avant snapshot ;
* prix ou quantité invalide ;
* état absent lors d’une mise à jour ;
* erreur de désérialisation ;
* erreur d’émission dans le publisher ;
* déconnexion Kraken ;
* désynchronisation détectée si le protocole fournit un checksum.

Une donnée invalide ne doit pas corrompre silencieusement l’état actuel du carnet.

## Checksum

Si Kraken fournit un checksum du carnet, son support devra être prévu dans l’adapter.

La première implémentation peut différer sa validation si elle augmente fortement la complexité, mais la structure choisie ne doit pas empêcher son ajout ultérieur.

La validation du checksum, lorsqu’elle sera implémentée, restera côté backend.

## Persistance

Le carnet d’ordres n’est pas persisté dans la V1.

Il s’agit d’un état temps réel éphémère reconstruit à partir de Kraken.

Une persistance future pourra être envisagée pour :

* replay ;
* recherche ;
* analyse microstructurelle ;
* backtesting ;
* entraînement ou contexte IA.

Cette évolution ne doit pas modifier le contrat frontend principal.

## Tests requis

L’implémentation doit au minimum couvrir :

* initialisation depuis un snapshot ;
* tri décroissant des bids ;
* tri croissant des asks ;
* ajout d’un niveau ;
* modification d’un niveau ;
* suppression d’un niveau avec quantité zéro ;
* limitation à la profondeur demandée ;
* calcul du spread ;
* calcul des volumes bid et ask ;
* calcul de l’imbalance ;
* gestion d’une update avant snapshot ;
* séparation de deux marchés ;
* séparation de deux profondeurs ;
* nettoyage de l’état au dernier désabonnement.

## Conséquences positives

* Le frontend reste simple et indépendant de Kraken.
* Le carnet est reconstruit une seule fois côté backend.
* Les métriques déterministes deviennent réutilisables.
* Les scanners et l’IA pourront consommer un modèle stable.
* La page `Market Details` reçoit un contrat directement exploitable.
* La logique peut être testée sans connexion WebSocket réelle.
* Un changement de fournisseur ne modifie pas le composant Angular.

## Conséquences négatives

* Le service `market-data` doit maintenir un état en mémoire.
* La reconstruction augmente la complexité du backend.
* La diffusion de snapshots complets consomme plus de bande passante que les deltas.
* Le cycle de vie des abonnements et de l’état doit être rigoureusement synchronisé.
* Une reconnexion Kraken nécessite une nouvelle initialisation complète.

## Alternatives rejetées

### Envoyer les deltas Kraken au frontend

Rejeté, car cela couple Angular au protocole Kraken et duplique la logique de reconstruction.

### Exposer directement les DTO Kraken

Rejeté, car cela viole l’indépendance du domaine vis-à-vis du fournisseur.

### Recalculer le spread et l’imbalance dans Angular

Rejeté, car ces calculs déterministes doivent être centralisés et réutilisables.

### Persister immédiatement tous les niveaux

Rejeté pour la V1, car cela ajoute une complexité importante sans bénéfice immédiat pour la page `Market Details`.

### Utiliser l’AI Engine pour interpréter le carnet brut

Rejeté. La reconstruction, le tri, les volumes, le spread et l’imbalance sont des calculs déterministes appartenant au backend Java. L’AI Engine pourra consommer les résultats structurés ultérieurement.

## Plan d’implémentation recommandé

1. Créer les modèles `OrderBookLevel`, `OrderBookSnapshot` et `OrderBookKey`.
2. Créer les DTO Kraken snapshot/update.
3. Créer le mapper Kraken dédié.
4. Implémenter `OrderBookStateService`.
5. Ajouter les tests unitaires du carnet.
6. Étendre les commandes d’abonnement Kraken avec le channel `book`.
7. Créer `OrderBookEventPublisher`.
8. Étendre le dispatcher des messages Kraken.
9. Étendre `MarketDataWebSocketHandler`.
10. Ajouter le modèle Angular `OrderBookSnapshot`.
11. Ajouter `streamOrderBook()` dans `MarketDataStreamService`.
12. Créer `OrderBookComponent`.
13. Brancher le composant dans `MarketDetail`.
14. Tester les abonnements, changements de profondeur et désabonnements.
15. Nettoyer les logs temporaires et valider la conformité ADR.

## Résultat attendu

À la fin de l’implémentation, la page `Market Details` doit afficher un carnet d’ordres temps réel cohérent, trié et limité à la profondeur sélectionnée.

Le frontend ne reçoit que des snapshots métier complets.

Toutes les opérations déterministes de reconstruction et d’analyse élémentaire du carnet restent dans le service Java `market-data`.
