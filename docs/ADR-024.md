ADR-024 — Broker Credential Management and Account Connection

Status: Accepted

Date: 2026-07-29

Decision owners: Trading OS architecture

Scope: Broker account onboarding, credential lifecycle and secret management

Context

Trading OS utilise actuellement des variables d’environnement pour fournir les identifiants nécessaires à la connexion à Kraken. Cette approche est acceptable pour le développement local, les tests et les démonstrations contrôlées, mais elle n’est pas compatible avec un véritable produit multi-utilisateur.

Dans un produit utilisable depuis une interface, un utilisateur doit pouvoir :

connecter son propre compte broker sans accéder au serveur ;

fournir ses identifiants API depuis l’interface ;

tester la connexion avant activation ;

connaître l’état de la connexion ;

remplacer ou révoquer ses identifiants ;

connecter plusieurs comptes ;

conserver son compte métier même lorsque les secrets changent.

Le système doit simultanément garantir que les secrets :

ne deviennent jamais des données métier ordinaires ;

ne sont jamais persistés en clair ;

ne sont jamais renvoyés par une API de lecture ;

ne sont jamais exposés dans les logs, événements, métriques ou traces ;

ne transitent que dans les composants strictement nécessaires ;

restent remplaçables par une solution de gestion de secrets externe.

Cette ADR formalise la frontière entre le domaine Trading Core, le Broker Service et le sous-domaine d’infrastructure Secret Management.

Decision 1 — BrokerAccount Is a Trading Core Domain Object

Un BrokerAccount est un objet métier appartenant au Trading Core.

Il représente la relation entre un utilisateur Trading OS et un compte détenu auprès d’un broker externe.

Il contient au minimum :

son identifiant interne ;

l’identifiant de son propriétaire ;

le provider broker ;

un nom d’affichage ;

un identifiant externe lorsqu’il est disponible ;

l’état métier de la connexion ;

une référence opaque vers les credentials ;

les timestamps métier utiles ;

les informations de dernière validation et de dernière synchronisation.

Exemple conceptuel :

BrokerAccount
- id
- ownerId
- provider
- displayName
- externalAccountId
- connectionStatus
- credentialReference
- lastValidatedAt
- lastSynchronizedAt
- createdAt
- updatedAt

Le BrokerAccount ne contient jamais directement une API key, un API secret, une passphrase ou tout autre secret.

Le Trading Core possède :

l’identité métier du compte ;

son rattachement à l’utilisateur ;

les invariants de propriété ;

son état fonctionnel ;

les opérations métier autorisées.

Decision 2 — BrokerConnection Represents the Technical Connection

La connexion technique au broker est distincte du compte métier.

Le Broker Service possède un modèle de connexion technique, nommé conceptuellement BrokerConnection, qui référence :

le BrokerAccountId du Trading Core ;

le provider ;

la référence vers le secret ;

le statut technique de validation ;

les permissions détectées ;

les métadonnées de validation ;

la version de configuration du provider.

Cette séparation évite de faire dépendre le modèle métier du format technique propre à Kraken ou à un futur broker.

Un BrokerAccount peut survivre :

à une rotation de credentials ;

à une révocation temporaire ;

à une indisponibilité du broker ;

à une migration de stockage de secrets ;

à un changement d’adapter technique.

Decision 3 — Credentials Are Infrastructure Secrets

Les credentials broker sont des secrets d’infrastructure et non des données métier.

Ils sont gérés exclusivement dans le périmètre du Broker Service et du sous-domaine Secret Management.

Le Trading Core ne peut manipuler qu’une référence opaque :

CredentialReference

Cette référence :

n’expose aucune partie du secret ;

ne permet pas au Trading Core de déchiffrer les données ;

reste stable tant que le secret logique existe ;

peut pointer vers une implémentation locale, Vault, KMS ou un autre backend.

Le Broker Service est le seul service métier autorisé à demander la résolution d’un secret broker.

Decision 4 — Secret Management Is an Infrastructure Subdomain

Trading OS introduit un sous-domaine d’infrastructure explicite nommé Secret Management.

Il fournit des ports indépendants du fournisseur de stockage :

SecretWriter
SecretReader
SecretRotator
SecretRevoker

Le domaine métier ne connaît pas les implémentations.

Les premières implémentations peuvent être :

EncryptedDatabaseSecretStore
EnvironmentCredentialProvider

Les implémentations futures peuvent inclure :

HashiCorp Vault ;

AWS Secrets Manager ou KMS ;

Azure Key Vault ;

Google Cloud Secret Manager ou KMS ;

Docker Secrets ;

Kubernetes Secrets ;

un HSM ou service équivalent.

Changer d’implémentation ne doit pas modifier le modèle BrokerAccount ni les use cases du Trading Core.

Decision 5 — Credentials Are Encrypted Before Persistence

Aucun credential utilisateur ne peut être persisté en clair.

La première implémentation de production utilise un chiffrement authentifié, par exemple AES-GCM, avec :

une clé maître fournie à l’application par l’environnement d’exécution ;

un nonce ou IV unique par chiffrement ;

un tag d’authentification ;

une version de clé ;

des métadonnées de format ;

une séparation entre la donnée chiffrée et la clé maître.

Exemple conceptuel :

EncryptedSecretPayload
- ciphertext
- initializationVector
- authenticationTag
- keyVersion
- algorithm
- createdAt

La clé maître :

n’est jamais stockée dans la base applicative ;

n’est jamais exposée au frontend ;

n’est jamais incluse dans les sauvegardes de données métier ;

n’est jamais confondue avec un credential utilisateur ;

peut être remplacée ultérieurement par une clé gérée par KMS ou Vault.

L’utilisation d’un chiffrement non authentifié est interdite.

Decision 6 — Credentials Are Write-Only From the Product Perspective

Les secrets sont considérés comme write-only depuis le point de vue utilisateur et API produit.

Après leur soumission :

ils ne sont jamais retournés par une API REST ;

ils ne sont jamais affichés à nouveau ;

ils ne sont jamais exportés ;

ils ne sont jamais inclus dans un DTO de lecture ;

ils ne sont jamais récupérables depuis l’interface.

L’interface peut uniquement afficher un indice non sensible calculé lors de l’enregistrement, par exemple :

API key: ••••••••AB12

Cet indice ne doit pas contenir le secret et doit être suffisamment limité pour ne pas faciliter une attaque.

Le remplacement d’un secret nécessite la saisie complète d’un nouveau secret.

Decision 7 — Connection Validation Precedes Activation

Une nouvelle connexion n’est jamais considérée comme active avant validation auprès du broker.

Flux nominal :

User submits credentials
↓
Broker Service validates format
↓
Broker adapter calls external broker
↓
Identity and permissions are verified
↓
Credentials are encrypted and stored
↓
BrokerConnection becomes CONNECTED
↓
Trading Core BrokerAccount becomes CONNECTED

Le système ne persiste pas les credentials lorsque :

leur format est invalide ;

l’authentification échoue ;

le compte ne possède pas les permissions minimales requises ;

la réponse du broker ne permet pas une validation fiable.

Une indisponibilité temporaire du broker ne doit pas être confondue avec des credentials invalides.

Decision 8 — Explicit Connection Lifecycle

La connexion broker suit une machine à états explicite.

States

CREATED
PENDING_VALIDATION
CONNECTED
INVALID_CREDENTIALS
INSUFFICIENT_PERMISSIONS
TEMPORARILY_UNAVAILABLE
REAUTHENTICATION_REQUIRED
DISCONNECTED
REVOKED

Main transitions

CREATED → PENDING_VALIDATION
PENDING_VALIDATION → CONNECTED
PENDING_VALIDATION → INVALID_CREDENTIALS
PENDING_VALIDATION → INSUFFICIENT_PERMISSIONS
PENDING_VALIDATION → TEMPORARILY_UNAVAILABLE
CONNECTED → TEMPORARILY_UNAVAILABLE
CONNECTED → REAUTHENTICATION_REQUIRED
CONNECTED → DISCONNECTED
CONNECTED → REVOKED
INVALID_CREDENTIALS → PENDING_VALIDATION
INSUFFICIENT_PERMISSIONS → PENDING_VALIDATION
TEMPORARILY_UNAVAILABLE → CONNECTED
TEMPORARILY_UNAVAILABLE → REAUTHENTICATION_REQUIRED
REAUTHENTICATION_REQUIRED → PENDING_VALIDATION
DISCONNECTED → PENDING_VALIDATION

REVOKED est terminal pour la version du secret concernée.

Une rotation crée une nouvelle version de credentials sans recréer le BrokerAccount.

Les transitions invalides doivent être rejetées par le domaine.

Decision 9 — Principle of Least Privilege

Trading OS demande uniquement les permissions nécessaires à la fonctionnalité active.

Pour la première phase en lecture seule, les permissions attendues couvrent uniquement :

lecture des informations de compte ;

lecture des balances ;

lecture des positions lorsqu’elles sont disponibles ;

lecture des ordres ;

lecture de l’historique nécessaire à la synchronisation.

Les permissions de trading ne sont pas exigées tant que l’exécution d’ordres n’est pas activée.

Les permissions suivantes ne doivent jamais être demandées :

retrait de fonds ;

transfert de fonds non nécessaire ;

gestion des moyens de financement ;

administration complète du compte broker.

Le système doit détecter et signaler les permissions insuffisantes de manière structurée.

Une permission excessive peut être signalée à l’utilisateur, mais ne doit pas conduire le système à demander davantage de droits.

Decision 10 — Provider-Specific Validation Through Adapters

La validation dépend du broker et passe exclusivement par un adapter de provider.

Contrat conceptuel :

BrokerCredentialValidator
- validate(provider, credentialMaterial)
- detectPermissions(provider, credentialMaterial)
- resolveExternalAccountIdentity(provider, credentialMaterial)

Kraken constitue la première implémentation.

Le modèle commun ne dépend pas :

du nom exact des champs Kraken ;

de son format de signature ;

de ses codes d’erreur propriétaires ;

de ses permissions spécifiques.

Les erreurs provider sont traduites vers des erreurs de domaine stables.

Decision 11 — Structured Validation Outcomes

Une validation retourne un résultat structuré et non une simple valeur booléenne.

Exemple conceptuel :

CredentialValidationResult
- outcome
- externalAccountId
- detectedPermissions
- missingPermissions
- validatedAt
- providerDiagnostics

Outcomes initiaux :

VALID
INVALID_CREDENTIALS
INSUFFICIENT_PERMISSIONS
BROKER_UNAVAILABLE
RATE_LIMITED
UNSUPPORTED_CREDENTIAL_FORMAT
UNEXPECTED_PROVIDER_RESPONSE

Les diagnostics sont internes et nettoyés de toute donnée sensible.

L’API publique retourne un code stable et un message utilisateur sûr.

Decision 12 — Credential Rotation Does Not Recreate the Account

L’utilisateur peut remplacer ses credentials sans supprimer le BrokerAccount.

Le flux de rotation :

reçoit les nouveaux credentials ;

valide les nouveaux credentials ;

chiffre et persiste une nouvelle version ;

active atomiquement la nouvelle référence ;

révoque logiquement l’ancienne version ;

conserve l’historique non sensible de la rotation ;

déclenche une nouvelle validation métier du compte.

En cas d’échec avant activation, l’ancienne version reste active.

Le système ne doit jamais se retrouver sans version active à cause d’une rotation partiellement échouée.

Decision 13 — Revocation and Disconnection Are Distinct

DISCONNECTED signifie que Trading OS n’utilise plus temporairement la connexion, mais qu’une reconnexion ou une nouvelle validation peut être demandée.

REVOKED signifie que la version de secret ne peut plus être utilisée.

Une suppression utilisateur doit :

vérifier la propriété du compte ;

révoquer le secret actif ;

empêcher tout nouvel appel broker ;

annuler les opérations techniques en attente lorsque possible ;

conserver ou supprimer les données métier selon les règles de rétention distinctes du projet.

La suppression du BrokerAccount et la révocation du secret sont deux actions coordonnées mais conceptuellement distinctes.

Decision 14 — Strict Ownership and Authorization

Toute opération sur une connexion broker est autorisée par rapport à l’utilisateur authentifié.

Un utilisateur ne peut jamais :

lire le statut détaillé d’un compte appartenant à un autre utilisateur ;

remplacer ses credentials ;

déclencher sa validation ;

demander sa révocation ;

utiliser sa référence de secret.

Le Trading Core valide la propriété métier.

Le Broker Service ne fait pas confiance à un identifiant reçu sans contexte d’identité ou preuve inter-service appropriée.

Les identifiants techniques ne constituent jamais à eux seuls une autorisation.

Decision 15 — Service Responsibility Boundaries

Angular Frontend

Responsable de :

collecter les credentials une seule fois ;

utiliser des champs adaptés aux secrets ;

transmettre les données par HTTPS ;

afficher les statuts et erreurs sûres ;

permettre le remplacement ou la révocation.

Il ne doit jamais :

persister les secrets dans localStorage ;

persister les secrets dans sessionStorage ;

conserver les secrets dans un store applicatif durable ;

réafficher un secret précédemment enregistré ;

journaliser le formulaire ;

inclure un secret dans une URL.

API Gateway

Responsable de :

transmettre l’identité authentifiée ;

appliquer les contrôles transverses prévus ;

ne pas enregistrer les corps contenant des secrets ;

ne pas mettre en cache les requêtes de credentials.

Trading Core

Responsable de :

posséder BrokerAccount ;

vérifier la propriété ;

orchestrer le use case métier de connexion ;

conserver l’état métier ;

ne jamais voir ni persister les credentials en clair.

Broker Service

Responsable de :

recevoir temporairement les credentials ;

appeler le provider ;

valider identité et permissions ;

chiffrer ou déléguer l’écriture au Secret Management ;

résoudre le secret uniquement pour exécuter un appel broker autorisé ;

gérer rotation et révocation techniques ;

nettoyer toute donnée sensible des erreurs.

Secret Management

Responsable de :

stocker les secrets ;

les chiffrer et déchiffrer ;

gérer les versions ;

révoquer les versions ;

fournir des références opaques ;

permettre la migration vers un backend externe.

Decision 16 — REST API Uses Command-Oriented Endpoints

Les opérations contenant des secrets sont des commandes explicites.

Endpoints conceptuels :

POST   /broker-accounts
POST   /broker-accounts/{id}/credentials
POST   /broker-accounts/{id}/validate
PUT    /broker-accounts/{id}/credentials
POST   /broker-accounts/{id}/disconnect
DELETE /broker-accounts/{id}
GET    /broker-accounts
GET    /broker-accounts/{id}
GET    /broker-accounts/{id}/status

Les noms exacts peuvent être adaptés aux conventions existantes, mais la séparation lecture/commande doit être conservée.

Tous les contrôleurs Spring retournent des ResponseEntity, conformément aux conventions de Trading OS.

Aucun endpoint GET ne retourne un secret.

Les payloads contenant un secret ne doivent pas être idempotés par réutilisation d’un corps stocké en cache.

Decision 17 — Public DTOs Never Contain Secret Material

Les DTO d’écriture et de lecture sont séparés.

Exemples conceptuels :

CreateBrokerAccountRequest
- provider
- displayName

SubmitBrokerCredentialsRequest
- apiKey
- apiSecret
- optionalPassphrase

BrokerAccountResponse
- id
- provider
- displayName
- externalAccountId
- connectionStatus
- apiKeyHint
- detectedPermissions
- lastValidatedAt
- lastSynchronizedAt

Un DTO de réponse ne doit jamais contenir :

API key complète ;

API secret ;

passphrase ;

ciphertext ;

IV ;

key version interne ;

CredentialReference résoluble par le client.

Decision 18 — Secrets Are Excluded From Logs, Traces and Events

Les secrets ne doivent apparaître dans aucun système d’observabilité.

Sont interdits :

logs applicatifs ;

logs HTTP ;

traces distribuées ;

métriques avec labels dynamiques ;

événements de domaine ;

dead-letter queues ;

messages d’exception ;

rapports de test ;

captures Swagger/OpenAPI ;

audit contenant le payload brut.

Les classes transportant des secrets doivent :

éviter les toString() générés contenant les valeurs ;

éviter @Data lorsque cela génère des représentations dangereuses ;

masquer explicitement les champs sensibles ;

être traitées par des filtres de redaction lorsqu’un logging HTTP existe.

Les événements ne transportent que des identifiants et métadonnées non sensibles.

Decision 19 — Secret Material Has Minimal In-Memory Lifetime

Les credentials en clair ne doivent exister en mémoire que pendant la durée strictement nécessaire.

Les implémentations doivent :

éviter les copies inutiles ;

éviter leur présence dans des objets à longue durée de vie ;

ne pas les placer dans un cache ;

ne pas les stocker dans une session ;

ne pas les soumettre à une file de messages en clair ;

nettoyer les buffers mutables lorsque le langage et l’API le permettent.

En Java, l’usage de char[] ou d’un wrapper spécialisé peut être préféré pour les secrets sensibles, sans introduire une complexité disproportionnée dans les DTO HTTP.

Decision 20 — Credential Source Abstraction Supports Development Mode

Le mode .env reste supporté uniquement comme source de credentials de développement ou de démonstration.

Le système expose une abstraction conceptuelle :

BrokerCredentialSource

Implémentations initiales :

EnvironmentBrokerCredentialSource
StoredSecretBrokerCredentialSource

Règles :

le mode environnement ne représente pas un flux utilisateur ;

il ne doit pas permettre plusieurs utilisateurs réels ;

il est désactivé par défaut dans les profils de production ;

il est clairement identifié comme mode legacy/development ;

les use cases produit utilisent le stockage sécurisé.

La configuration choisit explicitement le mode actif.

Decision 21 — Multi-Broker Compatibility Is Mandatory

Le modèle commun ne dépend jamais de Kraken.

Le provider est représenté par une identité stable telle que :

KRAKEN

Les caractéristiques propres au broker sont encapsulées derrière des adapters et des descripteurs de credentials.

Un provider peut déclarer :

les champs requis ;

les permissions nécessaires ;

les capacités supportées ;

la stratégie de validation ;

les contraintes de rotation.

L’ajout d’un provider ne doit pas imposer de modifier les invariants centraux du BrokerAccount.

Decision 22 — Audit Records Contain Metadata Only

Les opérations sensibles sont auditables sans enregistrer les secrets.

Un audit peut contenir :

l’utilisateur ayant initié l’action ;

le BrokerAccountId ;

le provider ;

le type d’action ;

le résultat ;

la date ;

un correlation ID ;

une version de secret opaque ;

la cause métier nettoyée.

Il ne contient jamais :

le secret ;

le ciphertext ;

un hash réutilisable du secret ;

un payload complet ;

une réponse brute du broker.

Decision 23 — Failure Handling Preserves Security and State Consistency

Les erreurs doivent être classées et nettoyées.

Types initiaux :

INVALID_CREDENTIALS
INSUFFICIENT_PERMISSIONS
BROKER_UNAVAILABLE
RATE_LIMITED
SECRET_STORAGE_UNAVAILABLE
ENCRYPTION_FAILURE
DECRYPTION_FAILURE
OWNERSHIP_VIOLATION
CONNECTION_STATE_CONFLICT

Le système doit garantir que :

un échec de stockage ne marque pas la connexion comme active ;

un échec de rotation conserve l’ancienne version active ;

un échec de notification au Trading Core est récupérable ou réconciliable ;

aucune exception technique ne contient les credentials ;

les erreurs externes sont traduites en erreurs internes stables.

Les opérations distribuées doivent être conçues pour la cohérence éventuelle contrôlée, avec idempotence et réconciliation lorsque la transaction atomique inter-service n’est pas possible.

Decision 24 — Future Migration to External Secret Stores

L’implémentation chiffrée en base constitue un premier backend, pas une dépendance définitive.

Toute persistance passe par les ports du sous-domaine Secret Management.

Une migration future doit pouvoir :

lire une version depuis l’ancien backend ;

l’écrire dans le nouveau backend ;

valider la nouvelle référence ;

basculer atomiquement la référence active ;

révoquer l’ancienne version ;

conserver une trace d’audit non sensible.

Aucun use case métier ne doit être réécrit pour cette migration.

Security Requirements

L’implémentation doit respecter les contraintes suivantes :

HTTPS obligatoire en production ;

authentification et autorisation pour toutes les commandes ;

protection CSRF adaptée au mode d’authentification ;

limitation de débit sur validation et rotation ;

taille maximale des payloads ;

validation stricte des entrées ;

absence de secrets dans OpenAPI examples ;

désactivation du body logging pour les endpoints concernés ;

masquage des headers sensibles ;

séparation des rôles applicatifs et base de données ;

sauvegardes chiffrées ;

clé maître hors base ;

rotation de clé supportée par versionnement ;

accès minimal du Broker Service au Secret Store ;

absence d’accès direct du frontend et du Trading Core au Secret Store.

Implementation Constraints

L’implémentation doit respecter les contraintes suivantes :

Ne pas transférer les credentials au Trading Core si l’orchestration peut être réalisée sans cela.

Ne pas persister les secrets dans la base du Trading Core.

Ne pas exposer de repository de secrets hors du Broker Service/Secret Management.

Ne pas lier le domaine commun au DTO Kraken.

Ne pas utiliser un chiffrement déterministe.

Ne pas réutiliser un IV avec la même clé.

Ne pas stocker la clé maître dans Git, dans une migration SQL ou dans la base.

Ne pas créer d’endpoint de lecture des credentials.

Ne pas inclure les payloads sensibles dans les événements.

Ne pas autoriser un changement de propriétaire par simple update.

Ne pas supprimer le BrokerAccount lors d’une rotation.

Ne pas demander de permissions de retrait.

Utiliser ResponseEntity dans tous les contrôleurs REST.

Respecter la séparation ports/adapters existante du projet.

Préserver la compatibilité du mode de développement par configuration explicite.

Acceptance Criteria

ADR-024 est considérée comme correctement implémentée lorsque :

un utilisateur authentifié peut créer un BrokerAccount depuis l’API ;

il peut soumettre ses credentials sans modifier un fichier serveur ;

Kraken valide les credentials et les permissions ;

un secret valide est chiffré avant persistance ;

aucun secret invalide n’est conservé ;

le Trading Core ne persiste jamais de secret ;

les endpoints GET ne retournent aucun secret ;

les logs et traces ne contiennent aucun secret ;

un utilisateur ne peut pas manipuler le compte d’un autre utilisateur ;

une rotation réussie conserve le même BrokerAccount ;

une rotation échouée conserve les anciens credentials actifs ;

une révocation empêche toute nouvelle utilisation ;

le statut distingue credentials invalides, permissions insuffisantes et indisponibilité temporaire ;

le mode environnement reste disponible uniquement pour le développement ;

le backend de secrets est interchangeable derrière des ports ;

les tests de sécurité, domaine, intégration et architecture passent.

Consequences

Positive consequences

Les utilisateurs peuvent connecter leurs comptes depuis l’interface.

Le produit devient compatible avec un usage multi-utilisateur.

Les secrets sont isolés du domaine métier.

La rotation ne détruit pas l’historique du compte.

Kraken reste un adapter et non une dépendance du modèle commun.

Le système prépare une future migration vers Vault ou KMS.

La sécurité devient explicite et testable.

Le projet démontre une architecture DevSecOps crédible.

Negative consequences

Le flux de création de compte devient distribué et plus complexe.

Une gestion de clés et de versions doit être maintenue.

Les tests d’intégration exigent davantage de scénarios d’échec.

Les logs HTTP génériques doivent être adaptés.

Les migrations et sauvegardes doivent prendre en compte les secrets chiffrés.

La rotation de clé maître nécessite une procédure dédiée.

Risks

mauvaise configuration de la clé maître ;

exposition accidentelle par logging ou sérialisation ;

incohérence entre Trading Core et Broker Service ;

permissions broker mal interprétées ;

rotation partiellement appliquée ;

dépendance excessive à l’implémentation de stockage initiale.

Ces risques sont réduits par les frontières, ports, états, tests et critères définis dans cette ADR.

Rejected Alternatives

Keep credentials exclusively in .env

Rejeté car incompatible avec le multi-utilisateur et une interface produit.

Store credentials in the Trading Core database

Rejeté car le Trading Core ne doit pas posséder les secrets techniques des brokers.

Let Angular store credentials locally

Rejeté pour raisons de sécurité et d’exposition dans le navigateur.

Return credentials to the user after creation

Rejeté car les secrets sont write-only et ne doivent jamais être récupérables.

Hash credentials instead of encrypting them

Rejeté car le Broker Service doit réutiliser les credentials pour authentifier ses appels auprès du broker. Un hash non réversible ne répond pas au besoin.

Allow each capability or service to access the secret store

Rejeté car cela élargirait excessivement la surface d’accès aux secrets.

Couple the model directly to Kraken

Rejeté afin de préserver l’évolution multi-broker.

Final Decision

Trading OS remplace le modèle utilisateur fondé sur des credentials broker fournis par .env par un modèle de connexion de compte piloté depuis l’interface.

Le Trading Core possède le BrokerAccount et ses invariants métier. Le Broker Service possède la connexion technique, la validation du provider et l’utilisation des credentials. Le sous-domaine Secret Management possède le chiffrement, le stockage, le versionnement, la rotation et la révocation des secrets.

Les credentials sont write-only, chiffrés avant persistance, jamais retournés, jamais journalisés et accessibles uniquement au périmètre technique autorisé. Le mode environnement reste disponible pour le développement, tandis que le stockage sécurisé devient la stratégie produit par défaut.
