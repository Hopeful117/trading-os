# ML-01.1 - Dukascopy 12-Month Historical Dataset Readiness

## 1. Executive Summary

This read-only experiment evaluates the Dukascopy M1 dataset acquired for the
period `[2025-10-01T00:00:00Z, 2026-10-01T00:00:00Z)` for EUR/USD and GBP/USD.
It does not train a model, execute KMeans, modify scientific policy, or change
the source data.

The acquisition is reproducible and internally consistent at the M1 import
boundary:

| Instrument | M1 observations | Invalid | Malformed | Conflicting duplicates | Cross-file overlaps |
|---|---:|---:|---:|---:|---:|
| EUR/USD | 371,614 | 0 | 0 | 0 | 0 |
| GBP/USD | 371,266 | 0 | 0 | 0 | 0 |

The strict H1 diagnostic population is materially constrained by long unknown
gaps. There are no strict 57-H1 segments, which is the minimum contiguous span
for a 33-H1 feature lookback followed by H+24. Consequently:

- 93 EUR/USD and 24 GBP/USD strict full-H1 anchors have all four features
  available under the existing `VolatilityCalculator`.
- H+4 is available for 65 EUR/USD and 16 GBP/USD anchors.
- H+12 is available for 14 EUR/USD and 2 GBP/USD anchors.
- H+24 is available for 0 anchors for both instruments.
- The joint feature plus H+4/H+12/H+24 population is 0 for both instruments.

The dataset is therefore not ready for ML-01.2. The remaining blockers are
scientific and contractual, not acquisition failures: Dukascopy-specific H1
admissibility and closure evidence are not approved, the current ML-01
preparer is HistData-specific, and no approved partition, purge, embargo or
minimum effective-sample configuration exists.

## 2. Research Questions And Methodology

The experiment inspected ADR-092 through ADR-095, Story 0228, the Dukascopy
reader, the HistData reader and ML-01 preparation code, the existing feature and
outcome definitions, and the two previous ML-01.1 HistData reports.

The following existing Java capability was executed directly:

- `DukascopyOfflinePipeline.read(...)` for all 24 normalized monthly files.
- `DukascopyOfflinePipeline.assemble(...)` separately per instrument.
- Existing `VolatilityCalculator` for strict 33-H1 windows in a temporary,
  non-repository diagnostic harness.

An H1 diagnostic adapter was necessary because `DukascopyOfflinePipeline` only
exposes M1 observations, while `HistDataOfflinePipeline` hardcodes HistData's
source format and UTC-05 semantics. The adapter was not added to the
repository, did not modify source data, and did not define a new admissibility
policy. It only formed UTC H1 buckets and passed complete contiguous buckets to
the existing Java volatility calculator.

No Dukascopy-specific session or closure assumption was applied. Every gap not
covered by authoritative closure evidence remains unknown and is rejected for
continuity-dependent windows under ADR-094.

partial-H1 policy and continuity assumptions. The providers were not merged.

## 12. Scientific Limitations And Blockers

Confirmed limitations:

1. No authoritative Dukascopy historical closure calendar was supplied.
2. Long gaps remain unknown under ADR-094; they were not reclassified as
   weekends or holidays.
3. The existing H1 diagnostic adapter is temporary and is not a persisted
   Dukascopy ML-01 capability.
4. `Ml01HistDataPreparation` is coupled to HistData filenames, timezone and
   exploratory policy, so no Dukascopy ML-01 bundle was generated.
5. Partial-H1 admissibility for Dukascopy is not approved.
6. Chronological purge, feature-lookback overlap, embargo and scaling scope
   were not approved or applied.
7. No complete H+24 strict population exists, so ML-01 joint readiness is zero.
8. Raw anchor counts and greedy disjoint counts are not effective sample sizes.

## 15. Recommended Next Experiment Or Governance Decision

Before ML-01.2, obtain an explicit scientific decision on whether to:

1. retain strict Dukascopy continuity, in which case the current 12-month
   population is insufficient for the full H+24 protocol;
2. approve a provider-specific closure-evidence source, without turning a
   calendar heuristic into verified evidence; or
3. approve a separately versioned Dukascopy exploratory admissibility profile,
   with partial-candle and continuity strata reported separately.

After that decision, an approval-gated implementation may add a provider-neutral
ML-01 population adapter and regenerate a fingerprinted bundle. Partition dates,
future-window purge, feature-lookback overlap handling, embargo, train-only
scaling and minimum effective samples must be fixed before any KMeans execution.

No ML-01.2 run, KMeans execution, model training, policy modification, source
data modification, commit, push or pull request was performed for this
experiment.
