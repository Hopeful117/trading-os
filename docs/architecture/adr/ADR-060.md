# ADR-060 - Versioned Feature Projection and Immutable FeatureSnapshot

## Status

Accepted for Story 0108A implementation.

## Related Decisions

- ADR-048 - Intelligence Evidence and Authority.
- ADR-056 - Deterministic Market Intelligence Evidence and Analyzer Boundary.
- ADR-057 - Historical Market Evidence, Known-At Semantics, and Source Retention.
- ADR-058 - Historical Market Intelligence Replay and Evidence Acquisition Boundary.
- ADR-059 - Objective Future Market Outcomes and Evaluation Truth.

## Decision

Trading OS represents research features as a versioned projection of trusted
deterministic Market Intelligence artifacts. `FeatureProjection` is derived
research representation and is not a business authority or a second analytical
engine.

The authority chain is:

```text
historical evidence
    -> IntelligenceContext @ T0
    -> deterministic analyzers
    -> typed persisted artifacts
    -> FeatureProjection
    -> immutable FeatureSnapshot
```

The projection consumes only artifacts produced under the same T0 boundary.
It must not depend on `ObservedMarketOutcome`, future evidence, maturity, or
current provider responses. Future outcomes remain separate immutable facts and
may later be associated with the same snapshot for several horizons.

## Projection Version and Schema

The first projection is `feature-projection-v1`. The version owns the exact
feature definitions, semantic names, order, types, units, source semantics,
transformations, categorical representation and missingness rules. A semantic
change requires a new projection version; an existing version is never silently
redefined.

Feature order is defined by the schema and never by map iteration, reflection,
database row order or JSON object order. Numeric values remain `BigDecimal`,
categorical values remain canonical strings, and booleans remain booleans.
Statistical preprocessing belongs to a later ML boundary.

## Missingness and Provenance

Missingness is explicit and is not represented by zero, false or an unqualified
NaN. Feature values may be absent with statuses such as `MISSING`,
`INSUFFICIENT_DATA`, `STALE_INPUT`, `INVALID_INPUT`, `UNAVAILABLE`,
`UNSUPPORTED` or `NOT_APPLICABLE`.

Snapshots retain the context fingerprint, evaluation cutoff, evidence policy,
projection version and available analyzer, algorithm, rule, profile, policy,
parameter, input, result and source-evidence provenance. Operational timestamps
and database identifiers do not participate in deterministic identity.

## Identity, Fingerprint and Immutability

Snapshot identity is based on the market, T0, context fingerprint, projection
version and semantic analyzer provenance. Outcome horizon and outcome identity
are explicitly excluded so one snapshot can be reused across multiple future
outcomes.

The snapshot fingerprint includes the ordered schema definitions, ordered typed
values and semantic provenance. It excludes creation time, database IDs,
randomness, outcomes and future evidence. PostgreSQL persistence is append-only
with a unique fingerprint and explicit conflict detection.

## Persistence and Boundary

PostgreSQL remains canonical. The physical representation uses relational
identity/provenance columns and a versioned typed payload for feature values,
group status and analyzer provenance. This is a small hybrid persistence model,
not a generic EAV feature store.

Python, ML models, datasets, labels, preprocessing, exports, ResearchSample,
manifests and outcome joins are outside this decision and Story 0108A.
