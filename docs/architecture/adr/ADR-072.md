# ADR-072 - Opaque Broker Provider Selection at the Trading Core Boundary

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-23 |
| **Decision Makers** | Project Owner, Trading OS Architecture |
| **Related ADRs** | ADR-030, ADR-041, ADR-043, ADR-071 |
| **Related Stories** | Story 0145, Story 0146 |

---

## 1. Context

Trading Core currently contains a concrete `BrokerProvider` enum while Broker
Service owns the provider registry and provider-specific capabilities. This is
inconsistent with ADR-030 and ADR-041, which require Trading Core to remain
provider-neutral and forbid provider identifiers, DTOs, SDKs and authentication
details from crossing into the core domain.

ADR-071 selects cTrader as the future execution platform, but does not authorize
coupling Trading Core to cTrader. Story 0146 must establish the next provider
foundation without adding `CTRADER` to a Trading Core enum.

## 2. Decision

Provider identity and provider selection authority remain inside Broker Service.

Trading Core SHALL:

- route execution and account facts using the local `BrokerAccount.id` only;
- preserve the explicit `Account.brokerAccountId` relation;
- not contain concrete provider enums, provider names, provider DTOs, provider
  SDK types, provider authentication details or provider error types;
- use an opaque broker-owned provider-registration reference only where a
  connection command must select a provider;
- treat that reference as routing input, never as financial Account identity;
- never resolve an Account through `(owner, provider)`.

Broker Service SHALL:

- own the provider catalog and concrete provider identifiers;
- resolve the opaque provider-registration reference to a provider internally;
- validate that the selected provider is registered and capable for the requested
  operation;
- return a broker-neutral unavailable/unsupported result when no capability is
  registered;
- never fall back from one provider to another.

The exact opaque reference representation is an implementation detail, provided
that it cannot expose or require a concrete provider enum in Trading Core.

## 3. Identity Invariants

```text
Account.accountId       = financial identity
BrokerAccount.id        = execution/routing identity
BrokerConnection.id     = Broker Service connection identity
Provider identity       = Broker Service authority
External account ID     = provider identity, never local routing identity
```

The `Account.brokerAccountId` relation remains the canonical financial-to-routing
relation. Provider metadata retained for legacy compatibility must not become the
canonical relation and must not override Broker Service authority.

## 4. Capability and Failure Semantics

- An opaque provider reference that cannot be resolved fails closed.
- A resolved provider with no registered capability fails as unavailable.
- No provider fallback is allowed.
- No account facts means no valid Risk context and no new execution.
- Timeout remains distinct from rejection.
- Unknown financial outcomes require reconciliation and cannot be blindly retried.

## 5. Security Boundary

Credentials, tokens, authorization details, provider payloads and provider errors
remain inside Broker Service. Trading Core receives only broker-neutral outcomes
and opaque routing references where required.

Ownership is validated by the application boundary using the authenticated owner,
the local BrokerAccount identity and the Broker Service connection owner. An opaque
provider reference is never an authorization credential.

## 6. Consequences

Positive:

- cTrader can be added without introducing a cTrader enum into Trading Core.
- Broker Service remains the sole provider catalog and capability authority.
- Account and BrokerAccount identities remain distinct.
- Unsupported provider capabilities fail explicitly instead of falling back.
- Future provider additions do not require provider-specific Trading Core branches.

Trade-offs:

- Provider-selection commands require an opaque reference contract.
- Existing Trading Core provider enum usage must be migrated or retired.
- Legacy provider metadata may require a compatibility transition.
- Provider catalog discovery is a later Broker Service concern and is not
  implemented by this ADR.

## 7. Rejected Alternative

Adding `CTRADER` to the Trading Core `BrokerProvider` enum is rejected because it
would make the core depend on a concrete provider identifier and contradict
ADR-030, ADR-041 and the provider boundary in ADR-071.

Adding a synthetic or fake provider capability is also rejected because it would
make provider recognition appear equivalent to provider availability.

## 8. Scope Boundary

This ADR does not authorize:

- cTrader OAuth or token lifecycle;
- cTrader SDK or transport;
- cTrader account synchronization;
- FTMO rules or Challenge phase progression;
- execution, modification, close or reconciliation implementation;
- Market Data integration;
- changes to Risk formulas or human authorization.

## 9. Required Follow-Up

Story 0146 may implement only the provider-neutral foundation after this ADR is
approved. It must preserve the opaque reference and Broker Service ownership
defined here. Any change to the provider-selection contract or identity authority
requires a new ADR or an explicit amendment decision.
