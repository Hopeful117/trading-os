## 1. Context

Trading OS has two account concepts with different responsibilities:

```text
Account.accountId
    = Trading Core financial account identity

BrokerAccount.id
    = execution and broker-routing identity
```

These identifiers are independently generated and represent different domain
concepts. `Account` owns balances, equity, trades, and local financial state.
`BrokerAccount` owns provider, execution mode, connection metadata, and routing
identity.

ADR-042 establishes the corresponding position authority boundary:

```text
LIVE  position authority = external broker/provider
PAPER position authority = Trading Core
```

The repository currently has no direct durable relation between `Account` and
`BrokerAccount`. It instead uses several incomplete or inconsistent mechanisms:

- `AccountRiskConfiguration` contains both IDs but is not created by PAPER
  account provisioning;
- PAPER settlement searches by `(owner, provider)`;
- T1 currently treats `ExecutionIntent.brokerAccountId` as an Account ID;
- Story 0038 assigns the same UUID to both entities in its persistence fixture;
- PAPER risk evaluation still uses the external `BrokerRiskFactsPort`.

The result is that a PAPER account can be created and a simulated entry can be
persisted, while the real T0/T1 risk path cannot reliably resolve the same
logical financial account without test-only assumptions.

## 2. Problem Statement

The architecture must define:

- distinct financial and execution identities;
- the canonical durable relationship between them;
- first-milestone cardinality and ownership invariants;
- explicit PAPER risk configuration lifecycle;
- mode-correct Risk Facts acquisition;
- correct identity flow through T0 and T1;
- fail-closed behavior when required facts or configuration are unavailable.

The decision must not collapse `Account` and `BrokerAccount`, make provider
lookup an identity mechanism, or move risk interpretation into infrastructure
adapters.

## 4. Decision

Trading OS adopts the following identity model:

```text
Account.accountId
    = financial Account identity

BrokerAccount.id
    = execution/routing identity

Account -> BrokerAccount
    = explicit durable canonical relation
```

The two identifiers SHALL remain distinct. Equal UUID values, if they occur by
accident, SHALL NOT imply identity equivalence.

No service SHALL use any of the following as the canonical relationship:

- equality of the two UUIDs;
- `(owner, provider)` lookup;
- display name;
- provider-specific external identifiers;
- existence of a risk configuration row.

The exact Java field or persistence representation is an implementation
decision. The relation semantics are architectural and fixed by this ADR.

## 5. Canonical Relationship Authority

The canonical Account-to-BrokerAccount relation belongs to the account/domain
model, independently of risk configuration.

The current `account_risk_configuration.broker_account_id` SHALL NOT be the
sole identity authority because:

- risk configuration may not exist;
- account identity exists independently of policy;
- the column currently lacks a foreign key to `broker_account`;
- PAPER account creation does not create the configuration;
- risk policy lifecycle must not determine account identity lifecycle.

If the current configuration column remains during migration, it SHALL be one
of:

- transitional mapping data; or
- validated configuration metadata that cannot disagree with the canonical
  Account relation.

It SHALL NOT become a second independently mutable relationship.

Required invariant:

```text
ACCOUNT_RISK_CONFIGURATION_BROKER_ACCOUNT_ID
    CANNOT_DRIFT_FROM_CANONICAL_RELATION
```

## 6. Cardinality

For the first milestone:

```text
Account 1 <-> 1 BrokerAccount
```

More precisely:

- one financial Account maps to exactly one BrokerAccount;
- one BrokerAccount maps to at most one canonical financial Account.

This supports multiple accounts for one user and provider:

```text
User
    +-- BrokerAccount A -> Account A
    +-- BrokerAccount B -> Account B
    +-- PAPER BrokerAccount -> PAPER Account
```

The architecture SHALL NOT introduce `BrokerAccount -> N financial Accounts`
without a demonstrated product requirement for multiple financial views,
portfolios, or policies over one external account.

This first-milestone constraint remains evolvable through a future ADR.

## 7. Ownership, Provider, and Mode Invariants

### 7.1 Ownership

The linked records must belong to the same authenticated owner:

```text
Account.user.userId == BrokerAccount.ownerId
```

Database foreign keys may enforce record existence, but cross-record owner
consistency requires deterministic domain/application validation unless the
schema is deliberately designed for composite enforcement.

### 7.2 Provider

`BrokerAccount.provider` is the provider authority.

The legacy `Account.broker` string is metadata and must not become the new
canonical provider identity. If retained during migration, it must agree with
the linked BrokerAccount or be treated as stale/legacy data and rejected where
provider correctness matters.

### 7.3 Execution Mode

Execution mode is authoritative on `BrokerAccount`:

```text
Account -> BrokerAccount -> executionMode
```

PAPER is an execution mode, not a `BrokerProvider`.

No duplicate independently mutable execution mode is introduced on `Account`.

## 8. Account Creation Invariant

A newly usable trading account must establish the following logical graph:

```text
BrokerAccount
    + financial Account
    + canonical relation
    + explicit RiskConfiguration
    + assigned immutable RiskProfile
        = risk-ready trading account
```

For PAPER, the following is insufficient:

```text
BrokerAccount exists
    + legacy Rules exists
```

Account creation must not report a PAPER account as risk-ready unless the
explicit configuration and profile requirements are satisfied or the account
is clearly marked unavailable for trading.

The exact local transaction/orchestration boundary remains implementation work.

## 9. Risk Configuration

`RiskConfiguration` represents policy and limits. It is separate from current
financial state:

```text
RiskConfiguration
    = policy, limits, version, assignment and provenance

RiskFacts
    = current factual account, position and market state

RiskEngine
    = deterministic interpretation and decision
```

PAPER SHALL require an explicit, versioned, persisted RiskProfile assignment
before it is eligible for deterministic trading evaluation.

The legacy `Rules` entity is not implicitly equivalent to the current

- `Rules.java:16-49` is unversioned legacy configuration;
- `RiskPersistence.java:259-301` models versioned immutable profiles and
  assignments;
- `V2__trade_plan_risk_evaluation.sql:1-43` defines the current schema.

The current legacy values are not an authorized default policy for the current
RiskProfile architecture.

```text
DEFAULTS_AUTHORIZED_BY_EXISTING_POLICY = NO
```

The system must not invent a default PAPER profile or silently copy a profile
from another account. Until an explicit versioned default policy is approved,
PAPER provisioning must either require explicit setup or remain unavailable for
trading.

Missing or invalid policy fails closed.

## 10. Risk Facts Boundary

The logical Risk Facts boundary SHALL be neutral and mode-independent:

```text
RiskFacts boundary
    +-- LIVE facts
    +-- PAPER facts
```

The boundary represents factual snapshots, completeness, timestamps, and
provenance. It does not evaluate policy or authorize execution.

The existing `BrokerRiskFactsPort` may remain temporarily as a LIVE adapter or
compatibility boundary. This ADR does not require a mechanical rename. The
semantic target is a neutral Risk Facts contract, not a naming-only refactor.

## 11. Risk Facts Routing

Risk Facts source selection belongs to Trading Core application orchestration
or a mode-aware application adapter/router.

The target flow is:

```text
Application layer
    -> resolve financial Account
    -> resolve canonical BrokerAccount
    -> read execution mode
    -> select authoritative facts source
    -> assemble immutable RiskEvaluationContext
    -> invoke Risk Domain
```

The Risk Domain SHALL NOT inspect:

- `ExecutionMode`;
- `BrokerProvider`;
- repositories;
- Feign clients;
- provider DTOs;
- Broker Service availability.

Mode changes fact acquisition authority, not risk interpretation authority.

## 12. LIVE Risk Facts

LIVE financial and position facts remain externally authoritative where the
provider owns them:

```text
LIVE
    -> Broker Service
    -> external provider
    -> provider-neutral Risk Facts
    -> immutable RiskEvaluationContext
    -> Risk Domain
```

Local Trading Core projections may support display, audit, or correlation, but
must not silently replace fresh provider authority for LIVE risk evaluation.

This preserves ADR-042 and ADR-040 provider reconciliation semantics.

## 13. PAPER Risk Facts

PAPER facts are authoritative in Trading Core:

```text
PAPER
    -> persisted Account / AccountBalance
    -> persisted Trade and execution/fill state
    -> local baseline and realized state where required
    -> Market Data for current valuation inputs
    -> provider-neutral Risk Facts
```

PAPER risk evaluation SHALL NOT require:

- Broker Service account facts;
- provider credentials;
- provider balances;
- provider position queries;
- provider reconciliation;
- external broker mutation.

Market Data supplies current prices and conversion/valuation inputs only. It
does not own PAPER account identity, balances, positions, or risk policy.

## 14. Required Risk Facts

The current Risk Domain consumes factual inputs including:

- balance;
- equity;
- used and free margin;
- daily-start balance;
- daily closed PnL;
- open positions;
- position market value;
- position loss at stop;
- position margin;
- current market prices;
- proposed notional and expected loss;
- required margin.

Evidence:

- `risk-domain/src/main/java/com/hope/trading/risk/snapshot/AccountSnapshot.java:8-27`
- `risk-domain/src/main/java/com/hope/trading/risk/snapshot/PositionSnapshot.java:8-22`
- `risk-domain/src/main/java/com/hope/trading/risk/metric/ObservedMetricsCalculator.java:6-12`
- `risk-domain/src/main/java/com/hope/trading/risk/metric/ProjectionEngine.java:14-38`
- `trading-core/src/main/java/com/hope/trading/trading_core/risk/application/TradePlanRiskEvaluationService.java:154-200`

The authority matrix is:

| Fact | LIVE authority | PAPER authority | Market Data required? |
|---|---|---|---|
| Balances | Broker Service/provider | Local AccountBalance | No |
| Equity | Provider facts plus valuation | Local state plus valuation | Often |
| Used margin | Provider facts | Explicit supported PAPER calculation | As defined by calculation |
| Daily start balance | Provider ledger/baseline | Local baseline or local ledger | Possibly |
| Daily closed PnL | Provider trades/ledger | Local closed Trade/execution state | For conversion only |
| Open exposure | Provider positions | Local OPEN Trade state | No |
| Entry basis | Provider position | Local Trade/fill state | No |
| Position value | Provider state plus valuation | Local exposure plus valuation | Yes |
| Position risk/protection | Provider protective facts | Explicit local PAPER representation | Possibly |
| Current price | Provider/market snapshot | Market Data | Yes |
| Required margin | Broker-neutral authoritative source | Explicit supported PAPER source | Usually |
| Provider position reference | Provider | Not applicable | No |

The ADR does not invent PAPER margin, fee, slippage, or protective-stop
semantics. Those remain implementation dependencies or separate decisions.

## 15. Required Margin Gap

The current required-margin implementation is deliberately unavailable:

- `UnavailableRequiredMarginClient.java:7-13`

It returns an empty result until an authoritative broker-neutral margin read
exists. This can independently prevent complete T0/T1 evaluation.

The required behavior is:

```text
missing required margin
    -> risk context unavailable
    -> no authorization
```

It must not become zero by default. Margin architecture is an implementation
dependency and is not expanded by this ADR.

## 16. T0 Identity Flow

T0 SHALL use the financial Account identity:

```text
RiskEvaluation.Command.accountId
    -> Account.accountId
    -> Account ownership validation
    -> canonical BrokerAccount relation
    -> provider/mode validation
    -> mode-aware Risk Facts source
    -> immutable RiskEvaluationContext
    -> Risk Domain
```

The risk configuration and assigned profile are keyed by the same financial
Account ID. The linked BrokerAccount ID is used for routing and external facts,
not as a substitute Account ID.

## 17. T1 Identity Flow

T1 SHALL resolve the same financial Account as T0.

The target flow is:

```text
ExecutionIntent
    + brokerAccountId
    |     = routing identity
    |
    + TradePlanReference
          -> TradePlan.tradingAccountId
                = financial Account identity
          -> Account
          -> canonical BrokerAccount relation
          -> relation must match intent.brokerAccountId
          -> mode-aware Risk Facts source
          -> T1 RiskEvaluationContext
```

The current behavior is incorrect:

```text
intent.brokerAccountId
    -> AccountRepository.findById
```

The T1 risk persistence record must store the financial Account ID in its
`account_id` field. Unavailable/error persistence must not substitute the
BrokerAccount ID where the financial Account ID is known.

## 18. Settlement Identity Consequence

PAPER settlement must eventually resolve the same canonical financial Account
used by T0 and T1:

```text
ExecutionIntent.brokerAccountId
    -> canonical Account relation
    -> Account financial state
```

`(owner, provider)` lookup is not an authoritative settlement mapping.

Settlement implementation remains governed by ADR-042 and is not changed by
this documentation ADR.

## 19. Fail-Closed Behavior

Required facts and configuration are mandatory inputs. The following conditions
must prevent authorization:

- financial Account missing;
- canonical relation missing;
- linked ownership inconsistent;
- provider or execution mode inconsistent;
- RiskConfiguration missing;
- assigned RiskProfile missing;
- RiskProfile invalid or incomplete;
- required Market Data unavailable or incomplete;
- required margin unavailable;
- local PAPER state inconsistent;
- required valuation impossible.

Failures must remain distinguishable where practical:

| Condition | Classification |
|---|---|
| Missing Account | Account/domain lookup failure |
| Missing relation or inconsistent owner | Mapping/domain invariant failure |
| Missing configuration/profile | Configuration unavailable |
| Invalid profile | Configuration invalid |
| Missing market input | Valuation unavailable |
| Missing margin | Risk dependency unavailable |
| Inconsistent local state | Domain/context invalid |

No missing fact may silently become zero, empty exposure, unlimited risk, or a
successful validation unless that value is proven authoritative.

## 20. Security and Ownership

Authorization must follow the complete identity chain:

```text
authenticated user
    -> BrokerAccount.ownerId
    -> linked Account.user.userId
    -> Account financial state
    -> risk configuration/profile
    -> local PAPER positions
```

The application must validate ownership before exposing or mutating either
account's state. A database relation alone is insufficient if it permits
cross-user links.

Provider and execution mode must be validated from the linked BrokerAccount,
not accepted from an untrusted client as authoritative facts.

## 21. Migration and Legacy Data

This ADR introduces no migration. Future implementation requires:

```text
SCHEMA_CHANGE_REQUIRED = YES
BACKFILL_REQUIRED = YES
BACKFILL_DETERMINISTIC_FOR_ALL_ROWS = NO
AMBIGUOUS_LEGACY_ROWS_POSSIBLE = YES
```

Provable backfill evidence may include:

- existing `account_risk_configuration.broker_account_id`;
- valid Account and BrokerAccount existence;
- matching ownership;
- matching provider;
- consistent execution mode.

`(owner, provider)` is not sufficient as a universal backfill key. Existing
BrokerAccount rows can have the same owner/provider, while the Account model's
`UNIQUE(user_id, broker)` constraint represents a different and narrower rule.

The Story 0038 equal-UUID fixture is not migration evidence.

Future migration must:

- backfill only provable mappings;
- quarantine or reject ambiguous rows;
- require explicit manual resolution where necessary;
- never choose the first matching account;
- never reinterpret existing UUID meaning;
- preserve existing LIVE external authority.

## 22. Database Constraint Direction

Future schema work should distinguish:

### Database-enforceable invariants

- foreign key from the canonical relation to `broker_account`;
- first-milestone uniqueness for the one-to-one relationship;
- required relation after a complete migration/provisioning transition;
- existence of the linked Account and BrokerAccount.

### Domain/application invariants

- Account owner equals BrokerAccount owner;
- provider metadata consistency;
- execution-mode lifecycle validity;
- risk readiness;
- mode-correct fact routing;
- complete and trustworthy local PAPER facts.

The existing `UNIQUE(user_id, broker)` constraint must be explicitly reviewed
and safely replaced or relaxed during implementation if multiple accounts for a
provider are supported. It is not changed by this ADR.

## 23. Alternatives Considered: Identity

### A. Same Account/BrokerAccount UUID

Rejected.

- the entities have different responsibilities;
- production creates independent identifiers;
- equality hides incorrect lookups;
- it couples financial identity to execution routing;
- Story 0038 demonstrates the resulting false confidence.

### B. Explicit durable relation

Accepted.

- explicit and auditable;
- deterministic;
- supports multiple accounts;
- preserves distinct identities;
- allows ownership/provider/mode invariants to be validated.

### C. `(owner, provider)` lookup

Rejected as canonical identity.

- ambiguous with multiple accounts;
- does not identify a financial Account;
- current Account and BrokerAccount uniqueness rules differ;
- cannot safely support LIVE/PAPER coexistence.

### D. Dedicated identity entity or value object

Deferred.

The first milestone does not justify another abstraction if an explicit one-to-
one relation is sufficient. A future identity abstraction may be introduced if
the relationship becomes more complex than the current model supports.

## 24. Alternatives Considered: Risk Facts

### A. Use `BrokerRiskFactsPort` for every mode

Rejected as the long-term semantic boundary.

It gives Broker Service/provider facts authority over PAPER state and requires
credentials or an external account that PAPER does not possess.

### B. Neutral mode-aware Risk Facts boundary

Accepted.

It preserves the distinction between factual inputs and risk interpretation and
supports both external LIVE facts and local PAPER facts.

### C. Router above the existing LIVE adapter

Accepted as a staged implementation technique.

The existing LIVE adapter can remain while a mode-aware router selects a local
PAPER source.

### D. Mode branching inside the Risk Domain

Rejected.

It would make the deterministic Risk Domain aware of infrastructure and
execution providers. Mode belongs to fact acquisition, not rule interpretation.

## 25. Alternatives Considered: PAPER Risk Configuration

### A. Promote legacy Rules automatically

Rejected.

Legacy `Rules` are not versioned `RiskProfile` records and have no approved
translation or provenance path.

### B. Require explicit valid profile assignment

Accepted for the first milestone.

It is fail-closed and does not invent limits.

### C. Copy a profile from another account

Rejected/deferred.

It creates hidden policy inheritance and ambiguous provenance.

### D. Automatically create a versioned default profile

Deferred until a default policy and its limits are explicitly authorized.

## 27. Relationship to Other ADRs

### ADR-042

ADR-042 remains authoritative for position authority and close semantics:

```text
LIVE_POSITION_AUTHORITY = BROKER
PAPER_POSITION_AUTHORITY = TRADING_CORE
```

ADR-043 provides the account identity and facts-source architecture required to
make that distinction executable safely. It does not supersede ADR-042 and does
not decide PAPER position query, exit, or settlement implementation.

### ADR-028

```text
ADR_028_COMPATIBLE = YES
ADR_028_AMENDMENT_REQUIRED = NO
```

ADR-028 already requires immutable context, fact acquisition outside the Risk
Domain, deterministic interpretation, provenance, and fail-closed behavior.
ADR-043 changes where context facts are acquired, not who interprets them.

An amendment is required only if later implementation changes risk-rule
semantics, result meanings, fail-closed behavior, or introduces new rule
categories.

### ADR-029

ADR-029 remains authoritative for execution lifecycle, idempotency, attempts,
orders, reconciliation, and execution audit. `ExecutionIntent.brokerAccountId`
continues to identify execution routing and must not be repurposed as a
financial Account ID.

### ADR-041

```text
ADR_041_COMPATIBLE = YES
ADR_041_AMENDMENT_REQUIRED = NO
```

ADR-043 preserves:

- human authorization;
- mandatory server-side T1;
- separate T0/T1 provenance;
- LIVE external authority;
- fail-closed safety.

ADR-041 contains contradictory implementation-status statements about T1. That
is documentation debt and is not rewritten by this ADR.

## 28. Scope Boundary

This ADR does not decide or implement:

- PAPER position-query implementation;
- PAPER EXIT implementation;
- PAPER realized-PnL settlement;
- universal Position aggregate;
- simulation realism;
- fees, slippage, latency, or partial fills;
- pending orders;
- cTrader integration;
- FTMO rules;
- frontend UX;
- automatic profile inheritance;
- final default risk limits;
- new Risk Domain rules;
- changes to `RiskValidationResult` semantics;
- backtesting or historical replay.

## 29. Future Implementation Tests

No tests are created by this ADR. Future implementation must prove:

### Identity

- application-created Account and BrokerAccount have distinct IDs;
- the explicit relation resolves the correct Account;
- multiple accounts for one provider are unambiguous;
- cross-user relations are rejected;
- provider/mode mismatches are rejected;
- missing relations fail closed.

### Risk Configuration

- explicit profile assignment survives reload;
- legacy Rules alone are insufficient;
- missing/invalid configuration blocks evaluation;
- no implicit unlimited or zero policy is created.

### PAPER Facts

- PAPER T0 and T1 use local financial facts;
- PAPER evaluation makes zero Broker Service financial/position-facts calls;
- Market Data is used only for valuation inputs;
- missing local facts fail closed.

### LIVE Regression

- LIVE T0 and T1 preserve Broker Service/provider authority;
- local PAPER routing does not alter LIVE facts or reconciliation.

### T0/T1 Identity

- both evaluations use the same financial Account ID;
- `ExecutionIntent.brokerAccountId` remains routing identity;
- T1 persists financial Account ID;
- distinct-ID execution succeeds without fixture aliasing.

### Restart

```text
create PAPER account
    -> persist
    -> reload
    -> relation/profile intact
    -> deterministic risk evaluation remains possible
```
