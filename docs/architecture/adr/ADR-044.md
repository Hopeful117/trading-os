## 1. Context

Trading OS currently contains an API Gateway, Trading Core, Broker Service,
Market Data, Market Intelligence, and Eureka. The Gateway is the intended
external product entry point. Trading Core and Broker Service already validate
user JWTs locally. Market Data and Market Intelligence do not currently expose
an equivalent local Spring Security boundary.

The current code also contains several identity paths:

- the original user JWT;
- `X-Actor-Id` added by the Gateway for some Market Intelligence routes;
- `actorId` in request payloads;
- `actorId` in query parameters;
- user and resource identifiers in URL paths.

The Gateway currently derives `X-Actor-Id` from its authenticated context for
some routes. This is only safe if the receiving service can establish that the
caller is trusted to assert the identity. A header rewrite alone does not
authenticate the caller to the receiving service.

Docker Compose also publishes several service ports for local development.
That is useful for debugging, but it must not silently become the production
trust boundary.

The security audit found concrete consequences of the current ambiguity:

- several Trade operations do not perform explicit ownership checks;
- Market Intelligence accepts actor identity through request data on some paths;
- Market Intelligence and Market Data lack a visible local security boundary;
- internal endpoints depend in part on network placement rather than explicit
  service authentication;
- public Gateway routes and downstream mappings are not fully aligned.

## 2. Problem Statement

Trading OS needs a V1 trust model that distinguishes four independent concerns:

```text
USER AUTHENTICATION
    Who is the end user, if any?

SERVICE AUTHENTICATION
    Which Trading OS service is calling?

ACTOR PROPAGATION
    On whose behalf is the operation being performed?

RESOURCE AUTHORIZATION
    May that actor access or mutate this resource?
```

The architecture must prevent a client-controlled actor identifier from becoming
an authorization authority. It must also support future scheduled and system
operations without inventing fake user identities, while remaining practical
for the current Spring, Feign, Eureka, and Docker Compose architecture.

## 3. Decision Drivers

- Establish an explicit trust boundary instead of relying on naming or network
  placement alone.
- Preserve defense in depth in Trading Core and Broker Service.
- Keep the V1 mechanism implementable without introducing an OAuth server,
  service mesh, Kubernetes, or a cloud IAM platform.
- Allow a receiving service to validate a caller independently.
- Preserve verifiable user context for synchronous user-driven operations.
- Represent service identity separately from delegated user identity.
- Make key rotation and testing possible without redesigning the platform.
- Keep public market reads separate from sensitive internal market operations.
- Avoid silently breaking Angular login, onboarding, market browsing,
  intelligence, planning, risk, PAPER execution, position queries, and PAPER
  exit.

## 4. Considered Options

### 4.1 Forward the original user JWT only

The Gateway and services forward the browser's signed JWT. Each downstream
service validates the same issuer, signature, expiry, and relevant claims.

Advantages:

- smallest change for synchronous user-driven calls;
- preserves the actual user identity;
- compatible with existing Gateway, Trading Core, Broker Service, and Feign
  concepts;
- no new token issuer is required.

Limitations:

- authenticates the user, not the calling service;
- does not distinguish a browser-originated request from a service-originated
  request using the same token;
- is not suitable as the only credential for system operations;
- does not prove that Service A is authorized to assert a delegated actor to
  Service B.

Conclusion: useful as a user-context mechanism, insufficient as the complete
service-to-service trust model.

### 4.2 Dedicated internal or service JWT

Each service authenticates internal calls with a short-lived service JWT. The
token identifies the caller service, target audience, expiry, token id, and
optionally a delegated actor derived from a validated user context.

Advantages:

- explicitly authenticates service identity;
- supports calls without a browser user;
- works with Spring Security filters and Feign interceptors;
- can be tested locally with configured keys;
- does not require a new authorization server.

Limitations:

- requires a signing-key distribution and rotation policy;
- requires clear claim and audience validation;
- delegated user context must be signed by a trusted caller, not copied from a
  client payload;
- a single shared secret would not distinguish one service from another and is
  therefore not sufficient for individual service identity.

Conclusion: appropriate for V1 if service keys are distinct and externally
configured. This ADR selects this option for internal calls.

### 4.3 OAuth2 client credentials or machine identity

Services obtain access tokens from an OAuth2 authorization server.

Advantages:

- mature machine identity and token lifecycle model;
- strong support for scopes, audiences, rotation, and cloud deployment;
- suitable for a larger service estate.

Limitations:

- Trading OS has no authorization server in the current architecture;
- introduces a new availability-critical platform dependency;
- adds operational and local-development complexity before current ownership
  gaps are fixed.

Conclusion: deferred future evolution, not selected for V1.

### 4.4 Mutual TLS

Services mutually authenticate with certificates at the transport layer.

Advantages:

- strong service identity and channel protection;
- independent of application payload headers;
- well suited to mature production platforms.

Limitations:

- certificate issuance, distribution, renewal, and local debugging are
  significant operational work;
- does not itself carry user identity or ownership context;
- does not fit the current Compose/Eureka setup without additional tooling.

Conclusion: compatible with a future hardened deployment, deferred for V1.

### 4.5 Network trust only

Services trust calls because they arrive on the internal Docker or cloud
network.

Advantages:

- no application changes;
- simple local deployment.

Limitations:

- `/internal/**` and a private network are not authentication;
- a compromised or misrouted workload can impersonate another service or user;
- direct ports and topology changes bypass the assumption;
- no trustworthy user or service identity is established.

Conclusion: rejected as an authorization boundary. Network restriction remains
a defense-in-depth control only.

### 4.6 Hybrid model

User JWTs carry synchronous user context, while internal service JWTs carry
service identity and, when needed, a signed delegated actor. Public market reads
remain public by policy. Internal operations require service authentication.

Conclusion: selected for V1 because it addresses both user-driven and future
system-driven calls without introducing an authorization server or service
mesh.

## 5. Decision

Trading OS SHALL use a hybrid V1 trust model:

1. The API Gateway is the supported production external application ingress.
2. Every sensitive downstream service retains local application security and
   validates the credential relevant to its endpoint.
3. A user JWT is the source of end-user identity for synchronous user-driven
   operations. A downstream service may validate the same JWT independently.
4. Internal service-to-service endpoints require an explicit service principal
   credential. V1 uses short-lived signed service JWTs with distinct
   per-service signing keys, configured externally.
5. A service JWT may contain a delegated actor only when the calling service
   derived that actor from a previously validated user context and is trusted
   by the receiving service to delegate that context.
6. User identity, service identity, delegated actor, and resource ownership are
   represented and authorized as separate concerns.
7. Client-provided actor identifiers never establish identity or authorization.
8. Network isolation is required in production where practical, but never
   replaces service authentication or resource authorization.

V1 does not require a central token issuer. A future OAuth2 client-credentials
or mTLS deployment may replace the internal service JWT mechanism without
changing the conceptual trust model.

## 6. Trust Model

### 6.1 External user operation

```text
Browser
    | Authorization: Bearer <user JWT>
    v
API Gateway
    | validates user JWT
    | strips client identity headers
    v
Service A
    | validates user JWT locally
    | derives actor from authenticated principal
    | server-side ownership check
    | optional internal call with service JWT
    v
Service B
    | validates Service A identity and audience
    | validates delegated actor claim, if present
    | server-side ownership check
```

The user JWT establishes the user. It does not establish that Service A is
Service A. The internal service JWT establishes the caller service. A delegated
actor is accepted only as a signed, authorized delegation from that caller.

### 6.2 Internal or system operation

```text
Trusted Service / Scheduler
    | short-lived service JWT
    | sub = SERVICE_PRINCIPAL
    | actor = absent or SYSTEM
    v
Internal API
    | validates caller, audience, expiry, and permissions
    | performs operation without fake user UUID
```

System work has no user actor unless it is explicitly delegated from a
validated user operation. `SYSTEM`, or no actor where actor context is not
meaningful, is preferable to a fabricated user identifier.

### 6.3 Conceptual token claims

The exact claim names belong to implementation, but the service credential must
be able to express:

- caller service identity;
- target audience/service;
- issued-at and short expiry;
- unique token identifier for replay controls where needed;
- service permissions or endpoint class;
- optional delegated actor identity;
- delegation provenance or authentication method.

An internal service JWT is not a replacement for object-level ownership checks.

## 7. Actor Propagation Rules

### 7.1 Authoritative identity sources

For a user-authenticated request, actor identity is derived in this order:

1. locally validated user JWT principal;
2. locally validated internal service JWT delegated actor claim;
3. no actor for a service-only/system operation.

`actorId` in a body, query parameter, or path is a target or business input,
never an identity source.

### 7.2 Disagreement rule

If a request actor identifier is present and differs from the authenticated or
trusted delegated actor, the request MUST be rejected. The service MUST NOT
silently select the client value or silently overwrite a conflicting value.

This rule applies to:

- request payload `actorId`;
- query parameter `actorId`;
- user identifiers in paths when they purport to identify the caller;
- `X-Actor-Id` supplied by an external client.

### 7.3 X-Actor-Id policy

`X-Actor-Id` is not a trusted contract and is not required in the target V1
model. It should be removed from the public identity protocol.

During migration, if compatibility requires the header:

- the Gateway MUST strip any client-supplied value before authentication;
- the Gateway MAY overwrite it with a value derived from its validated user
  context for explicitly compatible routes;
- the receiving service MUST authenticate the caller independently;
- the receiving service MUST compare the header with its authenticated or
  trusted delegated actor;
- a mismatch MUST be rejected;
- the header MUST never be used as the sole authorization authority.

New endpoints MUST use authenticated principal or signed delegated context,
not `X-Actor-Id`.

## 8. Endpoint Trust Classes

Trading OS SHALL use four small endpoint trust classes:

| Class | Meaning | Required controls |
|---|---|---|
| `PUBLIC` | Deliberately public information only | No user identity required; bounded input, rate limits, and safe output. |
| `USER_AUTHENTICATED` | Product operation for an end user | Valid user JWT or trusted delegated user context plus object authorization. |
| `SERVICE_INTERNAL` | Service-to-service operation | Valid service principal, target audience, endpoint allowlist, and explicit actor semantics. |
| `MANAGEMENT` | Operational or administrative surface | Internal/restricted network and separate operational authorization; never normal product traffic. |

The `/internal/**` path is a naming convention that commonly maps to
`SERVICE_INTERNAL`; it is not a security mechanism by itself.

## 9. Service-by-Service Consequences

### 9.1 API Gateway

- Remains the supported production external ingress.
- Validates external user JWTs for non-public product routes.
- Removes or overwrites identity-related headers supplied by clients.
- Does not make downstream services trust a request merely because it passed
  through the Gateway.
- Does not route `/internal/**` as public product traffic.
- May propagate a user JWT to the first downstream service where the service
  can validate it.
- Must not expose a client-controlled `X-Actor-Id` as trusted metadata.

### 9.2 Trading Core

- Retains local JWT validation as defense in depth.
- Remains authoritative for users, accounts, user-specific trading state,
  deterministic risk, PAPER financial state, and execution orchestration.
- Derives user actor from the local authenticated principal.
- Must perform server-side ownership authorization for Account, BrokerAccount,
  Trade, TradePlan, Execution, Position, and risk configuration resources.
- Uses a service principal when calling internal Broker Service, Market Data,
  or Market Intelligence endpoints.
- Does not treat authentication as proof of resource ownership.

### 9.3 Broker Service

- Retains local JWT validation and sensitive endpoint protection.
- Credentials, broker accounts, execution, cancellation, and reconciliation
  remain sensitive operations.
- User-driven calls may carry a validated user context, but internal execution
  calls must also authenticate Trading Core as the caller service.
- Background reconciliation uses a service principal and has no fake user actor
  unless a real delegated user operation exists.
- Broker Service remains responsible for broker-specific credential and provider
  protections; this ADR does not redesign LIVE broker behavior.

### 9.4 Market Intelligence

- User-facing analysis, scans, opportunities, and planning operations obtain
  actor identity from validated authentication context.
- Legacy body/query `actorId` values are not authoritative.
- Gateway -> Market Intelligence calls use validated user context for user
  operations and a service credential for internal operations.
- Trading Core -> Market Intelligence calls use a service credential and a
  signed delegated actor only when acting on behalf of a user.
- Internal risk and planning handoffs require service authentication even when
  a delegated actor is present.

### 9.5 Market Data

- Public market catalogue and public market reads may remain `PUBLIC` where the
  operation is genuinely public and bounded.
- Internal valuation batches, provider operations, expensive/unbounded work,
  and management endpoints require `SERVICE_INTERNAL` or `MANAGEMENT` trust.
- Public status does not imply that every Market Data endpoint is public.
- The public WebSocket, if retained, is a deliberate public market-read
  surface with origin policy, input bounds, connection controls, and rate
  limits. It is not an internal trust channel.

### 9.6 Eureka

- Is infrastructure, not a user-facing product API.
- Remains internal/restricted in production.
- Registration and discovery do not authenticate business actors or replace
  service authentication.

## 10. Public Market Data Policy

Public market information does not automatically require user authentication.
The following may remain public when their data and cost characteristics justify
it:

- market catalogue;
- ticker;
- OHLC;
- order book;
- recent trades.

The following are not automatically public:

- internal valuation snapshot batches;
- provider credentials or provider operations;
- unbounded or expensive queries;
- management and operational endpoints.

Market Data therefore has separate endpoint policies rather than an all-public
or all-user-authenticated service boundary.

## 11. Gateway Header Sanitation

At the external boundary, the Gateway MUST strip client-supplied values for
identity headers, including `X-Actor-Id` and future service/delegation headers.

If a compatibility header is generated, the Gateway MUST overwrite rather than
merge the value. The generated value must come from the Gateway's validated
security context. Downstream services must still authenticate the caller and
validate ownership or delegation.

No external client may choose the value of a trusted identity propagation
header.

## 12. Ownership Authorization

Authentication answers:

```text
Who is calling?
```

Authorization answers:

```text
May this caller perform this operation?
```

Ownership answers:

```text
Does this actor own or control the requested resource?
```

For user-owned aggregates, a valid user or delegated actor is only a starting
point. The authoritative service must resolve the resource and validate its
relationship to that actor before reading or mutating it.

This applies at minimum to Account, BrokerAccount, Trade, TradePlan, Execution,
Position, RiskConfiguration, and credentials. Resource identifiers may be
client-supplied targets; they do not grant access.

## 13. Internal Endpoint Semantics

`/internal/**` means "not part of the public product route contract". It does
not mean "trusted without authentication".

In production, internal endpoints should normally have all of the following:

- no public Gateway route;
- service principal authentication;
- target audience and endpoint allowlist checks;
- network restriction as defense in depth;
- explicit user delegation only when the operation is on behalf of a user;
- explicit system/service context when it is not;
- no reliance on arbitrary actor headers or payload fields.

Not every internal endpoint needs a user actor. A service may perform an
operation as itself or as `SYSTEM`, provided the receiving service authorizes
that service for the operation.

## 14. Original User JWT Forwarding

Original user JWT propagation is allowed for synchronous user-driven operations
when all of the following hold:

- the receiving service can independently validate signature, issuer, expiry,
  and intended audience;
- transport occurs over a protected internal channel;
- the token is not logged or exposed in error data;
- the receiving service derives the actor from its validated principal;
- object ownership is checked locally.

Feign clients may propagate the token through a controlled request interceptor,
but propagation must not be implemented by copying arbitrary actor headers.

Forwarding the user JWT does not establish service identity. Internal calls to
sensitive endpoints therefore also require a service credential under this
ADR. The two identities are complementary:

```text
user JWT       -> user context
service JWT    -> caller service context
ownership      -> resource authorization
```

For a service-to-service call, the implementation may use a service JWT with a
signed delegated actor claim rather than forwarding the original token again.
The choice is an implementation detail as long as the actor is verifiable and
the caller service is authenticated.

## 15. Production Topology Principles

Production deployment SHALL follow these properties:

- Gateway is externally reachable.
- Service ports are internal unless explicit exposure is justified and
  separately protected.
- Eureka is internal/restricted.
- Management endpoints are internal/restricted and use the `MANAGEMENT` class.
- Databases are internal and not product ingress points.
- Public Market Data is exposed only through deliberate route and policy
  decisions.
- Network isolation supplements, but does not replace, application security.
- Docker Compose port publication for local debugging does not define the
  production trust model.

Kubernetes, a service mesh, and cloud-specific network controls are not required
by this ADR.

## 16. Local Development Consequences

Local development may publish direct service ports for debugging and integration
testing. This is a `DEV_CONVENIENCE`, not a production authorization boundary.

Local configurations must still make it possible to test:

- Gateway authentication;
- downstream local JWT validation;
- service JWT validation on internal endpoints;
- delegated actor validation;
- mismatch rejection;
- object ownership failures;
- public Market Data reads without user JWT;
- protected internal Market Data operations.

Test keys and local secrets may be generated for development, but production
secrets must never use predictable defaults.

## 17. Secret Management Requirements

This ADR establishes only trust-relevant requirements:

- production signing secrets and keys are supplied externally;
- missing required production secrets fail fast;
- no predictable fallback production secret is accepted;
- secrets are not committed to the repository;
- secrets and bearer tokens are not logged;
- service signing keys are distinct enough to establish the configured caller
  identity;
- key identifiers and an overlap period must support future rotation.

This ADR does not select Vault, a cloud secret manager, or another complete
secret-management platform.

## 18. Migration Strategy

The decision is architectural; implementation belongs to a later approved
security hardening Story. The migration should be staged:

1. Define endpoint trust class and caller/delegation contracts.
2. Add shared validation primitives and test key material for local tests.
3. Keep Trading Core and Broker Service local JWT validation.
4. Add service-principal validation to sensitive internal endpoints.
5. Add controlled Feign propagation for user JWT or signed delegated context.
6. Sanitize identity headers at Gateway and reject actor mismatches.
7. Add local ownership authorization to legacy Trade and other user-resource
   operations.
8. Add Market Intelligence local authentication and remove actor authority from
   body/query fields.
9. Add stronger protection to internal Market Data operations while preserving
   public read classes.
10. Align Gateway routes and downstream mappings, including Execution.
11. Restrict production service and management exposure.
12. Add contract, negative, IDOR, delegation, and multi-user integration tests.

The migration must preserve the existing user-facing flows and must not change
the LIVE/PAPER position authority established by ADR-042.

## 19. Security Invariants

The following invariants are accepted by this proposed ADR:

1. Gateway is the supported production external ingress. **Established.**
2. Client-provided `actorId` is never authorization authority. **Established.**
3. Trusted actor headers are stripped or overwritten at ingress. **Established.**
4. Sensitive services retain local security. **Established.**
5. User-owned resources require server-side ownership authorization. **Established.**
6. `/internal/**` naming alone provides no security. **Established.**
7. Public Market Data may remain unauthenticated where genuinely public. **Established.**
8. Internal Market Data operations require stronger trust than public reads. **Established.**
9. Service ports are not publicly exposed in production unless explicitly justified. **Established.**
10. Management and Eureka surfaces are internal/restricted. **Established.**
11. Production secrets have no predictable fallback. **Established.**
12. Background operations use service/system identity rather than fake user identity. **Established.**

## 20. Consequences

### Positive

- User authentication, service authentication, actor propagation, and ownership
  become explicit and independently testable.
- A downstream service can reject an unauthenticated or unauthorized caller
  even when the request bypasses the Gateway.
- `X-Actor-Id`, body `actorId`, and query `actorId` can no longer silently grant
  access.
- Market Data can preserve public reads without exposing sensitive internal
  operations.
- Background work has a valid identity model without fake users.
- Existing Spring Security, Feign, Eureka, and Compose components remain usable.

### Negative

- Services need local credential validation and per-service key configuration.
- Feign calls require explicit propagation/interceptors and endpoint policies.
- Delegation adds a second identity dimension that must be visible in logs and
  tests without logging secrets.
- Some legacy APIs will need compatibility handling or removal in the later
  hardening Story.
- Local development requires test keys and negative security tests rather than
  relying only on an open Docker network.

## 21. Rejected Alternatives

- Gateway-only authentication: rejected because downstream bypasses remain
  possible and sensitive services need defense in depth.
- Network trust only: rejected because topology is not caller authentication.
- One shared internal secret with a self-declared caller name: rejected because
  any holder could impersonate any service.
- OAuth2 client credentials in V1: deferred because no authorization server
  exists and the operational cost is premature.
- mTLS in V1: deferred because certificate operations exceed the current
  platform need, while preserving it as a future transport hardening option.
- Client-controlled `X-Actor-Id`: rejected as an identity authority.
- Treating authenticated user identity as proof of ownership: rejected because
  object-level authorization remains mandatory.

## 22. Deferred Decisions

- Whether service JWT issuance uses a small shared internal component, per-service
  local signing, or a future OAuth2 issuer.
- Exact signing algorithm, key format, JWKS publication, and rotation protocol.
- Whether delegated actor context is carried in an internal service JWT or in a
  separate signed delegation artifact.
- Fine-grained scopes or endpoint permission vocabulary.
- mTLS or a service mesh for a future production platform.
- Full system-operation policy for Research Lab, AI agents, and monitoring.
- Cleanup or deletion of individual legacy endpoints.
- Live broker credential and execution redesign.

These decisions must not weaken the invariants established here.

## 23. Story Boundary

This ADR does not create or implement Story0044. Story0044 remains blocked until
this ADR is accepted by the human engineer.

After acceptance, the implementation Story should cover the audit findings that
depend on this trust model, including:

- Gateway identity-header sanitation;
- local authentication for Market Intelligence and protected Market Data
  operations;
- controlled JWT/service-context propagation;
- ownership enforcement;
- actor mismatch rejection;
- legacy actor input migration;
- service-port and management exposure policy;
- route/downstream contract tests.

Security-core work should be classified as `LEARN` or `PAIR` where ownership,
delegation, and trust-boundary behavior are changed. Routine implementation may
be delegated only after the trust contract is understood and approved.

- ADR-014 remains authoritative for the decision pipeline and responsibility
  boundaries.
- ADR-029 and ADR-030 remain authoritative for execution and Broker Service
  responsibilities; this ADR adds caller trust requirements without moving

- ADR-041 remains authoritative for human authorization and financial command
  safety; authentication does not replace human approval.
- ADR-042 remains authoritative for LIVE and PAPER position authority.
- ADR-043 remains authoritative for Account/BrokerAccount identity and mode-

This ADR adds the cross-service trust and identity boundary. It does not
redefine domain ownership or financial authority.
