# ADR-036 — Split Strategy Governance into Validation and Operational Dimensions

## Status

Accepted

## Date

2026-08-22

## Context

ADR-034 defined a single strategy lifecycle:

```text
DRAFT → CANDIDATE → VALIDATED → ENABLED → RETIRED
```

with `validationStatus` (UNVALIDATED | VALIDATED) as separate metadata
expressing whether accepted deterministic evidence actually supports the
strategy. ADR-034 also granted the bootstrap legacy strategy a temporary,
human-approved exception: it is permitted to run under controlled evaluation
while UNVALIDATED, and it MUST NOT be silently labeled as quantitatively
validated.

While Story 0013 made the pipeline strategy-agnostic and Story 0014 added a
second real production strategy (`OHLC_RANGE_EXPANSION_V1`), this single
lifecycle proved ambiguous for human engineers:

* DRAFT, CANDIDATE and VALIDATED describe maturity/validation progress;
* ENABLED describes operational activation;
* RETIRED describes end of life.

Concretely, the model could not answer two simple questions independently:

> "Is this strategy validated?" — mixed with activation intent.
>
> "Is this strategy allowed to run live?" — required knowing lifecycle rules,
> and nothing enforced them: the production pipeline evaluated every built-in
> strategy regardless of its declared lifecycle, so DRAFT was effectively
> ENABLED.

The legacy fixture illustrates the ambiguity perfectly: it must run live
(ADR-035 historical truth compatibility, shadow parity monitoring) while being
truthfully UNVALIDATED. Under the single lifecycle there is no honest state
for "running, unvalidated, temporarily permitted".

## Decision Question

How should strategy governance be modeled so that maturity/validation and
operational activation are explicit, independent dimensions with a single
domain source of truth for live-evaluation eligibility?

## Decision

Strategy governance SHALL be split into two independent dimensions on
`StrategyDefinition`:

### 1. Validation / maturity — `ValidationStatus` (unchanged)

```text
UNVALIDATED | VALIDATED
```

plus the mandatory `validationEvidenceRef` when VALIDATED. This dimension
answers: what level of accepted deterministic evidence supports this strategy?
It never indicates whether the strategy runs live.

REJECTED was considered and deliberately not introduced: no repository
workflow produces rejections today; adding it would be speculative.

### 2. Operational status — new `StrategyOperationalStatus`

```text
DISABLED | ENABLED | BOOTSTRAP_CONTROLLED_RUN | RETIRED
```

This dimension answers: is this strategy currently authorized to participate
in live evaluation?

* `DISABLED`: not authorized for live evaluation.
* `ENABLED`: fully governed authorization; requires `VALIDATED` plus accepted
  evidence (aggregate invariant).
* `BOOTSTRAP_CONTROLLED_RUN`: explicit data-level representation of the
  ADR-034 temporary exception — an UNVALIDATED bootstrap migration vehicle
  running under controlled evaluation with shadow parity monitoring. Reserved
  for UNVALIDATED definitions by invariant; its only exit is RETIRED. This is
  not a precedent for enabling unvalidated strategies in general.
* `RETIRED`: terminal.

### Legal operational transitions

```text
DISABLED → ENABLED | BOOTSTRAP_CONTROLLED_RUN | RETIRED
ENABLED → DISABLED | RETIRED
BOOTSTRAP_CONTROLLED_RUN → RETIRED
RETIRED → (terminal)
```

Disabling a previously enabled strategy preserves its validation truth:
VALIDATED + DISABLED ("approved but intentionally inactive") is a first-class
state.

### Single source of truth

Live-evaluation eligibility is owned exclusively by the domain:

```java
definition.isEligibleForLiveEvaluation()
```

defined as: `(ENABLED ∧ VALIDATED ∧ evidence present) ∨
BOOTSTRAP_CONTROLLED_RUN`. The production pipeline consumes this predicate;
no other layer may duplicate governance logic.

### Pipeline gating order

```text
Governance eligibility  (domain predicate)
    ↓
StrategyApplicability   (market fit: timeframe / provider / asset class)
    ↓
context assembly → evaluator
```

An ineligible or non-applicable strategy is *not selected*: it never reaches
an evaluator and therefore never produces NO_MATCH or NOT_EVALUABLE. The
distinction between "not selected", "evaluated but conditions false" and
"evaluated without valid inputs" is preserved (ADR-035 I-7/I-8).

### Current builtin governance states

| Strategy | validationStatus | operationalStatus |
|---|---|---|
| LEGACY_OHLC_TREND | UNVALIDATED | BOOTSTRAP_CONTROLLED_RUN |
| OHLC_RANGE_EXPANSION_V1 | UNVALIDATED | DISABLED |

Both states are expressed purely as `StrategyDefinition` data. No
orchestration code branches on strategy identity.

## Relation to Prior ADRs

* Supersedes ADR-034 §"Strategy Lifecycle": the single chain
  DRAFT→CANDIDATE→VALIDATED→ENABLED→RETIRED is replaced by the two-dimension
  model above.
* Carries forward, explicitly, the ADR-034 temporary bootstrap exception
  (previously implicit; now visible as `BOOTSTRAP_CONTROLLED_RUN` data).
* Refines ADR-035 I-10: the bullet "lifecycle status
  (DRAFT/CANDIDATE/VALIDATED/ENABLED/RETIRED)" is superseded by
  `operationalStatus` + existing `validationStatus`.
* Preserves ADR-035 I-1/I-7/I-8 unchanged: evaluator remains sole authority;
  NO_MATCH/NOT_EVALUABLE semantics untouched; applicability stays separate
  from governance.
* No ranking, AI authority or risk boundary changes.

## Migration Required

YES (schema value domain only). Flyway `V7__strategy_operational_governance_split.sql`:

* renames `lifecycle_status` to `operational_status`;
* widens it to VARCHAR(30);
* maps legacy values: DRAFT/CANDIDATE/VALIDATED → DISABLED;
  ENABLED → ENABLED; RETIRED → RETIRED.

Existing rows remain truthful: anything that had not reached ENABLED was
never live-authorized under the enforced model.

## Consequences

Positive:

* An engineer reading `StrategyDefinition` immediately sees validation truth
  and live authorization as separate facts.
* Governance has one domain source of truth; the pipeline can no longer
  evaluate strategies whose declared governance forbids it.
* The bootstrap exception is explicit, queryable and terminal-bound instead
  of implicit.

Negative:

* One more enum on the aggregate; transition matrix must be maintained.
* Existing persisted lifecycle values require the V7 mapping migration.

## Testing Implications

1. Legitimate combinations: VALIDATED+ENABLED eligible; VALIDATED+DISABLED,
   UNVALIDATED+DISABLED, RETIRED not eligible.
2. Invalid combinations rejected: ENABLED without evidence;
   BOOTSTRAP_CONTROLLED_RUN while VALIDATED.
3. Illegal transitions rejected (terminal RETIRED; BOOTSTRAP → ENABLED).
4. Pipeline selection proves governance and applicability filter
   independently, before context assembly/evaluation.
5. Multi-strategy simultaneity from Story 0014 still passes.
