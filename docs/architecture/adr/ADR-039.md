# ADR-039: Self-Hosted SonarQube Quality Gate Integration

## Status

Accepted

## Context

Trading OS needs a blocking quality gate for code quality and coverage enforcement. GitHub-hosted runners cannot access the local SonarQube instance, so a self-hosted runner architecture is required.

## Decision

### Architecture

- **Shared SonarQube instance**: Standalone SonarQube Community Build at `http://localhost:9000`, shared with DevLog AI
- **Self-hosted runner**: `trading-os-sonarqube` registered with labels `[self-hosted, linux, x64, engineering, sonarqube, trading-os]`
- **Security boundary**: Self-hosted Sonar jobs ONLY on `push` to `main` or `workflow_dispatch` — NEVER on `pull_request`
- **Token model**: One project-analysis token per project (8 GitHub Secrets)

### Security Model

PRs run only on GitHub-hosted runners (deterministic quality checks). Self-hosted Sonar analysis only runs on push to main or manual dispatch, preventing untrusted code execution on the local machine.

### Failure Semantics

All failure modes are fail-closed:
- Quality Gate failure → CI FAIL
- Scanner failure → CI FAIL
- Auth failure → CI FAIL
- Sonar unavailable → CI FAIL
- Missing artifact → CI FAIL

No `continue-on-error` is used.

### Projects

8 Sonar projects scanned in parallel:
- `trading-os:risk-domain`
- `trading-os:gateway`
- `trading-os:eureka-server`
- `trading-os:trading-core`
- `trading-os:broker-service`
- `trading-os:market-data`
- `trading-os:market-intelligence`
- `trading-os:trading-os-web`

### Artifact Strategy

GitHub-hosted jobs upload:
- JaCoCo XML reports
- Compiled classes (`target/classes/`)
- LCOV coverage (frontend)

Self-hosted Sonar job downloads/restores them. No rebuild on self-hosted runner.

## Consequences

- PRs get deterministic quality checks (GitHub-hosted)
- Main branch gets Sonar analysis (self-hosted, blocks merge to protected branches)
- No secrets exposed to untrusted PR code
- Single shared SonarQube instance for both Trading OS and DevLog AI
