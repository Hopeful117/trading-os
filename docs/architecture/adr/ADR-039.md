# ADR-039 — Self-Hosted SonarQube Quality Gate Integration

## Status

Accepted

## Date

2026-08-24

## Context

Trading OS has completed its V1 quality-hardening phase:

- Backend business modules have blocking JaCoCo LINE >= 80% gates.
- Gateway has a blocking JaCoCo LINE >= 80% gate.
- Eureka Server is excluded from the business coverage gate (framework bootstrap).
- Angular has blocking LINE >= 80% coverage.
- Prettier is blocking and formatting baseline is clean.
- All tests and builds are green.

SonarQube remains the only major quality gate not yet integrated into CI.
A shared standalone SonarQube Community Build 26.7 instance already runs on the
engineering workstation at `http://localhost:9000` and is used by DevLog AI.

GitHub Actions currently uses GitHub-hosted `ubuntu-latest` runners, which
cannot reach `localhost:9000`. An isolated self-hosted GitHub Actions runner
(`trading-os-sonarqube`) has been installed and registered on the same machine
under a dedicated Linux identity (`gha-trading-os`).

## Decision

Trading OS quality analysis uses the shared standalone SonarQube engineering
instance, accessed by an isolated self-hosted GitHub Actions runner running
under a dedicated Linux identity, while tests and builds remain on
GitHub-hosted runners.

### Architecture

```
GitHub-hosted (ubuntu-latest):
    backend-quality (matrix: 7 modules)
    frontend-quality (tests, lint, build)
    coverage-summary
    quality-gate (aggregate)

Self-hosted (trading-os-sonarqube):
    sonar-quality (8 Sonar analyses + Quality Gate wait)
```

### Trigger Model

- **pull_request to main**: GitHub-hosted jobs only (deterministic quality).
  Sonar analysis is skipped. A PR cannot execute code on the self-hosted
  runner, even by modifying the workflow file.
- **push to main**: GitHub-hosted jobs + self-hosted Sonar analysis.
- **workflow_dispatch**: Full pipeline including Sonar.

### Security Boundary

- Self-hosted runner jobs execute ONLY on `push` to `main` or
  `workflow_dispatch`.
- Pull requests (including fork PRs) NEVER trigger self-hosted jobs.
- The runner uses a dedicated Linux user (`gha-trading-os`) with no access to
  personal files, `.env`, SSH keys, or Kraken credentials.
- Only GitHub Secrets (`SONAR_TOKEN_*`) and GitHub Variables
  (`SONAR_HOST_URL`) are available to the Sonar job.

### Eight-Project Topology

One Sonar project per backend module plus the frontend:

```
trading-os:risk-domain
trading-os:gateway
trading-os:eureka-server
trading-os:trading-core
trading-os:broker-service
trading-os:market-data
trading-os:market-intelligence
trading-os:trading-os-web
```

### Artifact Model

GitHub-hosted backend jobs upload:
- JaCoCo XML reports (`target/site/jacoco/jacoco.xml`)
- Compiled classes (`target/classes/`)

GitHub-hosted frontend job uploads:
- LCOV coverage (`coverage/trading-os-web/lcov.info`)

The self-hosted Sonar job downloads these artifacts, restores them into the
expected paths, and runs analysis. No rebuild or retest on the self-hosted
runner.

### Token Model

One project-analysis token per Sonar project (8 tokens total). Each token is
stored as a separate GitHub Secret (`SONAR_TOKEN_*`). Least privilege: each
token can only execute analysis for its specific project.

### Quality Gate Semantics

Each scanner waits for its Quality Gate (`-Dsonar.qualitygate.wait=true`).
Failure of any analysis or Quality Gate blocks the sonar-quality job, which
blocks the final quality-gate job.

Fail-closed behavior:
- Quality Gate failure → CI FAIL
- Scanner failure → CI FAIL
- Authentication failure → CI FAIL
- Sonar unavailable → CI FAIL
- Missing artifact → CI FAIL

No `continue-on-error`.

### Eureka Participation

Eureka participates in Sonar static analysis (bugs, vulnerabilities, code
smells). Its local JaCoCo >= 80% gate remains intentionally absent. If the
Sonar server's overall coverage condition makes Eureka fail solely due to its
low test coverage, the Quality Gate policy for Eureka will be adjusted
separately.

### Defense-in-Depth

Sonar is additional defense-in-depth, not a replacement for existing gates:
- Local JaCoCo/Vitest LINE >= 80% enforcement remains.
- Prettier blocking remains.
- Production build verification remains.
- Sonar adds: static analysis, technical debt, security findings, duplication,
  overall coverage import.

## Alternatives Rejected

1. **Public Sonar exposure via tunnel/reverse proxy**: Rejected for security
   reasons. Self-hosted runner on the same machine is simpler and more secure.

2. **GitHub-hosted direct access to localhost**: Impossible. GitHub-hosted
   runners cannot reach developer-machine localhost.

3. **Unrestricted shared self-hosted runner**: Rejected to minimize blast
   radius. Each project gets its own dedicated runner identity.

4. **Docker Sonar as primary infrastructure**: The standalone installation is
   already running and shared with DevLog. Docker Compose stack is fallback
   only.

5. **Single global analysis token**: Rejected in favor of per-project tokens
   for least privilege.

## Consequences

- The first push to `main` after merge will serve as the connectivity and
  Quality Gate proof.
- SonarQube must be running on the engineering workstation for CI to pass on
  push to `main`.
- The self-hosted runner must be online for push-to-main quality checks.
- Branch protection should require the `Trading OS Quality Gate` check.
- Future improvement: add systemd service for SonarQube startup reliability.
- Future improvement: consider migrating from H2 to PostgreSQL for reliability.

## Security Considerations

- Fork PR code NEVER executes on the self-hosted runner.
- Workflow modifications in PRs cannot target the self-hosted runner (trigger
  condition prevents it).
- No local developer secrets (`.env`, Kraken credentials) are available to CI.
- GitHub Secrets are masked in workflow logs.
- Dedicated runner user has minimal filesystem access.
