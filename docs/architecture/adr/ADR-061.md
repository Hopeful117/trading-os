# ADR-061 - Explicit Selection of Immutable Outcome Versions

## Status

Proposed for the research dataset prerequisite following Story 0108A.

## Context

Story 0107C stores corrected objective outcomes append-only. Each outcome has a
deterministic fingerprint, but multiple immutable facts may share the same
market, cutoff, and horizon. Database ordering and operational `computedAt`
cannot determine which correction a reproducible research dataset selected.

## Decision

Research consumers must select an outcome by its complete immutable identity:

```text
marketId + evaluationCutoff + horizon + outcomeDefinitionVersion + outcomeFingerprint
```

The repository exposes exact identity lookup and never chooses between outcome
versions implicitly. A correction remains a new immutable outcome fingerprint.
The selected fingerprint must be recorded by any future `DatasetManifest`.

There is no synthetic ordering based on database IDs, row order, or
`computedAt`. Automatic "latest correction" selection is intentionally deferred
until a separate accepted-versus-superseded policy is introduced.

## Consequences

- Dataset construction is deterministic and auditable.
- Corrected outcomes cannot silently replace an earlier selected outcome.
- Future dataset population policies must name the selected outcome version.
- A later policy may add supersession metadata without changing immutable facts.

This decision does not add datasets, labels, ML training, Python, public APIs,
or changes to Risk, Broker, Execution, or Frontend behavior.
