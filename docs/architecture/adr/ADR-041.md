## Executive Summary

This ADR formalizes the architectural decisions governing human-authorized trade execution and financial command safety in Trading OS. These decisions (D1–D10) have been human-designed and approved conceptually during prior architectural work. They are now documented as a single authoritative ADR for governance traceability.

The repository already implements D1, D2 (partially), D4–D10 through Story 0030, Story 0033, and the Execution Domain (ADR-029). **D3 (Execution-Time Risk Revalidation) is the critical gap** — T1 revalidation does not yet exist.

---

## Context

Trading OS has completed:

- **Story 0030** — Connect Risk Decision to Human-Controlled Execution (merged, PR #26)
- **Story 0033** — Full Exposure Close (implemented, human-accepted, PR #29)
- **ADR-029** — Execution Domain Architecture (Accepted)
- **ADR-030** — Broker Service Architecture (Accepted)
- **ADR-040** — Position Management Command Architecture (Accepted)

Current execution flow:

```
TradePlan accepted
    ↓
T0 Risk Evaluation (APPROVED)
    ↓
Human clicks Execute
    ↓
ValidateAndCreateService → ExecutionIntent (VALIDATED)
    ↓
ExecuteTradeService pipeline
    ↓
BrokerSubmissionStep → Broker Service → Kraken
    ↓
Execution result (ACKNOWLEDGED / REJECTED / UNKNOWN)
```

**Problem:** The broker submission relies on the earlier T0 risk evaluation. Between T0 and actual execution, equity, exposure, margin, market price, and other risk-relevant facts may change. No fresh T1 safety decision occurs before financial commitment.

---

## Decisions

### D1 — Human Authority

**Decision:** Live financial execution requires explicit human authorization. Risk approval, AI recommendation, opportunity detection, or technical readiness MUST NOT independently authorize live execution. The human remains the authority that crosses the boundary from analysis/preparation into a financial command.

**Repository Evidence:** Story 0030 implementation — Angular `PlanPage` only shows "Execute Trade" button after `RiskDecisionResponse.approved === true` (`plan-page.ts:133-136`). The `execute$` observable only emits on explicit button click (`plan-page.ts:223-225`). No automatic subscription or effect submits an order after risk approval.

**Implementation Status:** **IMPLEMENTED**

---

### D2 — Financial Side-Effect Boundary

**Decision:** Financial execution must follow a safe side-effect lifecycle:

```
validate / prepare
    ↓
persist durable command state
    ↓
COMMIT
    ↓
broker call OUTSIDE long DB transaction
    ↓
record broker outcome
```

Never hold a database transaction open around remote broker execution. The system must preserve enough durable state to recover/reconcile after failures.

**Repository Evidence:**
- **Standard Execution (`ExecuteTradeService`):** NO `@Transactional` on service or pipeline steps. `BrokerSubmissionStep` saves attempt/intent, calls broker, then `ResponseProcessingStep`/`FinalizationStep` update state. **COMPLIANT.**
- **Position Close (`PositionCloseService.close()`):** HAS `@Transactional` on the method (line 26). The entire flow including `brokerPort.executeClose()` runs inside a Spring transaction. **NON_COMPLIANT.**
- **Position Close Reconciliation (`PositionCloseService.reconcile()`):** HAS `@Transactional` on the method (line 61). **NON_COMPLIANT.**
- **Execution Reconciliation (`RecoverExecutionService`):** NO `@Transactional`. **COMPLIANT.**

**Technical Debt:** Story 0033 accepted single-transaction orchestration for position close to avoid orphaned CREATED states, acknowledging: "A database rollback does NOT imply the broker command was not executed. If the broker call started before the crash, the financial mutation may have occurred." (Engineering Report §Transaction Semantics).

**Implementation Status:** **PARTIALLY_IMPLEMENTED** (Standard execution compliant; Position close non-compliant)

---

### D3 — Execution-Time Risk Revalidation (T1)

**Decision:** A previous risk decision at preparation time (T0) is not sufficient to guarantee execution later. Risk must be revalidated at execution time (T1) using the relevant current state.

```
T0
Opportunity / requested trade
    ↓
Risk evaluation (StoredEvaluation persisted)
├── authoritative policy at T0
├── facts at T0
└── immutable provenance

... time passes, market/account state may change ...

Human clicks Execute
    ↓
ValidateAndCreateService → ExecutionIntent (VALIDATED)

T1
Server-side risk revalidation
(
  authoritative current account policy snapshot (D12)
  +
  fresh authoritative execution-time facts
)
    ↓
if T1 APPROVED → broker execution may proceed
if T1 REJECTED → no financial command, terminal intent state
```

T0 and T1 are separate temporal safety decisions. T1 independently resolves the authoritative current account risk profile assignment server-side (D12). Policy drift between T0 and T1 is auditable information, not an error.

T1 is a mandatory server-side invariant. `ExecutionIntent` may precede T1. Broker submission before T1 APPROVED is forbidden. Frontend does not own or enforce the T1 gate (D11).

T0 and T1 decisions must remain distinguishable for auditability, including their respective policy identities.

**Repository Evidence:** 
- `TradePlanRiskEvaluationService` persists `StoredEvaluation` with `evaluationId`, `decision`, `evaluatedAt`, full provenance.
- `ValidateAndCreateService` loads this T0 evaluation and verifies `COMPLETED` + `APPROVED` (steps 2-3).
- `RiskPersistence.assignedProfile()` resolves the authoritative current account risk profile.
- **NO T1 revalidation exists.** Story 0030 Engineering Report §Remaining Risks explicitly documents: "Story 0030 DOES NOT re-evaluate risk immediately before broker submission... This is accepted for the current controlled V1 proof."

**Implementation Status:** **NOT_IMPLEMENTED** (Critical gap — Story 0034 target)

### D4 — Human Authorization and Idempotency

**Decision:** One human authorization corresponds to one logical execution authorization. Retries, duplicate HTTP requests, duplicate callbacks, technical retries, or provider uncertainty MUST NOT silently create additional financial commands. Idempotency is a safety property, not a mechanism for bypassing human authorization.

**Repository Evidence:**
- Angular generates `crypto.randomUUID()` per execution attempt (`plan-page.ts:145`).
- `Idempotency-Key` HTTP header transported through Gateway → Trading Core → Broker Service.
- `IdempotencyService.ensureUnique()` + DB unique constraint on `ExecutionIntent.idempotency_key`.
- `uk_execution_intent_trade_plan` prevents duplicate intents per TradePlan/version.
- `ExecutionIntent.activateAttempt()` enforces single active attempt.
- `@Version` optimistic locking on `ExecutionIntent`.
- Kraken `cl_ord_id` derived deterministically from idempotency key (`UUID.nameUUIDFromBytes`).
- Position close uses same pattern with `Idempotency-Key` header + DB constraint.

**Implementation Status:** **IMPLEMENTED**

---

### D5 — Broker Acknowledgement is Not Execution/Fill

**Decision:** A provider/broker acknowledgement MUST NOT automatically be interpreted as a filled trade. Keep concepts semantically distinct:

```
command submitted
broker acknowledged
order accepted
partially filled
filled
rejected
cancelled
unknown
```

**Repository Evidence:**
- `ExecutionStatus` enum: `CREATED`, `VALIDATED`, `SUBMISSION_IN_PROGRESS`, `SUBMISSION_OUTCOME_UNKNOWN`, `RECONCILIATION_IN_PROGRESS`, `COMPLETED`, `FAILED`, `RECOVERY_BLOCKED`, `CANCELLED`, `EXPIRED`.
- `ExecutionResult` sealed interface: `Acknowledged(externalOrderId, correlationId)`, `Rejected(reasonCode)`, `Unknown(reasonCode)`.
- Kraken adapter returns `Acknowledged` on order acceptance (returns `txid`), NOT on fill.
- Broker order status tracked separately via `BrokerOrder` aggregate with `OrderStatus`: `OPEN`, `ACKNOWLEDGED`, `PARTIALLY_FILLED`, `FILLED`, `REJECTED`, `CANCELLED`, `EXPIRED`, `UNKNOWN`.
- Reconciliation queries broker for actual fill state.

**Implementation Status:** **IMPLEMENTED**

---

### D6 — Unknown Outcome and Reconciliation

**Decision:** If the system cannot determine whether a financial command was accepted/executed by the broker, it must NOT blindly retry. The safe state is:

```
UNKNOWN
    ↓
RECONCILIATION REQUIRED
```

**Important:** This UNKNOWN semantic applies to uncertainty about a **financial side effect**. Do NOT automatically apply broker-command reconciliation semantics to failures occurring before any financial command could have been submitted.

**Repository Evidence:**
- `ExecutionStatus.SUBMISSION_OUTCOME_UNKNOWN` set when broker response is ambiguous (timeout, `RetryableException`).
- `BrokerSubmissionStep` catches `RetryableException` → `Unknown("BROKER_OUTCOME_UNKNOWN")`.
- `ReconcileExecutionService` queries broker via `ReconciliationCapability`.
- `RecoveryPipeline` only acts on `SUBMISSION_OUTCOME_UNKNOWN`, `RECONCILIATION_IN_PROGRESS`, `RECOVERY_BLOCKED`.
- Angular shows UNKNOWN as "Submission outcome uncertain" with Reconcile action, NOT blind retry.

**Implementation Status:** **IMPLEMENTED**

---

### D7 — Identity Separation

**Decision:** Keep distinct identities for:
- logical execution intent (`ExecutionIntentId`);
- execution attempt (`ExecutionAttemptId`);
- idempotency identity (`IdempotencyKey`);
- provider/broker correlation identity (`cl_ord_id` / `txid` / `externalOrderId`).

**Repository Evidence:**
- `ExecutionIntent` aggregate owns `idempotencyKey` (immutable).
- `ExecutionAttempt` created per submission with own `ExecutionAttemptId`, `attemptNumber`, `brokerCorrelationId`.
- `BrokerOrder` tracks provider `txid` and `cl_ord_id` separately.
- `BrokerExecutionPort.ExecutionRequest` carries all four: `executionIntentId`, `executionAttemptId`, `idempotencyKey`, `brokerAccountId`.
- Position close uses `PositionCloseCommand.id`, `resolvedMutationScope`, `idempotencyKey`, and broker `cl_ord_id`/`orderId`.

**Implementation Status:** **IMPLEMENTED**

---

### D8 — No Automated Live Financial Tests

**Decision:** Automated tests must never depend on executing live financial mutations. Use deterministic fakes, mocks, test adapters, and safe environments.

**Repository Evidence:**
- `ExecutionPipelineTest` uses `ExecutionTestSupport.Broker` (fake `BrokerExecutionPort`).
- `ValidateAndCreateServiceTest` mocks `RequiredMarginPort`; risk engine runs real deterministic logic.
- `BrokerService` tests use `KrakenCapabilities` with mocked `KrakenProviderClient`.
- No Kraken contact in CI; no write-capable credentials required.
- Story 0030/0033 engineering reports explicitly: "No Kraken order is submitted."

**Implementation Status:** **IMPLEMENTED**

---

### D9 — Provider-Neutral Trading Core

**Decision:** Trading Core must remain broker/provider neutral. Provider-specific behavior belongs behind Broker Service capabilities/adapters. Do NOT couple Trading Core directly to Kraken, FTMO, cTrader, or any specific provider.

**Repository Evidence:**
- `BrokerExecutionPort` / `BrokerExecutionAdapter` / `BrokerExecutionClient` boundary.
- `ExecutionParameters` broker-neutral (instrument, side, orderType, quantity, limitPrice).
- `KrakenCapabilities` implements `ExecutionCapability`, `ReconciliationCapability`, `PositionManagementCapability` behind interfaces.
- Trading Core never sees `reduce_only`, `cl_ord_id` logic, Kraken payloads.
- `PositionManagementCapability` introduced in ADR-040 for position close — separate from `ExecutionCapability`.

**Implementation Status:** **IMPLEMENTED**

---

### D10 — Audit Provenance

**Decision:** The execution lifecycle must preserve enough provenance to reconstruct:

```
execution intent
human authorization
T0 risk evaluation
T1 risk evaluation
execution attempt
idempotency identity
provider correlation
broker acknowledgement
fill/outcome information
failure
unknown outcome
reconciliation
```

The system must support answering: *Why was this financial command allowed, who authorized it, what risk information was used, what was submitted, and what did the broker actually report?*

**Repository Evidence:**
- `ExecutionIntent`: `tradePlanRef`, `riskApprovalRef`, `idempotencyKey`, `initiatorId`, `brokerAccountId`, `parameters`, `expiresAt`, `version`, `status`, timestamps.
- `ExecutionAttempt`: `intentId`, `attemptId`, `attemptNumber`, `status`, `brokerResponse`, `brokerCorrelationId`, `externalOrderId`, timestamps.
- `ExecutionEvent` (immutable): `ExecutionIntentCreated`, `ExecutionIntentValidated`, `ExecutionAttemptCreated`, `ExecutionAttemptStarted`, `BrokerSubmissionStarted`, `BrokerSubmissionAcknowledged`, `BrokerOrderLinked`, `BrokerOrderRejected`, `BrokerOrderFilled`, `BrokerOrderPartiallyFilled`, `ExecutionAttemptUnknown`, `ExecutionRetryScheduled`, `ExecutionRecoveryStarted`, etc.
- `StoredEvaluation` (T0): full provenance including `tradePlan`, `broker`, `market`, `ruleSet`, `context` payloads.
- **Gap:** T1 evaluation persistence not yet designed (see D3, D15).

**Implementation Status:** **PARTIALLY_IMPLEMENTED** (T0 complete; T1 pending)

## Technical Debt Identified

1. **Position Close Transaction Boundary** — `@Transactional` on `PositionCloseService.close()` and `reconcile()` spans broker calls. Accepted in Story 0033 for CREATED-state simplicity; requires separate remediation.

2. **PostgreSQL Partial Unique Index** — Story 0033 uses `WHERE status IN (...)` partial unique index for concurrency guard. Only tested on H2 (full unique index). Production PostgreSQL semantics unverified.
