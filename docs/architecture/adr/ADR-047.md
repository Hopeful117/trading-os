# ADR-047 - Manual Trade Plans as a First-Class Trade Plan Origin

## Status

Accepted

## Date

2026-09-20

## Context

Trading OS currently follows this decision pipeline:

```text
Trading Opportunity
    -> TradePlan
    -> deterministic RiskEvaluation
    -> human validation
    -> ExecutionIntent
    -> Execution
```

The current Trade Plan creation contract requires at least one
`TradingOpportunity`. This is correct for an opportunity-driven workflow, but it
prevents the platform from supporting a legitimate discretionary workflow in
which the human trader identifies and enters a trade without a prior generated
Opportunity.

Creating a second execution pipeline for discretionary trades would duplicate
risk evaluation, human authorization, idempotency, audit, execution and
reconciliation behavior. It would also make it possible for a manual trade to
bypass the invariants already established by ADR-028, ADR-029 and the
Execution Intent concept.

The platform is discretionary and human-controlled. A manual trade is therefore
a valid trading proposal, but it is not an authorization to execute and it is
not a direct broker command.

## Decision Question

How should Trading OS represent a trade entered directly by the human trader
without a generated Trading Opportunity while preserving the existing risk and
execution architecture?

## Decision

`TradePlan` remains the single normalized proposal model for all entry trades.

Every Trade Plan SHALL have an explicit origin:

```text
OPPORTUNITY
MANUAL
```

### Opportunity-Origin Trade Plans

An `OPPORTUNITY` Trade Plan is derived from one or more immutable
`TradingOpportunity` references, as defined by the existing Market Intelligence
architecture.

### Manual-Origin Trade Plans

A `MANUAL` Trade Plan is authored from an explicit human trading proposal. It
does not require a `TradingOpportunity` reference and MUST NOT create a fake
Opportunity merely to satisfy persistence or API constraints.

A manual Trade Plan MUST still contain:

- an immutable identity and version;
- its authenticated author;
- the account and planning context for which it was created;
- explicit instrument, direction, entry and execution parameters;
- the applicable planning and validity information;
- a traceable creation timestamp;
- an optional human rationale without treating that rationale as a risk decision.

The exact transport representation may evolve, but the persisted domain meaning
must distinguish `MANUAL` from `OPPORTUNITY` without relying on an empty or
synthetic Opportunity collection.

## Domain Ownership

Market Intelligence remains the owner of the Trade Plan domain concept,
including its immutable identity, origin, version and lifecycle.

Trading Core remains responsible for:

- account ownership and authorization;
- obtaining the account-specific planning and financial context;
- deterministic risk evaluation;
- human validation;
- Execution Intent creation;
- execution orchestration and reconciliation.

Trading OS Web expresses the user's proposal and approval intent. It does not
create an Execution Intent and does not become authoritative for risk, account
state or broker state.

## Mandatory Invariants

The following invariants apply equally to both Trade Plan origins:

1. A Trade Plan is a proposal, not an execution command.
2. Every Trade Plan must pass deterministic Risk Evaluation before execution.
3. No Execution Intent may be created without an approved Risk Evaluation.
4. Every Execution Intent references exactly one Trade Plan and its approved
   version.
5. Human approval is required before an Execution Intent is created.
6. The Execution Domain remains independent of whether the origin is manual or
   opportunity-driven.
7. Broker-specific concepts must not be introduced into the Trade Plan model.
8. A manual rationale, when provided, never overrides deterministic risk rules.
9. A Trade Plan remains immutable; a changed proposal creates a new version or
   a new plan according to the existing lifecycle rules.

## Manual Trade Lifecycle

The manual workflow SHALL be:

```text
Human trade input
    -> manual TradePlan
    -> RiskEvaluation
    -> human review of risk result
    -> ExecutionIntent
    -> Execution Domain
```

The manual workflow MUST NOT be:

```text
Human trade input
    -> Broker API
```

The same execution order types supported by the existing execution contract
remain the initial scope. Adding manual origin does not implicitly add MARKET,
LIMIT, stop-order, partial-fill or provider capabilities that are not already
supported.

## Context and Provenance

Manual origin removes the requirement for an Opportunity; it does not remove
the requirement for context.

The Trade Plan must retain the planning context needed to explain what account
and market decision context existed when the proposal was authored. The context
is evidence for planning and audit. It is not a replacement for the current
broker snapshot or deterministic risk facts used during authorization.

The authenticated actor is the authoritative author identity. A client-provided
actor identifier must not be used as an authorization authority, consistent with
ADR-044.

## Rejected Alternatives

### Separate Manual Execution Pipeline

Rejected.

It would duplicate risk, approval, idempotency, audit, execution and
reconciliation logic, and would create a bypass risk.

### Synthetic Opportunity for Every Manual Trade

Rejected.

It would misrepresent provenance and claim that Market Intelligence identified an
opportunity when the proposal was authored by the human trader.

### Direct Broker Command from the Frontend

Rejected.

It violates the human-controlled decision pipeline, bypasses deterministic risk
and exposes the frontend as an unsafe execution authority.

### Make Opportunity Mandatory for All Future Trade Plans

Rejected as the target model.

It prevents the product from supporting discretionary manual trading, which is a
core product use case.

## Consequences

### Positive

- Manual and opportunity-driven trades share one risk and execution path.
- Execution audit remains uniform across both origins.
- The provenance of a manual decision is explicit and truthful.
- Broker integrations do not need to know how a Trade Plan was created.
- The frontend can add a direct-trade workflow without creating a second
  execution architecture.

### Negative

- Trade Plan creation contracts must support an origin and optional Opportunity
  references.
- Persistence and transport schemas require migration.
- Manual plan validation must define which fields are required before risk
  evaluation.
- Market Intelligence and Trading Core need a clear boundary for creating a
  manual plan from authenticated user input.

## Scope Boundaries

This ADR does not decide:

- partial close;
- stop-loss or take-profit modification;
- pending-order modification or cancellation;
- automatic trading;
- a new position aggregate or internal Position UUID;
- new broker order types;
- a new risk policy or sizing algorithm;
- whether a manual rationale is mandatory for every account or product mode.

Those capabilities require separate decisions or Stories when they become
necessary.

## Implementation Constraints

The implementation must:

- preserve existing opportunity-origin behavior;
- avoid making existing persisted Trade Plans invalid;
- preserve Trade Plan version lineage;
- preserve Risk Evaluation and Execution Intent invariants;
- enforce account ownership server-side;
- keep the frontend non-authoritative;
- add tests for both origins and their invalid combinations;
- avoid introducing provider-specific fields into Market Intelligence models.
