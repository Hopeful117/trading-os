## 1. Context

The project requires one concrete prop-challenge target for the next readiness
track. The selected business provider is FTMO, the selected challenge is FTMO
Challenge 2-Step, and the selected execution platform is cTrader through cTrader
Open API.

The target selection is supported by two different evidence classes:

- FTMO support replied directly on 2026-10-23 that cTrader Open API and automated
  strategies are allowed.
- Official cTrader Open API documentation describes account access, real-time
  market data, trading operations, historical/current/pending operations, and
  demo/live account support.

Neither source proves that the exact FTMO Challenge account will expose every
required Open API operation, event, account fact, instrument, fee, swap, or
Challenge lifecycle fact. Those remain controlled validation requirements.

Kraken Prop cannot be the first target because support evidence states that
programmatic API access is not available for Kraken Prop accounts.

The current repository is still physically Kraken-only in selected provider
registration and Trading Core account-routing assumptions. That is a readiness
gap, not permission to couple Trading Core to FTMO or cTrader.

## 2. Decision

Trading OS adopts the following first prop-challenge target:

```text
BUSINESS_PROVIDER = FTMO
CHALLENGE = FTMO_CHALLENGE_2_STEP
EXECUTION_PLATFORM = CTRADER
INTEGRATION_BOUNDARY = CTRADER_OPEN_API
TARGET_SELECTION = ACCEPTED
EXECUTION_READINESS = NOT_READY
```

FTMO and cTrader remain separate concepts:

```text
FTMO
    -> Challenge/business provider

cTrader
    -> Broker/execution platform
    -> Broker Service adapter and technical authority
```

Trading Core SHALL remain provider-neutral. It SHALL NOT contain FTMO rules,
cTrader DTOs, cTrader SDK types, OAuth details, provider event payloads, or
provider-specific execution branches.

Broker Service SHALL own cTrader authentication, transport, mapping, provider
errors, connection lifecycle, account synchronization, and provider capability
composition. Trading Core SHALL own execution authorization, deterministic Risk,
execution state, reconciliation decisions, and Challenge business state.

Challenge definitions SHALL remain business-provider concepts in Trading Core.
Broker account identities SHALL remain execution-routing concepts. The selected
FTMO Challenge account may be associated with a cTrader BrokerAccount, but the
association must not collapse those identities.

## 3. Required Safety Invariants

The following invariants apply before any real Challenge execution:

```text
read-only synchronization precedes execution
no authoritative facts -> no Risk authorization
stale or incomplete facts -> no new execution
unknown provider outcome -> no blind retry
manual provider divergence -> stop local mutation and reconcile
human authorization -> required before every financial command
```

The minimum authoritative facts required for execution admission are account
identity, balance, equity, margin, open positions, pending orders, orders,
deals/fills, realized and unrealized P&L, commissions, swaps/carrying costs,
instrument constraints, observation time, freshness, and completeness.

Events may accelerate synchronization, but events alone SHALL NOT be the only
authority. Restart, reconnect, event loss, and uncertain operations require a
complete authoritative snapshot and reconciliation.

### 3.1 Provider Environment Semantic Exception

The cTrader `isLive` field is a provider transport fact, not a universal
business classification of financial exposure. FTMO FREE accounts may be
simulated/demo trading accounts while cTrader reports them with `isLive=true`.
This is a known provider semantic mismatch and must not require re-explaining
the same fact during every runtime validation.

Trading OS SHALL therefore distinguish at least:

```text
PROVIDER_REPORTED_ENVIRONMENT = cTrader account flag (`isLive`)
EFFECTIVE_EXECUTION_ENVIRONMENT = validated economic/execution classification
BUSINESS_PROVIDER = FTMO
ACCOUNT_PROGRAM = FTMO_FREE (when verified)
```

For an FTMO FREE account, `isLive=true` SHALL NOT alone prove that the account
is a real-money account. Conversely, an FTMO FREE label SHALL NOT alone prove
demo safety. Execution admission requires an explicit, provider-verified
classification of the effective execution environment and the applicable
account program. Unknown, contradictory, or unverified classifications remain
fail-closed.

The configured cTrader transport endpoint may still be the `live` endpoint for
this account. Transport environment and economic execution environment are
separate facts and must not be conflated.

The cTrader adapter owns provider facts and their translation. Trading Core
must receive only the resulting broker-neutral environment classification; it
must not contain a cTrader-specific `isLive` exception.

## 4. Scope Boundary

This ADR authorizes target selection and architectural direction only. It does
not authorize:

- production cTrader or FTMO implementation;
- OAuth, token, or secret creation;
- FTMO Challenge rule persistence;
- multi-phase Challenge domain implementation;
- cTrader order placement, modification, close, or reconciliation;
- Market Data cTrader instrument ingestion;
- a cTrader SDK or dependency decision;
- purchase of an FTMO Challenge;
- changes to the closed V1 milestone;
- removal of human authorization or fail-closed behavior.

## 5. Validation Boundary

Before implementation is considered execution-ready, controlled evidence must
prove, for the exact FTMO account:

1. authorization and selected-account binding;
2. complete read-only account, order, deal, position, and ledger facts;
3. freshness, completeness, reconnect, restart, and event-loss recovery;
4. instrument identity, constraints, volume, precision, margin, fees, and swaps;
5. required read/write operation coverage;
6. unknown-result and reconciliation behavior;
7. FTMO Challenge phase, loss, reset, minimum-day, fee, and terminal-state
   semantics.

Until those validations pass:

```text
FTMO_CTRADER_ACCOUNT_ACCESS = UNVERIFIED
FTMO_CHALLENGE_RULES = UNVERIFIED
EXECUTION_READINESS = NOT_READY
```

## 6. Consequences

Positive:

- The first prop target is explicit and traceable.
- FTMO business semantics remain separate from cTrader execution mechanics.
- Existing Broker, Risk, Challenge, execution, reconciliation, and human-control
  boundaries can be reused without provider leakage.
- cTrader becomes a meaningful second-provider architecture test rather than a
  Kraken-specific extension.
- Kraken Prop remains accurately classified without blocking the product.

Trade-offs:

- The target is selected before account-specific API access is proven.
- Multi-phase Challenge, account identity, synchronization, and instrument gaps
  remain implementation dependencies.
- Read-only validation and controlled dry-run evidence are required before any
  financial exposure.

## 7. First Implementation Story

The next implementation Story is Story 0145, focused only on the provider-neutral
prerequisite:

```text
generalize physical provider registration and account routing
without introducing FTMO- or cTrader-specific business code
```

This Story must not implement cTrader, FTMO rules, OAuth, or execution.
