# ADR-040 — Position Management Command Architecture

## Status

Accepted

## Date

2026-09-03

## Context

Trading OS has completed the following vertical lifecycle stories:

```text
Story 0030 — Connect Risk Decision to Human-Controlled Execution
Story 0031 — Close the Execution Feedback Loop
Story 0032 — Dedicated Open Positions Monitoring
```

Story 0032 established read-only observation of broker-authoritative open positions through a dedicated `/positions` page and `GET /api/v1/accounts/{accountId}/positions` endpoint. The current architecture is:

```text
Angular
    ↓
Trading Core
    ↓
Broker Service
    ↓
Provider capability
    ↓
Kraken (current)
```

Existing broker capabilities include:

```text
PositionCapability
ExecutionCapability
OrderCapability
ReconciliationCapability
```

Positions remain broker-authoritative external trading state. They are not persisted as a local Position aggregate in Trading Core. The read path projects broker positions through `PositionSnapshot → BrokerPositionFact → OpenPositionDashboardView`.

The next product capability is expected to be:

```text
Full Position Close
```

Before allowing mutation of an existing position, Trading OS must decide:

- how positions are identified for commands;
- which architectural capability owns position-management commands;
- how stale frontend state is handled;
- how provider-specific close semantics are isolated behind the broker abstraction;
- how uncertain outcomes are handled;
- how the architecture remains compatible with Kraken and future cTrader.

---

## Provider Evidence Summary

### Kraken Spot Margin

- Open positions have provider-generated `txid` references (string).
- Multiple positions for the same pair may exist (FIFO settlement order).
- **Closing is implemented through trading semantics rather than a position-targeted close endpoint.**
- **No officially documented API parameter accepts an OpenPositions txid to target a specific position for mutation.**
- `reduce_only=true` guarantees that an order can reduce exposure but cannot increase or reverse it.
- Without `reduce_only`, excess opposite-side quantity may flip exposure.
- Provider client IDs (`cl_ord_id`) do not provide a documented uniqueness/idempotency guarantee ("we don't enforce uniqueness on our side").
- An uncertain result therefore must not be blindly retried.
- **When multiple same-side positions exist for a pair, Kraken applies mandatory FIFO settlement: the oldest position is reduced/closed first.**
- **Neither `reduce_only` nor `settle-position` can target an arbitrary individual OpenPositions txid.**
- **A command intending to close one specific position may affect older positions first due to FIFO.**

### cTrader Open API

- Positions are explicit entities with `int64 positionId`.
- Both hedged (`ProtoOAAccountType.HEDGED`) and netted (`ProtoOAAccountType.NETTED`) account models exist.
- Hedged accounts can contain multiple positions for the same symbol.
- `ProtoOAClosePositionReq` explicitly targets an existing position by `positionId` + `volume`.
- Full or partial close uses `positionId` + `volume`.
- Oversized close volume is rejected (`TRADING_BAD_VOLUME`) rather than opening reverse exposure.
- `clientMsgId` is documented as correlation, not a documented idempotency guarantee.

---

## Decision Question

Should commands against existing broker positions:

**Option A** — extend the existing `ExecutionCapability` with fields such as `reduceOnly` and `positionReference`?

**Option B** — introduce a distinct broker capability dedicated to commands against existing positions?

---

## Decision

### Primary Decision: Distinct Position-Management Capability

Trading OS SHALL introduce a new broker capability dedicated to commands against existing positions. The existing `ExecutionCapability` remains responsible for opening/increasing exposure. A separate capability owns reducing/terminating existing exposure.

The capability name SHOULD follow existing repository conventions. Conceptually:

```text
PositionManagementCapability
```

or a name that fits the existing capability architecture (e.g., `PositionCommandCapability`).

### Capability Boundary

The initial capability supports only the operation required by Story 0033:

```text
FULL EXPOSURE CLOSE
```

It does NOT include:

```text
partial close
SL modification
TP modification
order modification
risk calculation
position monitoring
```

Future operations may extend this capability incrementally, but each operation must be justified by user value and provider semantics.

### Position Identity: Opaque Broker Position Reference (Read Identity / Resolution Handle)

The `brokerPositionReference` is an **opaque read identity and resolution handle**. It identifies what the user was observing; it does NOT specify what the provider will mutate.

Commands and queries use this opaque broker/provider position reference. The reference is forwarded opaquely through the architecture:

```text
Angular → Trading Core → Broker Service → provider adapter
```

Provider values differ and must not leak into Trading Core:

```text
Kraken → String txid (OpenPositions map key)
cTrader → int64 positionId
```

Trading Core treats the value as opaque. `account + instrument` is REJECTED as universal position identity because both providers may expose multiple positions for the same instrument.

**Critical semantic distinction:**

```text
brokerPositionReference identifies what the user was observing.
Broker Service determines what the provider can actually mutate.
```

The selected read identity is resolved server-side into the provider-authoritative mutation scope. Trading OS must never infer a finer mutation granularity than the provider supports. For Kraken, the selected txid resolves to pair/exposure scope. For future cTrader, read identity and mutation target may coincide.

### Position Command Addressability: Provider-Divergent

**Critical architectural distinction:** A provider object may have a stable identity for observation without that identity being independently actionable by mutation commands.

```text
Identity answers: "What broker state object am I observing?"
Addressability answers: "What exact thing can the provider safely mutate?"
```

These concepts may coincide or diverge by provider:

| Provider | Position Identity (Read) | Command Addressability (Write) |
|----------|--------------------------|--------------------------------|
| **Kraken Spot Margin** | OpenPositions txid (individual entry) | **Pair/exposure scope with mandatory FIFO settlement** — cannot target arbitrary individual txid |
| **cTrader (Hedged)** | `positionId` (individual entry) | **Individual `positionId`** — explicitly command-addressable |

**Architectural consequence:** Trading OS must never present or execute a position-level mutation unless the resolved provider can authoritatively address that position at that command granularity.

For Kraken, this means the mutation target is the **current aggregate exposure for the pair** (resolved via authoritative reload), not an individual OpenPositions txid.

### Internal Trading OS Position UUID: Not Introduced

Trading OS does NOT introduce a persistent internal Position UUID at this stage.

Rationale:

- Positions remain broker-authoritative.
- Trading OS currently has no persisted Position aggregate.
- Provider references are sufficient for observation, correlation, and server-side mutation-scope resolution where supported.
- Introducing local identity would require persistence and synchronization without demonstrated business value.

This decision may be revisited if future requirements require:
- cross-provider correlation;
- long-lived local position identity;
- historical position aggregates;
- provider-reference replacement;
- other demonstrated domain requirements.

### PositionSnapshot Contract Extension

The broker-neutral `PositionSnapshot` (and downstream projections) MUST expose an opaque broker position reference when they represent individually observable broker positions.

Likely future flow:

```text
provider
    ↓
PositionSnapshot.brokerPositionReference
    ↓
Broker Service
    ↓
Trading Core projection
    ↓
Angular
```

### Command Authority: Frontend Sends Intent, Not Authoritative State

The frontend expresses **intent**, not authoritative trading state.

For a full-exposure-close command, Angular may supply:
- account identifier
- broker position reference (opaque read identity / resolution handle — NOT the mutation target)
- idempotency key

Angular MUST NOT be authoritative for:
- current quantity
- side
- entry price
- provider-specific flags (e.g., `reduce_only`)
- provider command structure

Those values MUST be derived or validated server-side from current broker-authoritative state.

### Mandatory Authoritative Reload

Before mutating an existing position, Trading OS MUST reload the current broker-authoritative position state.

Conceptual safe flow:

```text
human command
    ↓
authentication
    ↓
ownership validation
    ↓
broker account/provider resolution
    ↓
reload open broker positions
    ↓
resolve current side + current aggregate reducible quantity for target scope
    ↓
validate command
    ↓
submit provider-specific close
```

If the target exposure no longer exists, the command MUST be rejected without submitting a broker mutation.

### Exposure-Reversal Invariant

This is an explicit architectural invariant:

```text
A command whose semantic intent is:
    CLOSE/REDUCE THIS EXPOSURE
must never silently become:
    OPEN OR INCREASE AN OPPOSITE POSITION.
```

Provider implementations are responsible for satisfying this invariant below the broker abstraction:

```text
Kraken → use reduce_only=true on opposite-side market order (pair-level, FIFO)
cTrader → use position-targeted ProtoOAClosePositionReq semantics
```

### Full-Exposure-Close Semantic Model

At the Trading Core / Broker Service boundary, the intent SHALL be expressed as:

```text
close the complete current broker-authoritative exposure for the target scope
```

rather than:

```text
sell quantity X
buy quantity X
reduceOnly=true
```

Those are provider-specific execution mechanics. The application intent remains `FULL EXPOSURE CLOSE`; the provider adapter determines how to achieve it safely for the resolved provider.

### Full Close vs Partial Close

The architecture deliberately preserves a distinction between:

```text
FULL EXPOSURE CLOSE
```

and:

```text
PARTIAL REDUCE
```

Story 0033 SHOULD NOT be forced to support partial close. The architecture may allow future partial reduction, but full close is expressible explicitly. Avoid defining `full close = partial close(currentQuantity)` as the only semantic model.

### SL/TP Boundary

Position protection modification is OUTSIDE the current decision. It may receive its own capability/architecture later. Provider research indicates materially different primitives (Kraken conditional close orders vs cTrader `ProtoOAAmendPositionSLTPReq`).

### Reuse from Execution Architecture

The following concepts SHALL be reused conceptually:

- human authorization boundary (explicit user action required)
- ownership checks (defense in depth: Trading Core + Broker Service)
- application-level idempotency (idempotency key)
- `ACKNOWLEDGED / REJECTED / UNKNOWN` semantics
- reconciliation after uncertain submission
- no blind retry
- frontend feedback patterns (polling, UNKNOWN state handling)

### What Must NOT Be Reused Blindly

Position-management commands MUST NOT couple to prerequisites specific to opening trades:

- TradePlan
- accepted entry intent
- entry-side risk evaluation
- entry parameters

Position close is not a new trade-entry workflow.

### ExecutionIntent Lifecycle: Adapt, Do Not Reuse Unchanged

The existing `ExecutionIntent` state model and persistence SHOULD NOT be reused unchanged if doing so forces TradePlan/entry semantics onto position commands.

Position commands may require a dedicated lifecycle abstraction, or a generalized command lifecycle may be identified. The ADR does not prescribe the exact persistence model.

### Application-Level Idempotency: Mandatory

Application-level idempotency remains MANDATORY.

Reason:
- Kraken does not guarantee uniqueness of `cl_ord_id`.
- cTrader `clientMsgId` is documented as correlation rather than idempotent deduplication.

Therefore, provider request identifiers MUST NOT be treated as sufficient idempotency guarantees.

### UNKNOWN Outcome Invariant

```text
timeout != rejection
timeout != success
```

If broker submission outcome is uncertain:

```text
UNKNOWN
    ↓
reconciliation
```

NOT:

```text
UNKNOWN
    ↓
blind retry
```

This is especially critical because repeating a close command could have financial consequences.

### Reconciliation

Reuse the proven Story 0031 architectural principle:

```text
submission outcome uncertain
    ↓
query provider-authoritative state
    ↓
determine whether command executed
```

Provider implementations may use different mechanisms:
- Kraken → order queries + position refresh
- cTrader → `ProtoOAReconcileReq` / position APIs

Trading Core SHALL consume provider-neutral reconciliation outcomes. Provider reconciliation APIs MUST NOT leak into Trading Core.

### Ownership and Security

Commands against open positions are sensitive broker mutations. Defense in depth is preserved:

```text
Trading Core → authenticated user → account ownership
Broker Service → broker-account/credential ownership
```

Frontend route guards alone are insufficient.

### Risk Semantics

The ADR distinguishes:

```text
increase exposure (requires TradePlan + RiskEvaluation)
```

from:

```text
reduce/terminate exposure (does NOT require TradePlan/entry RiskEvaluation)
```

Full close does NOT require an accepted TradePlan or the existing entry RiskEvaluation prerequisite. However, position commands still require deterministic validation:

- position exists
- position belongs to resolved broker account
- current quantity > 0
- command cannot increase/reverse exposure
- broker/provider supports requested operation

Provider-specific validation remains below the appropriate boundary.

### Provider Abstraction Rule

```text
Trading Core owns user intent and business safety.
Broker Service owns translation into provider-specific trading operations.
```

Therefore Trading Core MUST NOT know:
- Kraken provider-specific close mechanics
- Kraken leverage close mechanics
- `ProtoOAClosePositionReq`
- `ProtoOAAccountType`
- provider protobuf models

### Kraken Implementation Implication (Consequence)

The Kraken adapter will implement the broker-neutral full-exposure-close intent using an opposite-side market order with `reduce_only=true`. The adapter MUST guarantee no position reversal even though Kraken expresses the operation using an order primitive.

**For Story 0033, Kraken FULL EXPOSURE CLOSE uses exactly one mechanism: opposite-side market order with `reduce_only=true`.** This fits existing AddOrder execution infrastructure, provides no-reversal protection, supports explicit correlation via `cl_ord_id`, is compatible with current reconciliation concepts, and avoids introducing separate settle-position behavior into V1.

**For Kraken, "full close" means: close all current exposure for the pair, using FIFO settlement across all open positions for that pair.** The selected OpenPositions txid provides read identity for display; the mutation operates on the provider-defined exposure scope.

### cTrader Implementation Implication (Consequence)

The future cTrader adapter can map the same broker-neutral intent to the dedicated `ProtoOAClosePositionReq` using its provider position ID. This demonstrates why the abstraction must describe intent rather than order mechanics. cTrader is NOT implemented in Story 0033.

### Netting and Hedging Neutrality

The architecture MUST NOT assume one position per account + instrument. Position-targeted commands remain valid for:
- multiple same-symbol positions
- hedged accounts
- netted accounts
- provider-specific position models

The opaque broker position reference is therefore part of the architectural contract **for observation and correlation**. It serves as a read identity / resolution handle — the server resolves it into the provider-authoritative mutation scope. For mutation, the target scope is provider-dependent.

### Authority Reload Boundary

The broker-authoritative reload SHOULD occur as follows:

```text
Trading Core:
    - authentication
    - ownership validation
    - business intent validation
    - requests refreshed positions from Broker Service

Broker Service:
    - resolves broker position reference (resolution handle) to determine target exposure scope
    - performs final provider-authoritative revalidation immediately before mutation
    - submits provider-specific command
```

This boundary minimizes TOCTOU race by performing the final provider-authoritative read immediately before mutation inside the provider adapter.

### TOCTOU Requirement

Time Of Check / Time Of Use is explicitly addressed:

A position may change between position reload and provider mutation. The ADR requires provider-side safety guarantees where available:

- Kraken → `reduce_only=true` on opposite-side market order
- cTrader → position-targeted close semantics + provider-side volume validation

Server reload alone is not sufficient protection against every race.

## Consequences

### Positive

- Clear separation between opening/increasing exposure and reducing/terminating exposure.
- Provider-independent Trading Core.
- Safe support for Kraken `reduce_only=true` on opposite-side market order semantics (FIFO exposure close).
- Natural future cTrader support via dedicated close-position primitive.
- No instrument-only position ambiguity (multiple positions per symbol supported).
- No frontend authority over mutable broker state.
- Reusable UNKNOWN/reconciliation safety model from Story 0031.
- Incremental path toward partial close and SL/TP management.
- Truthful representation of provider capabilities — does not falsely equate read identity with command addressability.
- Supports provider-divergent addressability (Kraken: pair/exposure scope; cTrader: individual position).

### Negative / Accepted Costs

- New broker capability required.
- Position read contract must expose broker position reference consistently.
- Position command lifecycle may require new application/persistence concepts.
- Additional reconciliation mapping.
- Provider adapters require explicit close implementation.
- More interfaces than simply extending `ExecutionCapability`.
- UI may expose different close behavior depending on provider capability.
- Provider-neutral model must represent operation availability/addressability.

These are acceptable costs for semantic and safety correctness.

## Rejected Alternatives

### Alternative A — Extend ExecutionCapability with reduceOnly

Rejected because:
- Provider mechanics leak into broker-neutral abstraction.
- Opening/increasing and reducing/terminating exposure become conflated.
- cTrader uses a fundamentally different close-position primitive.
- `reduceOnly` is not a universal provider concept.

### Alternative B — Identify Position by Account + Instrument

Rejected because:
- Multiple positions for one instrument may exist (Kraken FIFO, cTrader HEDGED mode).

### Alternative C — Trust Quantity and Side from Angular

Rejected because:
- Story 0032 polling can be stale (10-second interval).
- Broker state may change outside Trading OS.
- Sensitive state must be reloaded server-side.

### Alternative D — Introduce Persistent Trading OS Position Aggregate Now

Rejected because:
- Broker remains authoritative.
- No demonstrated business requirement currently requires independent Trading OS position identity.
- Would introduce synchronization/persistence complexity prematurely.

### Alternative E — Blind Retry After Timeout

Rejected because:
- Providers do not provide sufficient universal idempotency guarantees.
- Financial mutation may already have occurred.

### Alternative F — Treat Kraken OpenPositions txid as Individually Command-Addressable

Rejected because:
- Official Kraken APIs do not support exact txid-targeted mutation.
- FIFO settlement would mutate a different position entry than the one selected.
- Would misrepresent provider capability to users.

### Alternative G — Pretend FIFO Reduction Equals Exact-Position Close

Rejected because:
- It can mutate different broker position entries from the one the user selected.
- Violates the architectural invariant: Identity != Command Addressability.
- Users would observe unexpected position closure order.

## Architectural Invariants

I1 — Broker Authority  
Open-position state is broker-authoritative.

I2 — Human Authority  
Position-management mutations originate from explicit human commands.

I3 — Position Identity and Addressability
Observed broker positions retain opaque read identities. A mutation may start from such a read identity, but the actual command target is resolved according to provider-authoritative command addressability. Trading OS must never infer a finer mutation granularity than the provider supports. For Kraken this is the pair-level aggregate with FIFO settlement; for cTrader this is the individual positionId.

I4 — Server Authority  
Current side and aggregate reducible quantity are derived from freshly reloaded broker state before mutation.

I5 — No Exposure Reversal  
A close/reduce command must never increase or reverse exposure.

I6 — Provider Isolation  
Provider-specific close mechanics remain inside Broker Service/provider adapters.

I7 — Uncertain Outcome  
UNKNOWN broker outcomes are reconciled before another financially equivalent command may be attempted.

I8 — Application Idempotency  
Provider correlation/request identifiers are not assumed to provide sufficient idempotency.

I9 — No Premature Local Position Aggregate  
Trading OS does not introduce persistent internal position identity without demonstrated domain need.

I10 — Command Addressability  
Trading OS must never present or execute a position-level mutation unless the resolved provider can authoritatively address that position at that command granularity.
