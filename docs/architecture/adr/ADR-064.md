## 1. Context

Trading OS already has two different meanings of execution:

```text
Operational execution
    approved TradePlan -> Risk -> human authorization -> broker or PAPER

Historical research execution
    hypothetical StrategyIntent -> historical evidence -> deterministic replay
```

The first path is governed by ADR-029, ADR-041, and the Risk architecture. It
may create financial side effects and must remain account-aware, human-controlled,
idempotent, and recoverable.

The second path does not authorize a trade, mutate an account, call a broker, or
replace Risk. It asks a narrower question:

> What execution and economic result could be defensibly attributed to a
> hypothetical strategy intent, using only admissible historical evidence and
> explicit versioned assumptions?

Story 0113 found that Trading Core already contains a partial deterministic
economic foundation:

```text
ReferenceMarketState
StrategyIntent
SimulatedExecution
TransactionCosts
CostEvidence
EconomicResult
MarketOrderEconomicEvaluator
```

These concepts must remain the foundation. A parallel economic domain would
create avoidable divergence from the existing Trading Core authority.

The foundation is not yet a complete research path:

- `MarketOrderEconomicEvaluator` has no production caller;
- `EconomicResult` is currently single-leg oriented;
- economic results are not persisted or exported in the current research
  dataset;
- `TransactionCosts` requires numeric funding and cannot by itself distinguish
  `NOT_APPLICABLE` from `UNAVAILABLE`;
- fee and funding values are supplied to the evaluator rather than selected from
  complete strict historical repositories;
- the current PAPER adapter uses current bid/ask state and is not a historical
  simulator;
- Funding Evidence is currently `PROVIDER_BLOCKED`;
- Broker source contains historical fee-schedule migrations that are not applied
  by the observed Broker runtime.

The current passive data clocks establish collection capability, not an
architectural invariant:

- OHLC collection exists;
- Order Book collection exists and was still growing at the latest measurement;
- FeatureSnapshot production exists;
- historical Funding Evidence does not currently exist.

The purpose of this ADR is to establish the authority, semantics, and limits
for future implementation. This ADR does not implement any of them.

## 2. Problem Statement

A predictive edge is not automatically a tradable edge.

A gross-profitable strategy is not automatically a net-profitable strategy.

Without an explicit architecture, future research could silently:

- use current provider state as historical state;
- treat event time as knowledge time;
- fill more quantity than captured liquidity supports;
- treat a touched LIMIT price as a fill;
- treat missing commission or funding as zero;
- use predicted funding as realized funding;
- subtract spread twice;
- put strategy P&L into `ObservedMarketOutcome`;
- duplicate Java accounting in Python;
- make Market Intelligence a second execution engine;
- call the operational PAPER adapter as a backtester;
- call a partial economic result fully net.

The architecture must make these outcomes impossible or visibly rejected.

## 3. Decision

Trading OS adopts a five-layer historical economic model:

```text
Historical Market Evidence
        -> Reference Market State
        -> Strategy Intent
        -> Simulated Execution
        -> Explicit Costs
        -> Economic Result
```

The layers remain conceptually separate. Each layer preserves its own authority,
provenance, temporal rules, missingness, and versioned semantics.

Trading Core remains the deterministic authority for historical execution
calculation, explicit cost application, cost completeness, and economic results.
Market Data remains the authority for normalized historical market evidence and
strict replay. Broker Service remains the authority for provider/account fee
truth and live provider execution facts. Market Intelligence remains the
orchestrator and owner of deterministic interpretation, FeatureSnapshots,
objective outcomes, and bounded research population. Python remains a downstream
statistical consumer.

This decision does not create a new microservice, public API, runtime
configuration, migration, simulator implementation, or Python service.

## 4. Architectural Invariants

The following are architectural invariants, not documentation-only comments:

```text
UNKNOWN != ZERO
UNAVAILABLE != ZERO
NOT_APPLICABLE != UNAVAILABLE
PREDICTED != REALIZED
GROSS != NET
VISIBLE_LIQUIDITY != GUARANTEED_LIQUIDITY
MARKET_MOVEMENT != STRATEGY_PNL
```

The following claims are prohibited unless their required evidence and policy
conditions are met:

```text
missing fee       -> zero fee
missing funding   -> zero funding
missing depth     -> infinite liquidity
LIMIT touched     -> LIMIT filled
current state     -> historical state
prediction        -> realized settlement
partial result    -> fully net profitability
```

Every simplifying assumption must be explicit, immutable for the result, and
identified by a semantic policy version.

## 5. Five-Layer Truth Model

### 5.1 Reference Market State

`ReferenceMarketState` remains the canonical Trading Core foundation for the
provider-neutral market facts consumed by economic calculation. It represents
market truth eligible for a specific historical cutoff. It does not represent
strategy truth or economic truth.

Its future semantic contract must be capable of identifying, as applicable:

- market identity;
- provider-neutral product type;
- instrument identity;
- reference price;
- best bid and best ask;
- spread;
- eligible visible Order Book state;
- captured visible depth;
- market constraints and precision;
- evaluation and execution cutoffs;
- source sequence/checkpoint;
- evidence fingerprints;
- `occurredAt` and `knownAt` bounds;
- normalization and replay policy versions.

The exact future class shape is an implementation concern. The current
`ReferenceMarketState` remains canonical and must evolve rather than be
duplicated.

### 5.2 Strategy Intent

The existing Trading Core `StrategyIntent` remains the canonical conceptual
representation of a hypothetical research action. It is not an operational
`TradePlan` and must not inherit account authorization, Risk approval, human
execution authorization, or broker mutation semantics.

Its minimum semantic responsibility is:

- market/instrument identity;
- decision time `T0`;
- side;
- order type;
- quantity or notional;
- optional order constraints;
- holding and exit policy reference where applicable;
- strategy definition/version fingerprint.

The current type is intentionally partial. It already contains instrument,
side, order type, quantity, and decision time. Future implementation may evolve
it or aggregate it with additional immutable research metadata. A separate
`ResearchStrategyIntent` type must not be created merely to rename the existing
concept.

Typed low-level concepts such as `Side`, `OrderType`, `Quantity`, and `MarketId`
may be reused where their semantics match. Operational `TradePlan` semantics
must not be reused wholesale.

The boundary is:

```text
StrategyIntent = what a hypothetical strategy wanted to do
TradePlan      = what a human reviewed and proposed for an account
```

Therefore:

```text
StrategyIntent != TradePlan
```

### 5.3 Simulated Execution

`SimulatedExecution` remains the canonical single-leg execution foundation.
It may evolve or be aggregated to represent multiple fills, partial quantity,
remainder, VWAP, and execution status. No parallel fill model is approved.

V1 supports MARKET orders only:

```text
StrategyIntent at T0
        -> explicit execution cutoff
        -> strict eligible ReferenceMarketState
        -> consume opposite-side visible book
        -> simulated fills
        -> filled quantity and remainder
        -> VWAP and execution status
```

V1 uses zero modeled latency as an explicit, versioned assumption. This means
the initial execution cutoff is `T0` unless a later execution policy explicitly
defines a submission delay. Zero modeled latency is not measured real-world
latency and must not be described as such.

### 5.4 Explicit Costs

`TransactionCosts` remains the canonical cost aggregation foundation. It must
evolve beyond mandatory numeric values where a cost is unavailable or not
applicable.

Explicit costs are separate from execution-price effects:

- commission or fee;
- funding;
- borrow or other provider-specific explicit cost only when later supported by
  admissible evidence and policy.

Spread crossing, visible depth consumption, and modeled execution degradation
primarily affect simulated fill prices or execution attribution. They must not
be charged again as arbitrary explicit costs.

### 5.5 Economic Result

`EconomicResult` remains the canonical economic-result foundation. Its current
single-leg shape is retained as an intermediate capability, not treated as the
complete lifecycle contract.

The future aggregate economic boundary combines:

```text
entry execution
    + holding interval
    + exit execution
    + applicable explicit costs
    -> aggregate EconomicResult
```

The exact aggregate class shape is deferred. It may aggregate existing
single-leg results rather than replace them. It must remain distinct from
`ObservedMarketOutcome` and from operational account P&L projections.

## 6. Ownership Boundaries

### 6.1 Market Data

Market Data owns:

- provider acquisition;
- provider-neutral normalization;
- OHLC, Order Book, and future Funding Evidence;
- `occurredAt` and `knownAt` semantics;
- effective-time evidence intervals where applicable;
- checksum and trust validation;
- valid Order Book sequence reconstruction;
- strict historical reads at a cutoff;
- source evidence fingerprints.

Market Data does not decide strategy profitability and does not own economic
result calculation.

The current Order Book contract in ADR-063 remains authoritative. A replay must
use one valid sequence and trusted snapshot/checkpoint, include only evidence
with `knownAt <= cutoff`, and return explicit unavailable/invalid results when a
complete reconstruction cannot be established. Because the provider may not
expose a complete network sequence, the architecture must expose that evidence
limitation rather than claim perfect gap detection.

### 6.2 Trading Core

Trading Core owns:

- the deterministic economic domain and calculation policy;
- provider-neutral reference-state consumption;
- deterministic MARKET fill calculation;
- visible-depth book walking;
- VWAP, precision, and quantity handling;
- execution status and remainder semantics;
- application of eligible fee and funding evidence;
- cost completeness;
- economic-result calculation and identity;
- calculation fingerprints.

Trading Core must not acquire provider-specific historical data directly. It
consumes provider-neutral ports or contracts whose source remains owned by the
source service.

Operational Execution Domain behavior remains governed by ADR-029. Historical
simulation does not enter `ExecutionIntent`, does not require Risk approval, and
does not create broker side effects.

### 6.3 Broker Service

Broker Service owns:

- broker connectivity and credentials;
- provider-specific mapping and error translation;
- live provider execution facts;
- provider/account fee truth;
- acquisition of historical provider/account fee schedules where supported.

`HistoricalFeeSchedule` remains the canonical existing fee-evidence foundation.
It includes provider/account scope, maker/taker rates, instrument/product,
settlement asset, effective interval, observed/known times, source, origin,
normalization version, and fingerprint.

Broker Service does not own historical strategy simulation, strategy
profitability, Risk authorization, or economic-result interpretation.

### 6.4 Market Intelligence

Market Intelligence owns:

- deterministic interpretation of replayed market evidence;
- analysis context orchestration;
- FeatureSnapshot projection;
- `ObservedMarketOutcome` evaluation;
- research population and dataset construction/export.

Market Intelligence may orchestrate candidate research intents and dataset
membership, but it must not own order matching, fills, transaction-cost
accounting, settlement, Risk, or broker calls. It must not become a second
execution engine.

### 6.5 Python Research

Python owns:

- strategy experimentation;
- statistical analysis;
- chronological and walk-forward splits;
- out-of-sample evaluation;
- break-even and cost-sensitivity studies;
- stress analysis, visualization, and ML experimentation.

Python must consume validated Java-produced economic samples. It must not
redefine fills, fees, funding, P&L, completeness, temporal eligibility, or
canonical economic fingerprints.

## 7. Historical Eligibility and Temporal Integrity

Historical evidence is eligible only under an explicit cutoff. The fundamental
rule is:

```text
evidence.knownAt <= applicableCutoff
```

Provider event time alone is insufficient. `occurredAt` identifies source/event
time; `knownAt` identifies the earliest defensible time Trading OS accepted the
evidence under its evidence policy.

The architecture defines three clocks.

### 7.1 Decision Time

At `T0`, every decision input must satisfy:

```text
knownAt <= T0
```

Future outcomes, execution results, future funding, and later corrections must
not enter the `FeatureSnapshot`, `StrategyIntent`, strategy definition input,
or decision fingerprint.

### 7.2 Execution Time

Execution may occur after decision time only through an explicit policy:

```text
decisionAt   = T0
submissionAt = T0 + modeledLatency
executionAt  >= submissionAt
```

V1 uses `modeledLatency = 0` and makes this assumption visible through the
execution model version. Evidence after `T0` is not eligible for V1 merely
because its provider `occurredAt` precedes `T0`.

### 7.3 Outcome Time

Future evidence after `T0` may describe what happened later. It remains separate
from what was known at decision time and what was available at execution time.
`ObservedMarketOutcome` remains the objective outcome contract under ADR-059.

## 8. V1 Deterministic Execution Policy

### 8.1 MARKET Only

V1 supports MARKET orders only. LIMIT orders remain unsupported because a
historical price touch does not establish:

- queue position;
- fill probability;
- order lifetime;
- cancellation or replacement;
- trade-through;
- actual fill.

The invariant is:

```text
limit touched != limit filled
```

The current PAPER adapter may continue to support its existing immediate LIMIT
behavior. That behavior is not historical research semantics and is not changed
by this ADR.

### 8.2 Visible-Depth Book Walking

V1 uses Level 3 visible-depth execution when a strict valid Order Book replay is
available:

- BUY consumes eligible asks from lowest to highest;
- SELL consumes eligible bids from highest to lowest;
- fills are deterministic from the immutable levels and quantity;
- VWAP, filled quantity, and remainder are explicit;
- the selected sequence/checkpoint and evidence fingerprint are retained;
- no liquidity beyond captured visible depth is inferred.

If requested quantity exceeds captured depth, the result must represent the
remainder explicitly. The execution status is `PARTIALLY_FILLED` with an
`INSUFFICIENT_DEPTH` reason when some quantity was filled. If no defensible fill
can be produced, the result is `UNFILLED` or `EXECUTION_UNAVAILABLE` according
to the existing result-status vocabulary.

Visible-book replay is a deterministic counterfactual over recorded liquidity.
It does not prove that the same liquidity would have remained available if the
hypothetical order had entered the market.

### 8.3 Execution Impact

The architecture distinguishes:

- spread crossing;
- visible-depth consumption;
- modeled execution degradation;
- commission;
- funding;
- other explicit provider costs.

Execution effects primarily change simulated fill prices. Explicit costs remain
separate monetary deductions.

Diagnostics such as spread, depth, and slippage attribution are allowed, but:

```text
one economic effect -> one accounting representation
```

The same effect must never be included in both the simulated price and the
explicit cost ledger.

## 9. Fee and Funding Architecture

### 9.1 Historical Fee Truth

Broker Service owns provider/account observed fee truth. Historical fee evidence
must be selected using provider-neutral scope, effective interval, known-at
eligibility, source provenance, and a schedule fingerprint.

Research must not silently select an arbitrary account's current fee tier.

When research is not tied to a live account, the selection/application policy is
a separate immutable, versioned `ResearchFeePolicy` concept. It may select a
historical account-scoped schedule or an explicit research assumption, but the
choice and scope must be visible in the economic result.

For initial MARKET execution, taker treatment is permitted only as an explicit
versioned policy consistent with provider semantics. LIMIT orders are unsupported
and therefore cannot be assumed maker orders.

### 9.2 Runtime Prerequisite

Broker source contains historical fee-schedule migrations V3/V4 while the
observed runtime was at V2 and did not contain `historical_fee_schedule`.
This is a known implementation prerequisite. It is not solved by this ADR and
must be addressed by a separate implementation Story before runtime fee-aware
research is claimed ready.

### 9.3 Funding

Funding historical evidence remains `PROVIDER_BLOCKED`. The architecture does
not invent a funding history or use current/predicted provider values as a
historical fallback.

The following meanings are mandatory:

```text
SPOT without applicable funding       -> NOT_APPLICABLE
Applicable perpetual funding missing  -> UNAVAILABLE
Predicted funding rate                 -> not realized FundingCost
Realized FundingCost                   -> only from eligible evidence/policy
```

A derivative holding interval crossing applicable funding events cannot be
classified as fully costed when required Funding Evidence is unavailable. Gross
or execution-adjusted research may still be produced when its status is visible.

## 10. Cost Completeness

Economic result availability/status and cost completeness are separate
dimensions.

### 10.1 Economic Result Availability

The existing `EconomicResultStatus` remains the availability/failure boundary
for the current foundation. Future execution evaluation should preserve explicit
statuses equivalent to:

```text
AVAILABLE
INSUFFICIENT_DATA
STALE
UNSUPPORTED
INVALID_INPUT
DEGRADED
EXECUTION_UNAVAILABLE
```

The exact enum evolution is implementation scope, not this ADR.

### 10.2 Cost Completeness

The future aggregate economic result must have a separate completeness dimension:

```text
FULLY_COSTED
PARTIALLY_COSTED
GROSS_ONLY
INSUFFICIENT_EVIDENCE
```

Semantics:

- `FULLY_COSTED`: all applicable execution and explicit cost components are
  supported by admissible evidence or an explicit versioned policy;
- `PARTIALLY_COSTED`: execution is evaluable and some applicable costs are
  known, but at least one applicable cost is incomplete;
- `GROSS_ONLY`: only market movement or strategy gross economics are defensible;
- `INSUFFICIENT_EVIDENCE`: required evidence is missing, stale, invalid, or
  ineligible.

`EXECUTION_UNAVAILABLE` is an availability/result status, not a claim that a
cost was fully or partially known.

The following invariant applies everywhere:

```text
EconomicResult.completeness != FULLY_COSTED
    -> it must not be presented as fully net profitability
```

For a complete lifecycle, authoritative `NetPnL` and `NetReturn` require both:

- `CostCompleteness = FULLY_COSTED`;
- a defensible completed entry/exit execution lifecycle under the selected
  execution policy.

A partial fill may have mathematically known costs for its filled portion, but
the overall intent must retain its requested quantity, remainder, execution
status, and inability to claim a fully executed strategy result.

## 11. Economic Result Semantics

The future aggregate result must be capable of distinguishing:

- `ReferenceMarketReturn`;
- `GrossStrategyPnL`;
- `ExecutionAdjustedPnL`;
- `CommissionCost`;
- `FundingCost`;
- `OtherExplicitCosts`;
- `NetPnL`;
- `NetReturn`;
- execution status;
- cost completeness;
- execution, cost, strategy, evidence, and policy fingerprints.

Unavailable components must not be forced to numeric zero. If a partial numeric
view is exposed, it must identify its scope and completeness and must not be
indistinguishable from an authoritative full-net result.

The accounting flow is:

```text
reference market movement
        -> simulated entry/exit prices
        -> execution-adjusted strategy result
        -> explicit commission/funding/other costs
        -> net economic result when complete
```

Spread crossing is already represented when BUY uses ask and SELL uses bid. It
must not be subtracted again as `spreadCost`.

## 12. `ObservedMarketOutcome` Boundary

`ObservedMarketOutcome` remains the immutable, provider-neutral objective future
market outcome under ADR-059. It must not acquire:

- strategy direction;
- entry or exit;
- simulated fills;
- quantity;
- spread or slippage;
- commission or funding;
- P&L;
- strategy success;
- Risk result;
- execution status.

Market movement is not strategy P&L. An economic result may reference an
objective outcome, but it is a separate fact with separate provenance and
identity.

## 13. PAPER Relationship

The architecture accepts option B from Story 0113:

```text
shared pure deterministic execution primitives
        /                         \
historical evidence adapter       PAPER/current-state adapter
        |                          |
historical research result        PAPER settlement
```

Shared primitives may eventually include:

- book walking;
- fill calculation;
- VWAP;
- precision;
- quantity handling;
- execution statuses.

The following remain separate:

- historical evidence acquisition;
- current/live market state;
- account mutation;
- PAPER settlement;
- Risk;
- persistence adapters;
- provider reconciliation.

Historical research must not call `SimulatedExecutionAdapter` as its simulator.
The current adapter reads current provider-backed snapshots and contains
operational PAPER behavior. PAPER settlement must not consume historical
research artifacts implicitly.

This ADR does not modify PAPER behavior. ADR-042 remains authoritative for the
fact that PAPER is Trading Core-owned local simulation and is not backtesting.

## 14. Risk and Operational Execution Boundary

Raw historical strategy research may evaluate strategy edge without applying
account-specific RiskRules. A later experiment may explicitly compare:

```text
strategy
versus
strategy + Risk policy
```

These are distinct research questions.

This independence does not weaken operational trading:

```text
Every operational TradePlan -> deterministic Risk authorization
                         -> explicit human authorization
                         -> Execution Domain
```

Historical `StrategyIntent` is not an `ExecutionIntent`, does not require Risk
approval, and cannot bypass operational Risk.

## 15. Java and Python Authority

Java is authoritative for:

- strict evidence selection;
- point-in-time reference state;
- deterministic fills and book walking;
- VWAP, rounding, and precision;
- fee and funding application;
- cost completeness;
- economic-result values and fingerprints.

Python is authoritative only for its statistical experiment outputs:

- walk-forward and OOS analysis;
- aggregate metrics;
- break-even and sensitivity analysis;
- stress comparisons;
- visualization and ML experiments.

Python must not independently calculate canonical fills, fees, funding, P&L, or
cost completeness.

The accepted research flow is bounded and does not introduce a Python runtime
dependency into production:

```text
Java strict factual datasets
        -> Python strategy/hypothesis exploration
        -> candidate StrategyIntent artifacts
        -> Java deterministic economic evaluation
        -> versioned EconomicResult artifacts
        -> Python statistical economic analysis
```

Candidate intents and results may be exchanged through offline exported,
versioned artifacts or a future bounded research interface. This ADR does not
choose a transport and does not create a Python service.

## 16. Versioning and Provenance

Semantic policy changes must create distinct experiment meaning. At minimum,
future results must identify:

- strategy definition/version;
- StrategyIntent fingerprint;
- FeatureSnapshot fingerprint and projection version;
- ReferenceMarketState fingerprint;
- Order Book sequence/checkpoint and source evidence fingerprint;
- execution model version;
- transaction-cost model version;
- fee policy version and fee schedule fingerprint/scope;
- funding policy version, Funding Evidence fingerprints, or explicit status;
- market/evidence normalization versions;
- outcome definition and selected immutable outcome fingerprints where used;
- dataset population/manifest fingerprint;
- repository/code version when exported.

Evidence and policy are separate:

```text
HistoricalFeeSchedule = provider/account evidence
ResearchFeePolicy     = how research selects/applies evidence or assumptions
```

They must not be merged into one mutable configuration blob.

The identity principle is:

```text
same semantic inputs + same policies
    -> same deterministic EconomicResult content/identity

changed evidence, strategy, execution policy, or cost policy
    -> different result identity
```

Operational timestamps, database identifiers, and random identifiers must not
change deterministic semantic identity unless explicitly part of the policy.

## 17. Research Dataset Boundary

`research-dataset-v1` remains unchanged. It contains the existing FeatureSnapshot
and explicitly selected objective outcomes under ADR-060 through ADR-062. No
economic result is retrofitted into V1.

Future economic research must use a separate economic dataset contract or an
explicit later dataset version. This ADR chooses the conceptual separation, not
the future schema name. The economic contract must preserve economic-result
completeness and provenance instead of weakening the existing V1 sample model.

`feature-projection-v1` remains unchanged. Liquidity features and any semantic
membership change require a future projection version. The ordering is:

```text
economic execution contract
    -> baseline economic research
    -> possible FeatureProjection V2
    -> explicit V1 versus V2 comparison
```

FeatureProjection V2 is not part of this ADR.

## 18. Backtest Architecture

The accepted V1 research architecture is hybrid:

```text
vectorized/statistical strategy exploration
        +
deterministic Java candidate execution replay
```

Vectorized exploration is appropriate for broad candidate screening. A full
event-driven exchange simulator is deferred because current evidence does not
justify reliable modeling of:

- queue position;
- calibrated latency distribution;
- cancel/replace behavior;
- counterfactual order impact;
- fill probability;
- dynamic market impact.

The initial scope is deliberately narrow:

- one bounded market/product scope;
- MARKET orders;
- strict visible-depth replay;
- existing `PT1H`, `PT4H`, and `PT24H` horizons where applicable;
- explicit versioned commission policy;
- explicit funding completeness;
- zero modeled latency;
- no LIMIT execution;
- no queue simulation;
- no calibrated latency;
- no dynamic market-impact model.

## 19. Metrics and Profitability Language

Prediction metrics remain separate from economic metrics.

Prediction metrics include:

```text
MAE, RMSE, R2, Pearson, Spearman, direction accuracy
```

Economic metrics include:

```text
gross/net PnL when applicable
return when denominator and completeness are valid
profit factor
expectancy
drawdown
turnover
exposure
cost/gross profit
```

Python may later calculate break-even cost, cost sensitivity, spread/depth
stress, and execution-policy comparisons from Java outputs.

Research language must preserve evidence quality:

Allowed:

```text
gross-positive
execution-adjusted positive
partially costed
fully costed
net-positive under policy X
```

Forbidden without complete evidence and policy:

```text
realistic net profit
fully net profitability
tradable edge
```

This is a research-integrity rule, not marketing policy.

## 21. Consequences

### Positive Consequences

- Predictive and economic claims remain distinguishable.
- Historical execution is tied to strict evidence and explicit cutoffs.
- Trading Core remains the single deterministic economic authority.
- Market Data remains the owner of historical market truth.
- Broker-specific details remain outside the economic domain.
- Spread cannot be silently double-counted.
- Missing fee, funding, and depth cannot silently become zero or infinite.
- Partial fills and incomplete costs remain visible.
- PAPER and research can eventually share pure primitives without sharing
  authority, evidence adapters, or account mutation.
- Python can perform useful statistical work without redefining financial
  semantics.
- Existing FeatureProjection and objective outcome contracts remain stable.
- The architecture remains bounded and avoids a premature exchange simulator.

### Negative Consequences

- More provenance, policy, and completeness metadata must be retained.
- A fully net economic result may be unavailable for a substantial portion of
  derivative research until Funding Evidence exists.
- Fee policy selection for account-independent research requires an explicit
  versioned assumption.
- Trading Core needs strict provider-neutral evidence ports without owning data
  acquisition.
- Partial execution and lifecycle aggregation are more complex than one fill
  and one numeric cost record.
- Research consumers must handle explicit degraded states rather than assuming a
  rectangular fully numeric dataset.

### Trade-offs

- V1 sacrifices limit-order realism for falsifiability and evidence quality.
- Zero modeled latency is reproducible but not realistic latency measurement.
- Visible-depth replay is more defensible than fixed slippage but remains a
  counterfactual over recorded liquidity.
- A separate economic dataset preserves V1 semantics but creates another
  versioned research contract.
- Sharing pure primitives reduces semantic drift but requires careful extraction
  from current operational adapters.

### Deferred Decisions

- exact aggregate `EconomicResult` class shape;
- exact completeness/status enum names in code;
- economic dataset schema/name;
- research fee-policy storage and selection API;
- Funding Evidence provider and settlement acquisition;
- latency calibration;
- queue and limit-fill model;
- dynamic market-impact model;
- PAPER integration with economic research primitives;
- public or internal economic-result API;
- physical persistence schema and migration sequence.

### Known Limitations

1. Funding historical evidence is currently `PROVIDER_BLOCKED`.
2. Historical fee-schedule source migrations are ahead of observed Broker runtime.
3. Order Book providers may not expose a complete network sequence, limiting
   detectable gap guarantees.
4. Visible book depth is not guaranteed counterfactual liquidity.
5. Current economic classes are partial and not integrated into production or
   research export.
6. The current PAPER adapter remains operationally simple and supports behavior
   that V1 historical research explicitly rejects.

## 22. Alternatives Rejected or Deferred

### Direct PAPER Adapter Reuse

Rejected. It depends on current snapshots, operational account checks, and PAPER
settlement assumptions. It is not historical evidence replay.

### Independent Market Intelligence Execution Engine

Rejected. It would duplicate Trading Core execution semantics and risk making
Market Intelligence a second financial authority.

### Python-Owned Economic Accounting

Rejected. It would produce divergent fills, fees, funding, rounding, and P&L
semantics. Python remains a downstream statistical consumer.

### Full Event-Driven Exchange Simulator

Deferred. Current evidence does not justify queue, latency, cancellation, dynamic
impact, and counterfactual matching claims.

### LIMIT Fill Simulation in V1

Rejected. Price touch does not prove queue position, lifetime, or fill.

### Zero-Cost Assumptions

Rejected. Missing fee or funding is unavailable or not applicable, never zero by
default.

### Infinite Liquidity Beyond Captured Depth

Rejected. Remainder and insufficient-depth status are mandatory.

### Predicted Funding as Realized Funding

Rejected. Prediction, rate evidence, settlement, and FundingCost remain distinct.

### Adding Strategy P&L to `ObservedMarketOutcome`

Rejected. Objective future market evolution and strategy economics are separate
immutable facts with different authorities and temporal meaning.

## 24. Falsification Review

The ADR was independently checked against the required failure modes:

- **Future leakage:** blocked by decision/execution/outcome clocks and
  `knownAt <= cutoff`.
- **Spread double counting:** blocked by one representation per effect.
- **Funding as zero:** blocked by explicit `NOT_APPLICABLE` versus
  `UNAVAILABLE`.
- **Fees as zero:** blocked by admissible fee evidence or explicit policy only.
- **Predicted funding as realized:** explicitly rejected.
- **TradePlan coupling:** existing `StrategyIntent` remains separate.
- **ObservedMarketOutcome contamination:** explicit prohibited fields.
- **Market Intelligence execution authority:** explicitly rejected.
- **Python duplication:** Java remains economic authority.
- **PAPER divergence:** shared pure primitives accepted; direct adapter reuse
  rejected.
- **Infinite liquidity:** depth overflow produces remainder/status.
- **LIMIT touch equals fill:** LIMIT unsupported in V1.
- **Partial result called net:** completeness and lifecycle gates prohibit it.
- **Versioning gaps:** strategy, execution, cost, fee, funding, normalization,
  dataset, and evidence provenance are required.
- **Provider leakage:** source-specific DTOs remain behind service boundaries.
- **Circular Java/Python dependency:** bounded artifacts are preferred; no Python
  production service is introduced.
- **Over-engineering:** V1 remains MARKET-only and hybrid.
- **Premature event-driven simulation:** explicitly deferred.

### Required scenario

For:

```text
T0
BTC perpetual BUY 2 BTC
valid FeatureSnapshot at T0
valid historical Order Book at execution cutoff
visible asks sufficient for only 1.7 BTC
historical commission policy available
Funding Evidence unavailable
```

The architecture requires:

```text
requested quantity = 2 BTC
simulated filled quantity <= 1.7 BTC
remaining quantity = explicit
execution status = PARTIALLY_FILLED / INSUFFICIENT_DEPTH
commission = applied only from admissible policy
funding = UNAVAILABLE
economic completeness != FULLY_COSTED
no authoritative fully-net profitability claim
```

It is therefore impossible under this ADR to silently produce a 2 BTC full fill,
funding equal to zero, and a fully net result.

## 25. Implementation Constraints

This ADR authorizes no implementation by itself. Future Stories must not:

- create a parallel economic domain;
- modify `research-dataset-v1`;
- modify `feature-projection-v1`;
- modify PAPER behavior under this ADR;
- apply Broker migrations as part of this documentation task;
- introduce provider DTOs into Trading Core economic contracts;
- use current provider state as historical fallback;
- create a Python production service for this boundary;
- add APIs, migrations, runtime configuration, or public UI surfaces without
  their own approved scope.

Future implementation must add deterministic tests for:

- cutoff and `knownAt` eligibility;
- fee and funding missingness;
- `NOT_APPLICABLE` versus `UNAVAILABLE`;
- depth overflow and remainder;
- spread/slippage/fee/funding double-counting;
- policy and evidence fingerprints;
- separation from `ObservedMarketOutcome`;
- Java-produced outputs consumed read-only by Python.
