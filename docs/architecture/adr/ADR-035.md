# ADR-035 — Strategy Evaluation Context and Strategy-Agnostic Evaluation Pipeline

## Status

Accepted

## Date

2026-08-22

## Context

ADR-034 established Strategy as the first-class domain authority for setup
truth. Stories 0009–0012 delivered:

- `StrategyDefinition` with versioned identity, required semantic inputs,
  applicability, parameters, lifecycle and validation metadata;
- `StrategyEvaluationContext` as an infrastructure-free typed semantic input
  container (marketId, instrument, timeframe, evaluatedAt, typed inputs, SHA-256
  digest);
- `StrategyEvaluator` as a pure deterministic function of (definition, context);
- `StrategyEvaluation` with four statuses: MATCH, NO_MATCH, NOT_EVALUABLE, FAILED;
- `StrategyMatch` as an immutable persisted fact derived only from MATCH;
- `TradingOpportunity` derived only from a persisted StrategyMatch;
- `StrategyEvaluatorRegistry` supporting multiple evaluators;
- `StrategyEvaluationService` translating missing-input and runtime exceptions
  into NOT_EVALUABLE / FAILED.

The bootstrap legacy evaluator (`LegacyOhlcTrendEvaluator`) already correctly
returns NO_MATCH when priceChange == 0. The evaluator is already a pure function
of (definition, context) with no clock access, no I/O, and no AI.

However, the surrounding pipeline is not yet strategy-agnostic. Five bootstrap
couplings remain:

1. `OhlcTrendObservationRule` throws `NoSuchElementException` on
   priceChange == 0, causing the pipeline to record a noSignal outcome before
   the strategy evaluator can express NO_MATCH.

2. `ProductionIntelligencePipeline` hardcodes
   `new OhlcTrendObservationRule()` in the observation build call.

3. `LiveStrategyEvaluationRunner` exposes only
   `evaluateLegacyOhlcTrend`; there is no generic method accepting an
   arbitrary StrategyDefinition and assembled context.

4. `StrategyEvaluationContextFactory` provides only
   `fromOhlcTrendValues`; there is no generic context assembly path.

5. `StrategyMatchOpportunityFactory.scenarioOf()` and `timeframeOf()`
   call `requireBootstrap()`, rejecting any non-bootstrap strategy from
   flowing through generic opportunity creation.

6. `BuiltinStrategies.all()` contains only `LEGACY_OHLC_TREND`.

The same deterministic evaluator must eventually serve:

- LIVE evaluation (current pipeline);
- FUTURE BACKTEST / historical replay;
- MARKET INTELLIGENCE deterministic evaluation;
- any future scanner or on-demand evaluation context.

without duplicating strategy semantics or leaking infrastructure into the
evaluator boundary.

## Decision Question

How should the pipeline be restructured so that Strategy alone owns setup truth
while live scanning, future historical replay, Market Intelligence, and
opportunity creation remain decoupled, and what remains from the bootstrap
transition?

## Repository Truth Assessment

The mission premise proposed that StrategyEvaluationContext needed to be
implemented. Repository inspection reveals it already exists as a well-designed
abstraction (`strategy/domain/StrategyEvaluationContext.java`):

- Infrastructure-free: exposes WHAT a strategy needs, never HOW values were
  produced.
- Typed semantic inputs via `SemanticValue` (DECIMAL, INTEGER, STRING, INSTANT,
  DURATION).
- `RequiredSemanticInput` keys declared by StrategyDefinition.
- Deterministic SHA-256 digest for provenance and replay.
- `evaluatedAt` documented as authoritative: evaluators must use this, never
  wall-clock time.
- Same shape produced by live scanning and future historical backtest providers.

The evaluator interface is clean: `evaluate(StrategyDefinition, context) ->
StrategyEvaluation`. The registry supports multiple evaluators. The evaluation
service translates exceptions into FAILED / NOT_EVALUABLE.

The actual remaining work is pipeline generalization, not new domain abstractions.
ADR-035 findings are consistent with repository truth.

## Decision

Trading OS SHALL generalize the evaluation pipeline so that:

1. StrategyEvaluator is the sole authority for deterministic setup truth.
2. Observation remains an upstream knowledge record that MUST NOT decide whether
   a Strategy matches.
3. The generic pipeline does not inspect concrete Strategy IDs.
4. `OhlcTrendObservationRule` exceptions no longer prevent the evaluator from
   expressing NO_MATCH.
5. Opportunity creation becomes strategy-agnostic.
6. The existing LEGACY_OHLC_TREND behavior is preserved as a compatibility
   fixture.

### Detailed Invariants

#### I-1. StrategyEvaluator Sole Authority

Only `StrategyEvaluator.evaluate(StrategyDefinition, context)` may produce:

- MATCH
- NO_MATCH
- NOT_EVALUABLE
- FAILED

Generic Observation or pipeline infrastructure MUST NOT decide that a Strategy
has or has not matched.

A normal market that simply does not satisfy a Strategy's conditions MUST
produce NO_MATCH, not a pipeline failure.

#### I-2. Observation Upstream Knowledge

Observation is a deterministic, explainable record of market state derived from
intelligence evidence, independent of any trading strategy.

Observation MUST NOT decide whether a Strategy matches. The bootstrap
`OhlcTrendObservationRule` currently embeds directional semantics (LONG/SHORT
type suffix) that overlap with strategy evaluation; this overlap is a migration
artifact.

The generic evaluation pipeline MUST work even if Observation produces a
direction-neutral record (no type suffix implying direction). Direction is a
Strategy evaluation result, not an Observation result.

For the bootstrap transition: `OhlcTrendObservationRule` MUST NOT terminate
strategy evaluation when priceChange == 0. A zero directional change should be
representable as a valid direction-neutral Observation result if Observation is
otherwise constructible. StrategyEvaluator then decides NO_MATCH for
LEGACY_OHLC_TREND.

Observation records: "What deterministic market state was observed?"
Strategy answers: "Does that state satisfy this Strategy?"

Do NOT remove Observation in Story 0013.

#### I-3. StrategyEvaluationContext Is Already Sufficient

`StrategyEvaluationContext` is the correct abstraction for semantic inputs.
It is already:

- infrastructure-free;
- typed via `SemanticValue` and `RequiredSemanticInput`;
- deterministic (content-addressed digest);
- live/backtest compatible (same shape from any provider).

No new context abstraction is needed. Future strategy types add new
`RequiredSemanticInput` keys and new semantic-input resolution logic without
changing the generic container.

#### I-4. Required Inputs Declaration

`StrategyDefinition.requiredInputs()` already declares the
`RequiredSemanticInput` keys a strategy needs. The planner or context assembly
layer uses this declaration to determine which deterministic capabilities to
execute and which semantic values to assemble.

The relationship is:

```
StrategyDefinition.requiredInputs
    -> planner determines required deterministic capabilities
    -> capabilities execute
    -> semantic values produced
    -> StrategyEvaluationContext assembled
    -> Strategy evaluated
```

The scanner does not need to know individual Strategy internals; it queries
required inputs from the definition and drives capability execution generically.

#### I-5. Time Semantics

`StrategyEvaluationContext.evaluatedAt` is the authoritative evaluation instant.
Evaluators MUST use `context.evaluatedAt()` and MUST NOT read wall-clock time.

Current code already satisfies this invariant:
- `StrategyEvaluationContext.evaluatedAt` is documented as authoritative.
- `LegacyOhlcTrendEvaluator` uses `context.evaluatedAt()` as fallback when
  `OBSERVED_AT` is absent.
- No `Instant.now()` calls exist in the strategy domain package.
- Pipeline uses `Clock` for orchestration timestamps, not for evaluation
  semantics.

`evaluatedAt` is the authoritative semantic evaluation instant. For LIVE
evaluation, it is derived from the analysis/evaluation timeline and bounded by
available market facts. For future BACKTEST evaluation, it is derived from the
replay timeline.

No semantic input with an effective timestamp later than `evaluatedAt` may be
visible to the evaluator. This is the anti-look-ahead invariant for future
backtesting.

#### I-6. Freshness and Missing Inputs

Ownership:

- Market Data knows raw data freshness.
- Market Intelligence knows whether deterministic capability output is usable.
- `StrategyEvaluationContext` communicates semantic availability via the
  presence/absence of `RequiredSemanticInput` keys.
- `StrategyEvaluator` decides NOT_EVALUABLE when required valid semantic inputs
  are unavailable.

Distinction:

- `NOT_EVALUABLE`: required semantic inputs are missing or stale. This is a
  normal outcome, not a failure. The strategy could not be evaluated against
  current market state.
- `FAILED`: an actual deterministic evaluation error occurred (unexpected
  exception, corrupt data, logic error). This represents a bug or unexpected
  runtime condition.

Stale required data becomes NOT_EVALUABLE rather than NO_MATCH. A strategy that
requires fresh data and receives stale data has not been evaluated; it has not
produced a setup decision.

#### I-7. NO_MATCH Semantics

NO_MATCH means: all required semantic inputs were present and valid, the
evaluator executed successfully, and the strategy's deterministic conditions
were not satisfied by the current market state.

NO_MATCH is a normal, expected, truthful outcome. It is NOT a pipeline failure.
It must NOT be represented as an error in logs, monitoring, or pipeline status.

#### I-8. Applicability Filtering

`StrategyApplicability` determines whether a Strategy CAN meaningfully apply
to a given market/context, BEFORE evaluation occurs:

- unsupported asset class -> NOT APPLICABLE (excluded at selection stage);
- unsupported timeframe -> NOT APPLICABLE (excluded at selection stage);
- unsupported provider -> NOT APPLICABLE (excluded at selection stage).

This filtering occurs BEFORE `StrategyEvaluator.evaluate()` is called. There is
no `NOT_APPLICABLE` StrategyEvaluation status; applicability filtering is a
pre-evaluation selection concern owned by the Scanner/pipeline.

The distinction from NOT_EVALUABLE:

- NOT_APPLICABLE: Strategy is not designed for this market/context. Never
  reaches the evaluator.
- NOT_EVALUABLE: Strategy applies in principle, but required valid semantic
  inputs are currently unavailable. Reaches the evaluator, which returns
  NOT_EVALUABLE.
- NO_MATCH: Strategy applies, inputs are valid, evaluation completed,
  conditions are false.
- FAILED: Evaluation attempted but encountered an unexpected deterministic
  error.

Do not collapse these states.

#### I-9. Condition Results

`ConditionResult` (conditionId, passed, observedValue) is sufficient for V1
strategy explainability. Every MATCH and NO_MATCH should be explainable to a
human trader and reconstructable later.

Future extension (when needed, not now): threshold/reference values, category
grouping, provenance per condition. The current record model does not prevent
this extension.

#### I-10. StrategyDefinition Responsibilities

StrategyDefinition owns:

- strategy identity (StrategyId + version);
- name and description;
- lifecycle status (DRAFT / CANDIDATE / VALIDATED / ENABLED / RETIRED);
- validation status (UNVALIDATED / VALIDATED) and evidence reference;
- direction semantics (LONG_ONLY / SHORT_ONLY / DYNAMIC);
- applicability (asset classes, timeframes, providers);
- required semantic inputs;
- parameters;
- research reference;
- creation and update timestamps.

StrategyDefinition MUST NOT own:

- account or risk authorization;
- position sizing;
- broker execution;
- Market Data acquisition;
- Scanner orchestration;
- AI interpretation authority;
- opportunity ranking.

#### I-11. StrategyMatch Responsibilities

StrategyMatch is an immutable persisted fact recording that a specific Strategy
version satisfied its conditions for a specific market and context at a specific
time.

StrategyMatch stores:

- strategy identity and version;
- market identifier;
- pipeline provenance (analysisExecutionId, observationId);
- direction;
- context digest;
- condition results;
- matchedAt (semantic evaluation time);
- createdAt (persistence time).

StrategyMatch is append-only: it never changes because the strategy evolved,
was retired, new data arrived, or downstream concerns changed.

StrategyMatch MUST NOT contain account-risk authorization state, position
sizing, broker references, or opportunity lifecycle state.

#### I-12. TradingOpportunity Responsibilities

TradingOpportunity is a trader-facing actionable candidate derived from a
successful StrategyMatch.

TradingOpportunity owns:

- trader-visible scenario and timeframe (derived from strategy metadata);
- direction;
- instrument;
- origin (passive scan / user request);
- evidence references;
- validity window;
- match reference (StrategyMatch identity);
- opportunity lineage identity;
- lifecycle state (CREATED / ANALYZED / ACTIVE / ...).

TradingOpportunity MUST NOT re-evaluate strategy conditions or override match
decisions.

#### I-13. Opportunity Creation Generalization

Generic opportunity construction MUST NOT branch on concrete Strategy IDs.

The generic mapping is:

```
StrategyDefinition (declarative metadata)
    + StrategyMatch (actual evaluation result)
    -> TradingOpportunity
```

Opportunity scenario and timeframe are derived from declarative strategy
metadata (applicability timeframes, parameters, or strategy-level display
metadata), NOT from hardcoded per-strategy-ID branching.

`StrategyMatchOpportunityFactory` MUST become strategy-agnostic. The
`requireBootstrap()` guard MUST be removed.

The factory accepts a `StrategyDefinition` parameter alongside the match,
enabling metadata-driven construction without strategy-specific branching.

Minimum metadata required: the StrategyDefinition already carries
`applicability.timeframes` (which determines the applicable timeframe
semantics) and `parameters` (which can carry display-relevant values). If
additional display metadata is needed (e.g., a scenario classification string),
it should be added as declarative metadata on StrategyDefinition, not as a
per-strategy mapping implementation.

Prefer declarative metadata over mapping implementations unless repository
truth demonstrates that mapping contains actual behavior rather than metadata.
ADR-035 does not mandate a specific display mapping mechanism; Story 0013
implements the minimum viable approach.

#### I-14. Matching vs Ranking

StrategyEvaluator produces setup truth (MATCH / NO_MATCH / NOT_EVALUABLE /
FAILED).

Opportunity Ranking is downstream prioritization among valid matches. Ranking
MUST NOT alter historical MATCH truth. Ranking is NOT part of Story 0013.

The boundary:

- StrategyEvaluator: "does this market satisfy this strategy's conditions?"
- Ranking: "given multiple valid matches, which should the trader see first?"

#### I-15. Strategy vs Scanner

Scanner owns:

- user trigger;
- scan scope and market selection;
- orchestration and lifecycle;
- progress reporting;
- capability execution coordination.

Strategy owns:

- applicability requirements;
- deterministic setup conditions;
- MATCH semantics.

Scanner MUST NOT contain strategy-specific branching like
"if strategy == TREND_PULLBACK then run ATR". Instead, requirements should
drive planning generically through `StrategyDefinition.requiredInputs()`.

Strategy selection flow:

```
Scanner determines scan scope / candidate markets
    -> StrategyApplicability evaluates each StrategyDefinition
    -> applicable StrategyDefinitions selected
    -> required semantic inputs determined from definitions
    -> capabilities / semantic values resolved
    -> each applicable Strategy evaluated
```

Current state: `ProductionIntelligencePipeline` hardcodes the observation rule.
Generalization is Story 0013 scope.

#### I-16. Strategy vs Market Intelligence

Market Data: raw/provider-normalized facts.

Market Intelligence: deterministic derived market facts (observations,
capabilities, artifacts).

Strategy: combination of those facts into setup truth.

Capability vs Semantic Input boundary:

`RequiredSemanticInput` describes WHAT a Strategy needs (the semantic
contract). Capabilities describe HOW Market Intelligence derives deterministic
facts (the implementation). Strategy MUST NOT be coupled to capability
implementation classes.

```
Strategy
    declares semantic requirement (RequiredSemanticInput)
        |
planner / resolution layer
    determines deterministic producer (capability)
        |
capability executes
    produces semantic value
        |
StrategyEvaluationContext assembled
    with required inputs
```

This separation permits multiple implementations/producers in the future
without changing Strategy semantics.

Examples:

- ATR calculation -> Market Intelligence capability;
- Spread calculation -> Market Intelligence capability;
- Liquidity proxy -> Market Intelligence capability;
- Trend strength -> Market Intelligence capability;
- "ATR acceptable for Strategy X" -> Strategy condition (NOT a capability
  threshold);
- "spread acceptable for Strategy X" -> Strategy condition (NOT a capability
  threshold).

Strategy thresholds MUST NOT be encoded into generic Market Intelligence
capabilities.

#### I-17. Strategy vs Risk

Strategy may decide: "This market setup is worth considering."

Risk decides: "Taking this trade is authorized for this account under current
constraints."

`StrategyEvaluationContext` MUST NOT contain account-risk authorization state.
Account exposure, daily loss, position sizing, risk limits, and leverage
authorization remain outside Strategy setup truth.

#### I-18. Strategy vs AI

AI may later:

- explain;
- synthesize;
- rank assist;
- contextualize;
- recommend.

AI MUST NOT become authority for deterministic MATCH truth. StrategyEvaluator
remains deterministic.

ADR-034 already establishes this boundary. ADR-035 preserves it.

#### I-19. Live vs Backtest Compatibility

The StrategyEvaluator must not know whether evaluation is live or historical.

LIVE evaluation:

```
provider/current data
    -> deterministic capabilities
    -> StrategyEvaluationContext (evaluatedAt = analysis timeline instant)
    -> StrategyEvaluator
    -> StrategyEvaluation
```

Future BACKTEST evaluation:

```
historical replay data
    -> same deterministic capabilities/semantics
    -> StrategyEvaluationContext (evaluatedAt = historical replay instant)
    -> StrategyEvaluator (same code, same interface)
    -> StrategyEvaluation
```

The evaluator receives the same types in both cases. The context is
infrastructure-free. The only difference is who assembled the context and what
`evaluatedAt` represents.

Current code already satisfies this invariant at the evaluator boundary.
Pipeline orchestration (which is live-only) does not leak into the evaluator.

`StrategyMatch.analysisExecutionId` and `StrategyMatch.observationId` are
current LIVE evidence provenance. Future backtest may introduce alternative
provenance identifiers (e.g., `backtestRunId`, `replaySourceId`) additively
without changing the core match domain.

### Target Flow

The intended pipeline after Story 0013:

``` text
ActiveScan / AnalysisExecution
    -> StrategyApplicability selection (market/context -> applicable definitions)
    -> Required capabilities executed (driven by strategy requiredInputs)
    -> Deterministic Market Intelligence outputs
    -> Generic semantic-input resolution (capability outputs -> SemanticValues)
    -> StrategyEvaluationContext assembled (generic, typed inputs)
    -> StrategyEvaluation (one per applicable strategy)
    -> MATCH -> StrategyMatch (persisted, idempotent)
    -> TradingOpportunity (strategy-agnostic creation from metadata + match)
    -> PipelineRun finalized
```

Non-MATCH outcomes:

``` text
NO_MATCH -> PipelineRun.noSignal (truthful, not a failure)
NOT_EVALUABLE -> PipelineRun.fail (missing semantic inputs)
FAILED -> PipelineRun.fail (deterministic evaluation error)
```

The generic pipeline does not contain:

```
if strategy == LEGACY_OHLC_TREND then ...
```

Strategy-specific behavior lives in:

- `StrategyEvaluator` implementations (setup logic);
- generic semantic-input resolution (mapping capability outputs to required
  semantic keys);
- declarative StrategyDefinition metadata (scenario/timeframe for display).

### Legacy Transition

The following components are classified for transition:

| Component | Classification | Rationale |
|-----------|---------------|-----------|
| `OhlcTrendObservationRule` | RETAINED_AS_FIXTURE | Still needed for Observation construction; no longer decides opportunity existence. The exception on priceChange==0 must be softened to produce a valid (direction-neutral) ObservationRuleResult rather than throwing. |
| `LegacyOhlcTrendEvaluator` | RETAINED_AS_FIXTURE | Correctly implements NO_MATCH semantics. Preserved as the bootstrap evaluator until a real validated strategy replaces it. |
| `ObservationBuilder` | GENERALIZED | Must accept any `ObservationConsolidationRule`, not be tied to OhlcTrendObservationRule. Already generic in signature; coupling is in the pipeline call site. |
| `BuiltinStrategies` | GENERALIZED | Must support multiple strategy definitions. `all()` returns a list; new strategies are added as new methods or configuration. |
| `LiveStrategyEvaluationRunner` | GENERALIZED | Must expose a generic `evaluate(StrategyDefinition, StrategyEvaluationContext)` path. The legacy-specific method may be retained as a convenience but must not be the only path. |
| `StrategyEvaluationContextFactory` | REPLACED_BY_GENERIC | Strategy-specific factory methods (e.g., `fromOhlcTrendValues`) are replaced by generic semantic-input resolution driven by `StrategyDefinition.requiredInputs()`. |
| `StrategyMatchOpportunityFactory` | GENERALIZED | `requireBootstrap()` removed. Scenario and timeframe derived from declarative StrategyDefinition metadata. |
| `ShadowStrategyParityMonitor` | DEPRECATED_AFTER_PARITY_PROOF | Retained during Story 0013 to prove that generic Strategy evaluation preserves expected legacy semantics. Removed only after Story 0013 acceptance demonstrates the generic path correctly replaces bootstrap decision semantics. Not permanent architecture. |

No component is removed in this ADR. All transitions are additive or
behavior-preserving generalizations.

### Historical Truth Compatibility

Existing persisted `StrategyMatch` and `TradingOpportunity` records remain valid:

- StrategyMatch stores exact strategy identity/version; a retired or evolved
  strategy does not retroactively change historical matches.
- TradingOpportunity stores match reference and lineage; historical opportunity
  lineage is preserved.
- No data migration is required. New generalization code works alongside
  existing records.
- The bootstrap legacy strategy continues to produce matches and opportunities
  with identical semantics.

### Migration Required

NO. Architectural changes are additive. Existing behavior is preserved.

### Consequences

Positive:

- StrategyEvaluator is the sole, verifiable authority for setup truth.
- NO_MATCH becomes a normal, first-class pipeline outcome instead of being
  suppressed by observation exceptions.
- A second test Strategy can flow through the pipeline without changing generic
  orchestration code.
- Live and future backtest reuse the same evaluator boundary.
- Opportunity creation is decoupled from bootstrap strategy identity.
- Observation remains reusable by multiple strategies.
- The pipeline becomes genuinely strategy-agnostic.
- StrategyApplicability provides pre-evaluation filtering without adding a new
  evaluation status.

Negative:

- Additional abstraction in the pipeline orchestration (generic context
  assembly, generic opportunity mapping).
- StrategyDefinition may need minimal declarative display metadata for
  opportunity construction (scenario classification).
- ObservationBuilder softening of the priceChange==0 exception changes
  Observation behavior slightly (the observation still exists but may be
  direction-neutral).

### Alternatives Considered

#### Option A — Replace Observation with StrategyEvaluationContext

Remove Observation entirely; StrategyEvaluationContext replaces it.

Rejected: Observation serves a different purpose (deterministic market state
record reusable by many strategies and by AI). Observation is upstream
knowledge; StrategyEvaluationContext is strategy-facing semantic input.
Collapsing them would lose reusability and blur the knowledge/decision
boundary.

#### Option B — Keep pipeline coupled to bootstrap strategy

Preserve the hardcoded OhlcTrendObservationRule path and add new strategies
later.

Rejected: this prevents any second strategy from flowing through the pipeline
without custom orchestration, which is the core problem ADR-035 must solve.

#### Option C — Giant universal StrategyEvaluationContext

A single context containing every possible future indicator (ATR, spread,
RSI, volume, liquidity, ...).

Rejected: over-modeling, coupling to specific indicators, evolving into a
God DTO. The current typed-key approach (`RequiredSemanticInput` +
`SemanticValue`) is more evolvable.

#### Option D — Untyped Map<String,Object> for context inputs

Replace typed `SemanticValue` with a raw map.

Rejected: loses type safety, makes evaluator code fragile, removes the
benefit of `SemanticInputType` categorization.

#### Option E — Strategy-specific context factory methods as extension

Add `fromOhlcTrendValues(...)`, `fromTrendPullbackValues(...)`,
`fromBreakoutValues(...)` etc. as the generic extension mechanism.

Rejected: merely moves strategy coupling into the factory. The generic
infrastructure must not need to know concrete Strategy IDs. Extension should
be through new `RequiredSemanticInput` keys and generic semantic-input
resolution, not strategy-specific factory methods.

### Security and Risk Considerations

- `StrategyEvaluationContext` MUST NOT contain account-risk authorization
  state. Risk evaluation remains a separate domain concern.
- StrategyEvaluator MUST NOT call provider APIs or broker services.
- StrategyEvaluator MUST NOT access wall-clock time.
- No new secrets, credentials, or authorization bypasses are introduced.
- Historical StrategyMatch truth is immutable; no retroactive mutation is
  possible through the generalization.

### Testing Implications

Story 0013 must verify these architectural properties:

1. A Strategy can return NO_MATCH without pipeline failure.
2. Missing required semantic input produces NOT_EVALUABLE.
3. Deterministic evaluation error produces FAILED.
4. Generic pipeline does not inspect concrete Strategy IDs.
5. A second fake/test StrategyEvaluator can flow through the pipeline without
   changing generic orchestration code.
6. Same StrategyEvaluationContext + same Strategy version produces the same
   StrategyEvaluation.
7. StrategyEvaluator does not call provider APIs.
8. StrategyEvaluator does not call current wall-clock time directly.
9. StrategyMatch persists exact Strategy identity/version.
10. Opportunity creation works without bootstrap-specific branching.
11. No Risk/Broker side effects are introduced.

### Follow-up Stories

#### Story 0013: Strategy-Agnostic Evaluation Pipeline

Recommended title: "Strategy-Agnostic Evaluation Pipeline"

Primary objective: Remove remaining bootstrap coupling so multiple deterministic
Strategies can flow through the same pipeline without strategy-specific
orchestration.

Expected scope:

- Generic Strategy evaluation entry point in `LiveStrategyEvaluationRunner`;
- Generic semantic-input resolution replacing strategy-specific context factory
  methods (driven by `StrategyDefinition.requiredInputs()` and capability
  outputs);
- `StrategyApplicability`-based strategy selection in the pipeline;
- `OhlcTrendObservationRule` softened to not throw on priceChange==0;
- `ProductionIntelligencePipeline` generalized to use generic evaluation paths;
- `requireBootstrap()` removed from `StrategyMatchOpportunityFactory`;
- Declarative strategy metadata for opportunity display (minimum viable);
- `ShadowStrategyParityMonitor` retained until parity proof;
- Second fake Strategy architectural test proving generic pipeline works.

Explicit non-goals:

- First real V1 trading Strategy;
- ATR implementation unless already required infrastructure;
- New trading thresholds;
- Ranking;
- Backtesting engine;
- AI;
- Risk changes;
- Broker changes;
- Automated execution;
- Unrelated Market Data work.

#### Story 0014: First Actionable V1 Strategy

Documented but not created. May introduce deterministic capabilities such as:

- trend strength;
- ATR / volatility;
- spread quality;
- liquidity proxy;
- multi-timeframe context.

depending on the product decision. ADR-035 does not prescribe trading
thresholds or strategy parameters.
