# ADR-053 - Provider-Neutral Market Identity and Multi-Product Adapters

## Status

Accepted for Story 0096 implementation.

## Date

2026-10-14

## Context

Trading OS Market Data previously used one `Market.symbol` value both as the
canonical Trading OS instrument identity and as the provider request symbol.
That representation was sufficient for the existing Kraken Spot integration,
but Kraken Futures uses contract identifiers such as `PF_XBTUSD` while the
provider-neutral market identity is the pair `BTC/USD`.

Kraken also exposes multiple product families through separate APIs. Spot and
perpetual instruments may share a canonical pair while requiring different
discovery sources, ticker sources, and provider identifiers.

The product identity already established by ADR-051 is:

```text
provider + canonical symbol + productType
```

The adapter therefore needs to retain provider request identity without leaking
provider-specific contract codes into Trading Core.

## Decision

Market Data `Market` SHALL retain two distinct symbol concepts:

- `symbol`: the provider-neutral canonical symbol used by public contracts and
  Trading Core workflows;
- `providerSymbol`: the provider request identifier used only at the adapter
  boundary.

`providerSymbol` is generic Market Data metadata. It is not a Kraken-specific
field or table, and it does not participate in canonical Market identity.

Provider adapters MAY aggregate multiple product-specific sources behind one
provider-neutral `MarketDataProvider` port. Routing SHALL use the canonical
Market product identity, not display symbol alone.

For a market request:

```text
provider + productType + providerSymbol
        -> provider-specific source
        -> generic Market/TickerEvent/Snapshot contract
```

The public Market API continues to expose canonical `symbol`, `provider`, and
`productType`. Provider-specific request symbols remain internal unless a
future explicit contract requires their exposure.

## Consequences

- Spot and derivative markets with the same canonical pair can coexist without
  provider request ambiguity.
- Trading Core does not need Kraken contract-code knowledge.
- A provider adapter may use separate discovery and ticker APIs for different
  product families without creating provider-specific domain abstractions.
- Existing Spot rows require a provider-symbol backfill during migration.
- New provider integrations should map canonical and provider symbols at their
  own adapter boundary.
- Product-aware ticker routing becomes a required adapter responsibility.

## Constraints

- `provider + canonical symbol + productType` remains the persistence identity.
- Provider-specific product names, contract tags, and endpoint details must not
  leak into Trading Core or generic Market Data APIs.
- A provider product must not be mapped to a canonical product type unless its
  semantics are verified.
- Existing Spot behavior must remain unchanged.
