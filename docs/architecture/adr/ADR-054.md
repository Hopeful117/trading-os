## Context

PAPER settlement currently mutates Account and Trade state inside the outer
execution transaction, flushes those changes, and directly invokes Challenge
reevaluation through a `REQUIRES_NEW` transaction. The new transaction can wait
on rows still locked by the suspended execution transaction. The execution
transaction cannot commit while it waits, so a valid PAPER execution can fail
to complete indefinitely.

Challenge reevaluation reloads persisted Account state and must not derive
durable Challenge progression from a settlement that later rolls back.

## Decision

PAPER settlement SHALL enqueue a durable Challenge reevaluation request in the
same database transaction as the Account, Trade, execution lifecycle, and
settlement mutations. The request is therefore rolled back with the settlement
when execution fails.

Challenge reevaluation SHALL be delivered only after the settlement
transaction commits. Delivery runs in an independent transaction and retains
the existing `PESSIMISTIC_WRITE` Challenge locking.

The durable request SHALL support:

- idempotency for one settlement trigger;
- claim state and lease expiry for concurrent workers;
- bounded retry with a terminal failure state and the last failure recorded;
- successful completion state;
- scheduler-driven recovery when immediate delivery is unavailable;
- lease renewal while a delivery is still executing;
- retention cleanup for delivered requests.

An immediate post-commit delivery attempt MAY reduce visible latency, but it is
not authoritative. The durable scheduled retry remains authoritative, and the
execution request must not wait for Challenge reevaluation to complete.

Challenge reevaluation failure SHALL not roll back an already committed PAPER
settlement. It SHALL leave the durable request pending for retry and expose the
failure through existing application logging/metrics and persisted request
state.

The existing Challenge `PESSIMISTIC_WRITE` lock SHALL remain unchanged.

## Consequences

- A rolled-back settlement cannot leave a Challenge reevaluation request.
- A committed settlement is not blocked by Challenge row locks.
- Challenge progression becomes explicitly eventually consistent with the
  committed settlement.
- A transient reevaluation failure becomes recoverable instead of being only a
  swallowed log message.
- Duplicate scheduler and immediate-delivery attempts are serialized by the
  request claim and Challenge lock; settlement itself is never duplicated.
- A delivery lease is renewed while reevaluation is running, preventing an
  active long-running delivery from being reclaimed by another worker.
- After the configured maximum number of attempts, the request becomes
  terminally failed and is no longer scheduled.
- Delivered requests are retained for a bounded period and then deleted;
  account deletion cascades to associated outbox requests.
- A database migration and PostgreSQL concurrency coverage are required.

## Rejected Alternatives

Changing Challenge reevaluation to `REQUIRED` would avoid suspending the outer
transaction, but would make Challenge progression part of settlement atomicity
and would keep execution completion coupled to Challenge evaluation. It does
not satisfy the selected non-blocking post-commit consistency model.

Removing or weakening `PESSIMISTIC_WRITE`, increasing timeouts, swallowing the
failure without durable state, or performing direct database mutation are not
acceptable solutions.
