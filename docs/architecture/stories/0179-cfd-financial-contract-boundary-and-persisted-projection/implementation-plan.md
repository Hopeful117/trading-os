# Implementation Plan - Story 0179

## Status

`READY_FOR_HUMAN_APPROVAL`

This plan is based on the approved Repository Analysis, Story 0179, ADR-081,
ADR-082, ADR-045, ADR-042, ADR-043, and ADR-051. It does not authorize
implementation until this plan receives explicit human approval.

## Implementation Strategy

Implement the contract boundary in four controlled layers:

```text
Market Data configuration and normalization
    -> Market Data persistence and API
    -> Trading Core resolution and provider-neutral validation
    -> Trading Core CFD Trade snapshot persistence
```

The implementation will first reconcile the existing uncommitted changes with
this plan. No existing user changes will be discarded. Changes that conflict
with the approved Story or ADRs will be corrected only within this Story's
scope.

## 1. Define The Authoritative Contract Source

Use Market Data as the authoritative source for canonical financial metadata.

For the first implementation:

- contract multiplier is supplied by explicit Market Data configuration or a
  reviewed Market Data registry entry;
- contract source version is an explicit positive configuration/registry value;
- contract source identity is a provider-neutral identifier generated by Market
  Data, such as a canonical instrument contract key, never a cTrader symbol ID
  or provider payload field;
- contract observation time is assigned by Market Data when the normalized
  contract is materialized;
- missing multiplier, source version, quantity unit, constraints, or provenance
  leaves the CFD contract unavailable and causes the consuming path to fail
  closed;
- no multiplier is inferred from symbols, provider names, account environment,
  execution mode, leverage, or quantity values.

Provider-specific cTrader maps may remain configuration inputs inside the cTrader
adapter, but only the normalized provider-neutral contract crosses the Market
Data API.

## 2. Market Data Changes

### Model And Persistence

- Extend the persisted market representation with the normalized contract facts
  not already represented by `Market` and `MarketConstraints`.
- Keep the fields nullable for historical SPOT and incomplete legacy markets.
- Add an additive Flyway migration under `market-data`.
- Add all-or-none database constraints for the contract metadata group.
- Do not backfill historical markets in this Story.
- Ensure the schema accepts existing rows and remains compatible with
  `hibernate.ddl-auto=validate`.

### Provider Adapter

- Extend cTrader configuration with explicit multiplier and source-version
  inputs for supported CFD symbols.
- Validate positive decimal multiplier and positive source version.
- Normalize cTrader volume constraints into canonical underlying units as Story
  0178 already requires.
- Materialize complete contract metadata only when all required facts exist.
- Keep cTrader transport types, provider IDs, and volume semantics inside the
  adapter.
- Do not reject or classify a symbol based on the execution environment.

### API

- Extend the existing provider-neutral `MarketResponse` with contract metadata.
- Preserve existing SPOT and `LINEAR_PERPETUAL` response compatibility.
- Do not expose cTrader payloads or cTrader-specific identifiers.
- Add mapper tests proving complete metadata propagation and absent metadata for
  incomplete contracts.

## 3. Trading Core Changes

### Boundary DTO And Resolver

- Extend the Trading Core `MarketResponse` DTO with the provider-neutral fields.
- Update `InstrumentFinancialContractMapper` to consume the complete Market Data
  response without requiring a caller to invent the multiplier or provenance.
- Add a resolver that:
  - resolves exactly one canonical market for the instrument;
  - distinguishes confirmed non-CFD from missing/ambiguous identity;
  - rejects incomplete CFD metadata;
  - validates product type, currencies, quantity unit, precision, constraints,
    multiplier, and provenance through `InstrumentFinancialContract`.
- Return an explicit unavailable/fail-closed outcome rather than silently
  returning a legacy trade projection for an unresolved CFD.

### Trade Projection

- Persist a complete provider-neutral contract snapshot on CFD `Trade` rows.
- Add an explicit entity/application mapping method that copies every validated
  contract field, including:
  - product type;
  - base and quote currencies;
  - quantity unit;
  - contract multiplier;
  - price and quantity precision;
  - minimum quantity and increment;
  - neutral source identity, source version, and observation timestamp.
- Keep legacy rows nullable and do not backfill historical trades.
- Enforce all-or-none contract facts for newly persisted projections.
- Keep valuation-source fields limited to the approved projection scope; do not
  implement valuation orchestration or dynamic mark persistence here.

### Synchronization Integration

- Apply the resolver only at the provider-neutral LIVE position synchronization
  boundary where a Market Data market is identified as CFD.
- If the market is confirmed SPOT or `LINEAR_PERPETUAL`, preserve existing
  synchronization behavior.
- If CFD metadata is missing, ambiguous, or incomplete, abort or quarantine the
  affected synchronization operation rather than persisting an incomplete CFD
  trade.
- Preserve Broker Service authority for current LIVE position and balance facts.
- Do not add Broker Service calls to PAPER execution or settlement.

## 4. Explicitly Unchanged Areas

- `SettlementCompatibilityPolicy` remains unchanged.
- `CASH + CFD` and `INVENTORY + CFD` remain rejected.
- `PaperSettlementService` does not gain CFD settlement behavior.
- Risk formulas, margin semantics, financing, commissions, liquidation, and
  challenge rules remain unchanged.
- No universal `Position` aggregate is introduced.
- No broker order placement, cancellation, or external mutation is performed.
- `CTRADER_SAFETY_EXECUTION_ENABLED=false` remains the default.

## 5. Test Plan

### Market Data

- Configuration validation for missing, invalid, zero, and negative multipliers
  and source versions.
- cTrader adapter test with complete explicit CFD metadata.
- cTrader adapter test proving incomplete metadata does not create a partial
  persisted contract.
- Provider-neutral `MarketResponse` mapper test.
- Fresh-install migration test for new columns and constraints.
- Upgrade migration test preserving legacy markets.
- Negative migration test rejecting partial contract facts.

### Trading Core

- Resolver success test with complete provider-neutral metadata.
- Resolver failure tests for missing market, ambiguous market, missing
  multiplier, missing provenance, unsupported quantity unit, and invalid
  constraints.
- Trade snapshot mapping test covering every persisted field.
- JPA persistence/reload test for complete CFD contract facts.
- Legacy SPOT and `LINEAR_PERPETUAL` persistence regression tests.
- Synchronization test proving CFD population and missing-contract fail-closed
  behavior.
- Compatibility tests proving all existing CFD combinations remain rejected.
- Fresh-install and upgrade migration tests for Trading Core constraints.

## 6. Validation Sequence

1. Run focused Market Data tests.
2. Run focused Trading Core tests.
3. Run both module compilation checks.
4. Run migration tests with PostgreSQL where available.
5. Run `git diff --check`.
6. Review the complete diff against Story 0179 and all related ADRs.
7. Run broader module suites when the environment permits; report unavailable
   PostgreSQL/container checks explicitly.

## 7. Risks And Mitigations

| Risk | Mitigation |
|---|---|
| No authoritative multiplier available | Keep contract unavailable and fail closed; do not infer |
| Provider-specific provenance leakage | Generate and persist only neutral Market Data source identity |
| Missing Market Data during LIVE synchronization | Abort/quarantine affected synchronization rather than persist incomplete CFD facts |
| Legacy rows lack contract metadata | Nullable additive fields; no historical backfill |
| Existing SPOT/LINEAR behavior changes | Conditional CFD-only integration and regression tests |
| Scope expands into settlement | Keep compatibility and settlement code unchanged |
| Migration incompatibility | Fresh-install, upgrade, PostgreSQL constraint, and JPA validation tests |

## 8. Expected Deliverables

- Market Data contract metadata model, configuration, mapper, API, migration, and
  tests.
- Trading Core resolver, DTO mapping, Trade snapshot mapping, synchronization
  integration, migration, and tests.
- Updated implementation report with validation evidence and documentation
  reconciliation outcome.

## 9. Human Decisions Required Before Implementation

No additional product decision is required if the following plan constraints are
accepted:

- Market Data configuration/registry is the source of the explicit multiplier
  and source version.
- The boundary source identity is provider-neutral and generated by Market Data.
- Missing CFD contract facts fail closed during synchronization.
- Existing uncommitted changes will be reconciled to this plan before further
  implementation.
