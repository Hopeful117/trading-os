# ADR-013 — Frontend Architecture

* **Status:** Accepted
* **Date:** 2026-07-23

## Context

Trading OS provides a rich client application responsible for presenting market information, account status, AI recommendations and trading workflows.

The frontend must remain responsive while consuming data from multiple backend services through the Gateway.

As the application evolves, maintaining consistency in state management, navigation and user interactions becomes increasingly important.

The frontend should therefore follow a consistent architectural style focused on reactivity and business workflows.

---

## Decision

Trading OS adopts a reactive Angular architecture.

The frontend is responsible for:

* presenting information;
* orchestrating user interactions;
* displaying realtime data;
* guiding trading workflows.

Business logic remains server-side.

---

## Responsibilities

The frontend owns:

* page composition;
* user interactions;
* form validation;
* realtime visualization;
* local UI state.

The frontend must **not** duplicate deterministic business logic implemented by backend services.

---

## Reactive Programming

Angular applications should prefer reactive programming patterns.

Observable streams are considered the default mechanism for:

* HTTP responses;
* realtime updates;
* UI refreshes;
* asynchronous workflows.

The `async` pipe should be preferred whenever possible.

Manual subscriptions should remain exceptional.

---

## Navigation

Trading OS follows a workflow-oriented navigation.

Typical examples include:

```
Dashboard

↓

Markets

↓

Market Detail

↓

Trade Validation
```

Each page has a clearly identified business responsibility.

---

## PRG Pattern

Operations modifying backend state should follow the Post/Redirect/Get pattern whenever appropriate.

Typical examples include:

* account synchronization;
* user registration;
* future trade creation.

Objectives:

* prevent duplicate submissions;
* refresh displayed state;
* improve navigation consistency.

---

## Page Responsibilities

### Dashboard

Provides a high-level overview of:

* accounts;
* positions;
* risks;
* alerts;
* opportunities.

---

### Markets

Acts as a searchable market catalog.

Responsibilities include:

* searching markets;
* filtering markets;
* selecting a market.

It is not responsible for market analysis.

---

### Market Detail

Displays detailed information about a single market.

Future responsibilities include:

* realtime prices;
* charts;
* market metadata;
* news;
* AI recommendations;
* trade preparation.

---

### Scanner

Provides market opportunity discovery.

It displays the outputs of the Passive and Active Scanners rather than executing market analysis itself.

---

## Communication

The frontend communicates exclusively through the Gateway.

Backend services remain hidden from frontend applications.

Realtime updates should use dedicated streaming mechanisms when appropriate.

---

## UI Principles

Trading OS adopts a professional dashboard aesthetic.

Guidelines include:

* dark theme;
* clean typography;
* restrained accent colors;
* consistent spacing;
* reusable UI components;
* information density without visual overload.

The interface should prioritize readability during trading sessions.

---

## Consequences

Advantages:

* consistent architecture;
* predictable UI behaviour;
* easier maintenance;
* scalable component hierarchy;
* improved user experience.

Trade-offs:

* increased reliance on reactive programming;
* more structured page responsibilities.

These trade-offs are accepted.

---

## Alternatives Considered

### Fat Frontend

Rejected.

Business decisions belong to backend services.

---

### Manual State Synchronization

Rejected.

Reactive data flows provide a simpler and more maintainable architecture.
