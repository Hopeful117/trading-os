# ADR-022 — Gestion, fraîcheur et réutilisation des artefacts d’intelligence

* **Statut :** Accepted
* **Date :** 2026-07-29
* **Décideurs :** Équipe Trading OS
* **Contexte architectural :** Market Intelligence
* **ADR liés :**

    * ADR-020 — Modèle d’analyse et d’intelligence de marché
    * ADR-021 — Orchestration des analyses et intégration avec l’AI Engine

---

## 1. Contexte

Market Intelligence construit des analyses à partir de plusieurs sources :

* Market Data Service ;
* Trading Core ;
* Broker Service ;
* futur News Service ;
* analyses déterministes ;
* résultats produits par l’AI Engine ;
* observations d’intelligence déjà validées ou encore actives.

Une analyse peut nécessiter des opérations coûteuses :

* récupération de données distantes ;
* normalisation de données ;
* construction de fragments de contexte ;
* exécution d’algorithmes déterministes ;
* appels à l’AI Engine ;
* consolidation de plusieurs résultats.

Recalculer systématiquement chaque élément serait inefficace et augmenterait :

* la latence ;
* la consommation de ressources ;
* le nombre d’appels externes ;
* les coûts liés aux modèles d’intelligence artificielle ;
* la charge sur les services producteurs.

À l’inverse, une réutilisation incontrôlée de données ou de résultats précédents pourrait produire des analyses :

* obsolètes ;
* incohérentes ;
* non reproductibles ;
* non traçables ;
* incorrectement partagées entre utilisateurs ou comptes ;
* dangereuses dans un contexte de décision de trading.

Le système doit donc gérer la réutilisation comme une décision métier explicite, et non comme une simple optimisation technique basée sur Redis, Caffeine ou un TTL.

---

## 2. Décision

Trading OS introduit un modèle métier de gestion des artefacts d’intelligence.

Un artefact représente un résultat réutilisable produit ou consommé lors de la construction d’une analyse.

Exemples :

* contribution normalisée ;
* fragment de contexte ;
* synthèse de marché ;
* résumé de risque ;
* résultat d’une capacité déterministe ;
* résultat produit par l’AI Engine.

La gestion des artefacts repose sur les concepts suivants :

* propriété ;
* identité ;
* périmètre ;
* provenance ;
* dépendances ;
* fraîcheur ;
* invalidation ;
* résolution ;
* réutilisation ;
* recalcul.

Le cache technique reste un détail d’infrastructure.

---

# 3. Propriété des caches et des artefacts

## 3.1 Modèle hybride

La propriété des caches suit un modèle hybride.

### Services producteurs

Chaque service producteur reste propriétaire :

* de ses données primaires ;
* de leur cycle de vie ;
* de leur cache primaire éventuel ;
* de leur version logique ;
* des événements signalant leur modification ou leur invalidation.

Exemples :

* Market Data Service possède les données de marché ;
* Trading Core possède les règles de risque et les données métier de trading ;
* Broker Service possède les données synchronisées provenant du broker ;
* News Service possédera les actualités et événements économiques collectés.

### Market Intelligence

Market Intelligence est propriétaire des artefacts qu’il produit ou dérive :

* contributions normalisées ;
* fragments de contexte ;
* résumés consolidés ;
* résultats de capacités déterministes ;
* résultats IA réutilisables ;
* métadonnées de provenance ;
* relations de dépendance entre artefacts.

Market Intelligence ne devient pas propriétaire des données primaires des autres services.

---

## 3.2 Règle de responsabilité

> Le service propriétaire d’une donnée primaire reste responsable de sa vérité métier et des événements indiquant son évolution.

> Market Intelligence est responsable de la validité, de la fraîcheur et de la réutilisation des artefacts qu’il construit à partir de ces données.

---

# 4. Catégories d’artefacts réutilisables

## 4.1 Contributions normalisées

Les réponses provenant des services producteurs peuvent être transformées en contributions normalisées.

Exemples :

* `MarketSummary`
* `OrderBookSummary`
* `RiskSummary`
* `NewsSummary`
* `ActiveObservationSummary`

Ces objets sont adaptés au domaine de Market Intelligence.

Ils ne doivent pas être de simples copies des contrats externes ou des réponses brutes des fournisseurs.

Les jeux de données bruts et volumineux ne doivent pas être dupliqués sans nécessité métier démontrée.

---

## 4.2 Fragments de contexte

Le système peut réutiliser des parties ciblées d’un futur `IntelligenceContext`.

Exemples :

* `MarketContextFragment`
* `OrderFlowContextFragment`
* `RiskContextFragment`
* `NewsContextFragment`
* `ObservationContextFragment`

Le système ne met pas en cache un `IntelligenceContext` complet par défaut.

L’orchestrateur reconstruit le contexte final à partir des fragments compatibles avec l’exécution en cours.

Cette approche permet :

* une invalidation ciblée ;
* une reconstruction partielle ;
* une meilleure isolation des données ;
* une traçabilité plus précise ;
* une adaptation aux capacités réellement demandées.

---

## 4.3 Résultats déterministes

Les résultats de capacités déterministes sont de bons candidats à la réutilisation.

Exemples :

* analyse de volatilité ;
* détection de liquidité ;
* analyse de structure de marché ;
* détection d’imbalance ;
* analyse d’absorption ;
* calcul d’indicateurs ;
* classification déterministe d’un régime de marché.

La réutilisation est autorisée uniquement lorsque sont compatibles :

* la capacité ;
* sa version logique ;
* les paramètres ;
* les données d’entrée ;
* le périmètre ;
* la politique de fraîcheur ;
* les exigences de l’exécution.

---

## 4.4 Résultats produits par l’AI Engine

Un résultat IA peut être réutilisé, mais selon des règles plus strictes qu’un résultat déterministe.

La compatibilité doit notamment prendre en compte :

* la capacité IA ;
* la version de la capacité ;
* l’empreinte exacte du contexte transmis ;
* la version du prompt ou des instructions ;
* le modèle ou sa classe de compatibilité ;
* les paramètres d’inférence significatifs ;
* les outils autorisés ;
* le périmètre de sécurité ;
* la politique d’exécution ;
* la fraîcheur du résultat.

La réutilisation d’un résultat IA doit être explicite dans la provenance de l’exécution.

Le système doit pouvoir indiquer :

> Résultat IA réutilisé depuis une exécution précédente.

Aucun résultat IA n’est réutilisé silencieusement.

---

## 4.5 IntelligenceObservation

Une `IntelligenceObservation` ne constitue pas une simple entrée de cache.

Elle représente une information métier produite par la consolidation et fait partie de la mémoire d’intelligence du système.

Une observation peut être consultée comme contexte historique ou actif, mais elle possède son propre cycle de vie métier.

Une nouvelle exécution peut produire une nouvelle observation même lorsqu’elle réutilise certains artefacts précédents.

---

# 5. Fraîcheur

## 5.1 Concept transversal

La fraîcheur est un concept métier transversal de Trading OS.

Elle est indépendante :

* de Redis ;
* de Caffeine ;
* du stockage ;
* du TTL technique ;
* de la durée de conservation physique d’une entrée.

Chaque artefact réutilisable doit exposer suffisamment de métadonnées pour évaluer sa fraîcheur.

Exemples de métadonnées :

* `producedAt`
* `validUntil`
* `sourceVersion`
* `producerVersion`
* `provenance`
* `freshnessStatus`

---

## 5.2 États de fraîcheur

Les états suivants sont retenus :

```text
FRESH
STALE
EXPIRED
INVALIDATED
UNKNOWN
```

### FRESH

L’artefact satisfait pleinement les exigences de fraîcheur de l’usage demandé.

### STALE

L’artefact n’est plus optimal, mais peut éventuellement être réutilisé lorsque la politique de l’analyse l’autorise explicitement.

### EXPIRED

La période de validité métier est dépassée.

L’artefact ne doit pas être réutilisé comme une donnée valide.

### INVALIDATED

Un événement ou une dépendance a rendu l’artefact incompatible avec l’état actuel du système.

### UNKNOWN

Le système ne dispose pas de suffisamment d’informations fiables pour déterminer la fraîcheur.

`UNKNOWN` ne doit jamais être traité implicitement comme `FRESH`.

---

## 5.3 TTL et fraîcheur

Le TTL technique ne constitue pas une preuve de fraîcheur.

Exemple :

```text
TTL Redis : 10 minutes
Validité métier : 3 secondes
```

Une entrée peut donc encore exister dans le cache tout en étant `EXPIRED` ou `INVALIDATED`.

Inversement, un artefact peut être conservé après invalidation :

* pour l’audit ;
* pour la comparaison ;
* pour une exécution déjà engagée ;
* pour la traçabilité ;
* jusqu’à son éviction technique.

---

## 5.4 FreshnessPolicy

La réutilisation est évaluée à l’aide d’une `FreshnessPolicy`.

Une politique peut notamment préciser :

* l’âge maximal accepté ;
* la tolérance au statut `STALE` ;
* les événements déclenchant une invalidation ;
* l’utilisation autorisée en mode passif ;
* l’utilisation autorisée en mode actif ;
* le comportement en cas de fraîcheur inconnue ;
* le caractère critique ou non de l’artefact.

La fraîcheur dépend de l’usage demandé.

Le système ne doit pas se limiter à une méthode universelle comme :

```java
boolean isFresh();
```

Il doit évaluer la fraîcheur par rapport à une exigence :

```java
FreshnessAssessment assess(
    ArtifactFreshness freshness,
    ArtifactRequirement requirement,
    AnalysisExecutionPolicy executionPolicy
);
```

---

## 5.5 Mode passif et mode actif

Les exigences de fraîcheur peuvent varier selon le mode d’analyse.

### Mode passif

Le scanner passif peut accepter temporairement certains artefacts `STALE` lorsqu’ils servent à :

* maintenir une conscience générale du marché ;
* détecter des changements non critiques ;
* réduire des recalculs coûteux ;
* alimenter une surveillance à faible priorité.

Cette réutilisation doit être traçable.

### Mode actif

Le scanner actif applique des exigences plus strictes, en particulier pour :

* les décisions d’entrée ;
* le timing ;
* les règles de risque ;
* les prix exécutables ;
* les positions et soldes ;
* les données très volatiles.

Certaines capacités peuvent exiger exclusivement des données `FRESH`.

---

# 6. Invalidation

## 6.1 Séparation entre expiration et invalidation

L’expiration temporelle et l’invalidation sont deux concepts différents.

Une donnée devient `EXPIRED` lorsque sa période de validité est dépassée.

Une donnée devient `INVALIDATED` lorsqu’un événement métier ou une dépendance la rend incompatible, indépendamment de son âge.

---

## 6.2 Invalidation temporelle

L’invalidation temporelle résulte de l’écoulement du temps.

Exemple :

```text
OrderBookSummary
producedAt = 10:00:00
validUntil = 10:00:03
```

Après `10:00:03`, l’artefact devient `EXPIRED`.

---

## 6.3 Invalidation événementielle

Un événement métier peut invalider immédiatement un artefact encore présent et non expiré.

Exemples :

```text
PositionChanged
→ RiskSummary INVALIDATED
```

```text
OrderExecuted
→ AccountSummary INVALIDATED
```

```text
MarketSnapshotUpdated
→ OrderBookSummary INVALIDATED
```

```text
EconomicEventReleased
→ NewsContextFragment INVALIDATED
```

Les services producteurs doivent publier ou exposer les changements nécessaires à l’invalidation de leurs données dérivées.

Le mécanisme exact de transport des événements n’est pas imposé par cet ADR.

---

## 6.4 Invalidation par dépendance

Les artefacts dérivés doivent conserver leurs dépendances logiques.

Exemple :

```text
MarketSnapshot
    ├── OrderBookSummary
    ├── RecentTradesSummary
    └── LiquidityAnalysis
```

Lorsqu’une dépendance devient invalide, les artefacts dérivés doivent adapter leur état selon leur politique.

Selon le cas, ils peuvent devenir :

* `STALE` ;
* `INVALIDATED` ;
* non réutilisables pour une catégorie spécifique d’analyse.

La propagation doit être ciblée.

Le système ne doit pas invalider globalement tous les artefacts lorsqu’une seule source évolue.

---

## 6.5 Conservation après invalidation

Une entrée invalidée n’est pas nécessairement supprimée immédiatement.

Elle peut être conservée :

* pour l’audit ;
* pour la reproductibilité ;
* pour l’historique ;
* pour une exécution ayant déjà capturé cette version ;
* pour l’analyse des changements entre deux états.

L’éviction technique et la validité métier sont deux responsabilités distinctes.

---

# 7. Identité des artefacts

## 7.1 ArtifactCacheKey

Chaque artefact cacheable est identifié par une `ArtifactCacheKey` fortement typée.

Cette clé représente l’identité métier de l’artefact.

Elle reste indépendante de la technologie de stockage.

Structure conceptuelle :

```text
ArtifactCacheKey
├── ArtifactIdentity
│   ├── artifactType
│   ├── producerId
│   └── producerVersion
├── ArtifactScope
│   ├── market
│   ├── timeframe
│   ├── user
│   ├── account
│   ├── tenant
│   ├── analysisMode
│   └── securityScope
├── parametersFingerprint
└── inputFingerprint
```

---

## 7.2 ArtifactIdentity

`ArtifactIdentity` identifie :

* le type d’artefact ;
* le producteur ou la capacité ;
* la version logique du producteur.

La version utilisée doit être une version métier.

Elle évolue lorsqu’une modification rend les anciens résultats incompatibles.

La version complète de l’application ou le hash Git du build ne doivent pas être utilisés automatiquement, car cela provoquerait des invalidations trop larges.

---

## 7.3 ArtifactScope

`ArtifactScope` définit le périmètre dans lequel l’artefact peut être réutilisé.

Ce périmètre peut inclure :

* un marché ;
* un instrument ;
* un timeframe ;
* un utilisateur ;
* un compte de trading ;
* un tenant ;
* un mode actif ou passif ;
* une classification de sécurité.

Toutes les dimensions ne sont pas obligatoires pour chaque artefact.

Exemple public :

```text
MarketSummary
EUR-USD
Timeframe 1h
PUBLIC
```

Exemple sensible :

```text
RiskContextFragment
User 42
Account 7
TRADING_SENSITIVE
```

---

## 7.4 Règle d’isolation

> Une dimension de sécurité ne doit jamais être retirée de la clé afin d’améliorer le taux de réutilisation.

Un artefact public peut être partagé entre plusieurs exécutions et plusieurs utilisateurs.

Un artefact utilisateur, compte ou tenant doit rester strictement isolé.

---

## 7.5 Empreinte des paramètres

Les paramètres influençant réellement le résultat font partie de l’identité de l’artefact.

Exemples :

* profondeur du carnet ;
* période d’un indicateur ;
* timeframe ;
* seuil d’imbalance ;
* fenêtre historique ;
* stratégie de calcul ;
* paramètres de classification.

Les paramètres doivent être :

1. sélectionnés ;
2. normalisés ;
3. ordonnés ;
4. sérialisés de manière canonique ;
5. transformés en empreinte déterministe.

Les métadonnées techniques sans influence sur le résultat ne doivent pas entrer dans la clé.

Exemples exclus :

* `traceId`
* `requestId`
* horodatage de réception technique
* identifiant du thread
* nom de l’instance applicative

---

## 7.6 Empreinte des données d’entrée

Un résultat dérivé doit identifier les données ou versions ayant servi à le produire.

Cette identité peut être obtenue à partir :

* d’un identifiant de snapshot ;
* d’un numéro de séquence ;
* d’une version logique ;
* d’une bougie clôturée ;
* d’une fenêtre temporelle ;
* d’un ensemble ordonné de versions ;
* d’une empreinte des dépendances.

Il n’est pas obligatoire de recalculer un hash sur le contenu brut complet lorsque le service producteur fournit une identité fiable de snapshot ou de version.

---

## 7.7 Temporalité

L’heure courante ne doit pas être ajoutée systématiquement dans la clé.

Une telle stratégie empêcherait presque toute réutilisation.

La temporalité doit être représentée par :

* la version de la source ;
* l’identifiant du snapshot ;
* la bougie concernée ;
* les bornes d’une fenêtre temporelle ;
* les métadonnées de fraîcheur.

---

## 7.8 ArtifactCacheKey et IdempotencyKey

`ArtifactCacheKey` et `IdempotencyKey` restent deux concepts distincts.

### IdempotencyKey

Identifie une demande d’analyse équivalente.

Elle répond à la question :

> Une exécution correspondant à cette demande existe-t-elle déjà ?

### ArtifactCacheKey

Identifie un artefact réutilisable.

Elle répond à la question :

> Un résultat compatible a-t-il déjà été produit ?

Une `AnalysisExecution` peut consommer plusieurs artefacts possédant chacun leur propre `ArtifactCacheKey`.

L’`executionId` ne doit donc pas faire partie de la clé de cache par défaut.

Il reste toutefois enregistré dans la provenance.

---

## 7.9 Résultats IA

L’identité d’un artefact IA doit être plus stricte.

Elle peut inclure :

```text
AiArtifactIdentity
├── capabilityId
├── capabilityVersion
├── contextFingerprint
├── promptVersion
├── modelCompatibilityClass
├── inferencePolicyFingerprint
├── authorizedToolsFingerprint
└── securityScope
```

La compatibilité entre modèles doit être explicite.

Par défaut, une modification du modèle ou du comportement d’inférence rend le résultat non compatible.

---

## 7.10 Sérialisation technique

Le domaine ne doit pas manipuler directement une chaîne Redis telle que :

```text
market-intelligence:btc-usd:5m:liquidity:v3:abc123
```

Un adaptateur d’infrastructure sérialise la clé métier :

```text
ArtifactCacheKey
        ↓
CacheKeySerializer
        ↓
Redis key / Caffeine key / database key
```

L’entrée stockée doit conserver ses métadonnées d’identité en plus de l’éventuelle clé hashée.

---

# 8. Résolution des artefacts

## 8.1 ArtifactResolver

Le système introduit un service métier nommé conceptuellement `ArtifactResolver`.

Sa responsabilité n’est pas de lire directement un cache.

Sa responsabilité est de fournir le meilleur artefact compatible avec le besoin d’une exécution.

Signature conceptuelle :

```java
ArtifactResolution resolve(
    ArtifactRequirement requirement,
    AnalysisExecution execution
);
```

---

## 8.2 ArtifactRequirement

Un `ArtifactRequirement` décrit ce dont une capacité ou l’orchestrateur a besoin.

Il peut notamment contenir :

* le type d’artefact ;
* le périmètre ;
* les paramètres ;
* les versions compatibles ;
* les exigences de fraîcheur ;
* le niveau de qualité attendu ;
* la classification de sécurité ;
* la politique de recalcul ;
* le caractère obligatoire ou optionnel.

---

## 8.3 ReuseDecision

L’`ArtifactResolver` peut produire différentes décisions :

```text
REUSE
REUSE_WITH_WARNING
RECALCULATE
REJECT
```

### REUSE

Un artefact compatible et suffisamment frais peut être utilisé directement.

### REUSE_WITH_WARNING

Un artefact imparfait, généralement `STALE`, peut être utilisé parce que la politique de l’exécution l’autorise.

La dégradation doit être explicite dans le résultat.

### RECALCULATE

Aucun artefact acceptable n’existe ou la politique impose un nouveau calcul.

### REJECT

L’exigence ne peut pas être satisfaite.

Exemples :

* périmètre de sécurité incompatible ;
* données obligatoires indisponibles ;
* fraîcheur inconnue interdite ;
* version non compatible ;
* recalcul impossible ;
* capacité interdite par la politique d’exécution.

---

## 8.4 ArtifactResolution

La résolution doit produire un résultat traçable.

Structure conceptuelle :

```text
ArtifactResolution
├── decision
├── artifact
├── freshnessAssessment
├── provenance
├── reused
├── recalculated
├── degradation
└── reason
```

---

# 9. Interaction avec AnalysisExecution

## 9.1 Ordre général

Le contrôle d’idempotence intervient avant la résolution des artefacts.

Flux conceptuel :

```text
Nouvelle demande
        ↓
Validation
        ↓
Calcul de l’IdempotencyKey
        ↓
Recherche d’une AnalysisExecution existante
        ↓
Exécution existante compatible ?
    ├── Oui → retourner ou rattacher l’exécution existante
    └── Non → créer une nouvelle AnalysisExecution
                    ↓
              Résolution des artefacts
                    ↓
              Exécution des capacités manquantes
                    ↓
                 Consolidation
                    ↓
        Production d’IntelligenceObservation
```

L’idempotence répond à l’identité de la demande.

Le cache intervient ensuite pour résoudre les artefacts nécessaires à l’exécution.

---

## 9.2 Granularité de réutilisation

Le cache ne doit pas être consulté uniquement au niveau global de l’analyse.

La résolution se fait principalement :

* par fragment ;
* par contribution ;
* par capacité ;
* par résultat intermédiaire.

Une exécution peut donc être hybride.

Exemple :

```text
MarketSummary            REUSED
RiskContextFragment      REUSED
LiquidityAnalysis        RECALCULATED
NewsSummary              REUSED_WITH_WARNING
AI Scenario              RECALCULATED
Consolidation            NEW
```

---

## 9.3 Exécution entièrement réutilisée

Une nouvelle `AnalysisExecution` peut exceptionnellement reconstruire son résultat à partir d’artefacts entièrement réutilisés.

Elle reste toutefois une exécution distincte lorsque :

* la demande n’est pas idempotente avec une exécution précédente ;
* le contexte de consommation diffère ;
* une nouvelle consolidation est nécessaire ;
* une nouvelle observation métier doit être produite ;
* la politique exige une nouvelle trace d’exécution.

Le fait qu’aucune capacité ne soit recalculée ne signifie pas qu’aucune nouvelle exécution n’existe.

---

## 9.4 Exécution partiellement recalculée

Une exécution peut combiner :

* artefacts réutilisés ;
* artefacts recalculés ;
* artefacts réutilisés avec avertissement ;
* capacités ignorées dans le cadre d’une dégradation contrôlée.

Le statut de l’exécution et la qualité du résultat restent distincts.

Exemple :

```text
ExecutionStatus = COMPLETED
ResultQuality = PARTIAL
```

ou :

```text
ExecutionStatus = COMPLETED
ResultQuality = DEGRADED
```

---

## 9.5 Capacité et décision de réutilisation

Les règles métier spécifiques à une capacité ne doivent pas être codées intégralement dans un orchestrateur central.

Une capacité doit pouvoir contribuer à la décision de réutilisation.

Exemples :

```java
ReuseDecision evaluateReuse(
    CachedArtifact artifact,
    ArtifactRequirement requirement,
    AnalysisExecutionPolicy executionPolicy
);
```

Une capacité de timing d’entrée peut exiger `FRESH`.

Une capacité de synthèse générale peut accepter `STALE` en mode passif.

L’orchestrateur coordonne la décision, mais ne remplace pas les règles métier de chaque capacité.

---

## 9.6 Retry

Lors d’un retry ciblé défini dans ADR-021, l’`ArtifactResolver` peut réévaluer les artefacts déjà produits.

Les capacités terminées avec succès ne doivent pas être relancées inutilement.

Un artefact peut être réutilisé lors d’un retry uniquement si :

* son identité est toujours compatible ;
* sa fraîcheur satisfait encore la politique ;
* ses dépendances n’ont pas été invalidées ;
* l’exécution n’a pas expiré ;
* la politique de retry l’autorise.

Dans le cas contraire, un recalcul ciblé est requis.

---

## 9.7 Expiration de l’exécution

Une exécution expirée ne peut pas être modifiée par des résultats tardifs.

Les artefacts produits tardivement peuvent éventuellement être conservés comme artefacts indépendants si :

* leur production est valide ;
* leur provenance est complète ;
* leur politique l’autorise ;
* ils ne sont pas rattachés rétroactivement au résultat consolidé expiré.

Toute nouvelle analyse doit créer une nouvelle `AnalysisExecution` avec une nouvelle `IdempotencyKey` lorsque le contexte précédent n’est plus valide.

---

# 10. Provenance et traçabilité

Chaque artefact doit permettre de retrouver :

* son producteur ;
* sa version ;
* ses données d’entrée ;
* ses dépendances ;
* sa date de production ;
* sa fraîcheur ;
* sa classification ;
* son périmètre ;
* l’exécution ayant produit l’artefact ;
* les exécutions l’ayant réutilisé ;
* la décision ayant autorisé la réutilisation.

Une exécution doit conserver, pour chaque exigence :

* cache hit ou miss ;
* artefact réutilisé ;
* artefact recalculé ;
* artefact rejeté ;
* raison de la décision ;
* niveau de fraîcheur ;
* éventuelle dégradation ;
* source et version.

Cette traçabilité est requise pour :

* l’audit ;
* le débogage ;
* l’observabilité ;
* l’explication des analyses ;
* l’évaluation de la qualité ;
* l’optimisation future des politiques ;
* la maîtrise des coûts liés à l’AI Engine.

---

# 11. Considérations de sécurité

La réutilisation ne doit jamais contourner les règles de sécurité définies par ADR-021.

Un artefact doit être réutilisé uniquement lorsque :

* le périmètre de sécurité est compatible ;
* la classification autorise le consommateur ;
* les données utilisateur ou compte sont correctement isolées ;
* le contexte transmis à l’AI Engine respecte les règles de classification ;
* la provenance n’indique aucune source interdite.

Un résultat public ne doit pas contenir indirectement une dépendance privée.

La classification finale d’un artefact dérivé doit être au moins aussi restrictive que la classification la plus sensible de ses dépendances.

---

# 12. Stockage et infrastructure

Cet ADR ne choisit aucune technologie de cache.

L’implémentation peut ultérieurement utiliser :

* Caffeine ;
* Redis ;
* une base relationnelle ;
* une base spécialisée ;
* une combinaison de plusieurs niveaux de stockage.

Le domaine ne doit dépendre d’aucune API spécifique à ces technologies.

Interfaces conceptuelles possibles :

```java
public interface ArtifactStore {
    Optional<StoredArtifact> find(ArtifactCacheKey key);

    void save(StoredArtifact artifact);

    void invalidate(ArtifactCacheKey key);

    void evict(ArtifactCacheKey key);
}
```

```java
public interface ArtifactDependencyRegistry {
    void register(ArtifactDependency dependency);

    Set<ArtifactIdentity> findDependents(ArtifactIdentity source);
}
```

```java
public interface ArtifactResolver {
    ArtifactResolution resolve(
        ArtifactRequirement requirement,
        AnalysisExecution execution
    );
}
```

Ces interfaces sont indicatives et ne constituent pas une obligation d’implémentation immédiate.

---

# 13. Alternatives rejetées

## 13.1 Aucun cache dans Market Intelligence

Cette alternative obligerait Market Intelligence à recalculer chaque analyse et ne permettrait pas de réutiliser efficacement les artefacts dérivés.

Elle est rejetée pour des raisons de performance, de coût et de latence.

---

## 13.2 Centralisation de toutes les données dans Market Intelligence

Cette alternative ferait de Market Intelligence le propriétaire implicite de données appartenant à d’autres services.

Elle introduirait :

* une duplication excessive ;
* des problèmes de synchronisation ;
* un couplage fort ;
* une confusion de responsabilités.

Elle est rejetée.

---

## 13.3 Cache complet de l’IntelligenceContext

Cette alternative rendrait l’invalidation trop large et compliquerait la réutilisation partielle.

Elle est rejetée comme stratégie par défaut.

---

## 13.4 TTL comme unique règle de validité

Le TTL ne représente pas la validité métier.

Il ne permet pas de réagir correctement aux événements ou aux dépendances.

Cette alternative est rejetée.

---

## 13.5 Suppression immédiate de chaque entrée invalidée

Cette stratégie détruirait des informations utiles à l’audit, à la reproductibilité et aux exécutions en cours.

Elle est rejetée.

---

## 13.6 Clés Redis construites directement dans le domaine

Cette approche couplerait le modèle métier à une technologie et rendrait les migrations difficiles.

Elle est rejetée.

---

## 13.7 Utilisation de l’IdempotencyKey comme clé de cache

Une demande d’exécution et un artefact réutilisable ne possèdent pas la même identité.

Cette alternative empêcherait la réutilisation fine entre exécutions.

Elle est rejetée.

---

## 13.8 Réutilisation transparente des résultats IA

Réutiliser silencieusement un résultat IA empêcherait d’expliquer correctement une analyse et pourrait masquer un changement de modèle, de prompt ou de contexte.

Cette alternative est rejetée.

---

## 13.9 CacheManager comme abstraction métier principale

Un simple `CacheManager` exprime une préoccupation de stockage, mais pas les décisions métier de fraîcheur, de sécurité, de compatibilité et de recalcul.

L’abstraction métier retenue est `ArtifactResolver`.

---

# 14. Conséquences positives

Cette décision permet :

* une réutilisation fine des calculs ;
* une réduction de la latence ;
* une réduction des appels à l’AI Engine ;
* une diminution des coûts ;
* une invalidation ciblée ;
* une meilleure isolation des données ;
* une traçabilité complète ;
* une architecture indépendante de Redis ou d’un autre fournisseur ;
* une exécution hybride mêlant cache et recalcul ;
* une dégradation contrôlée ;
* une meilleure reproductibilité ;
* une meilleure observabilité ;
* une évolution progressive vers des analyses plus complexes.

---

# 15. Conséquences négatives et coûts

Cette décision introduit une complexité supplémentaire.

Le système devra gérer :

* plusieurs types d’artefacts ;
* des empreintes déterministes ;
* des versions logiques ;
* des métadonnées de provenance ;
* un graphe de dépendances ;
* des politiques de fraîcheur ;
* des décisions de réutilisation ;
* des invalidations événementielles ;
* une observabilité plus détaillée.

Une mauvaise définition des paramètres significatifs ou des périmètres pourrait provoquer :

* des faux cache hits ;
* des cache misses excessifs ;
* des fuites de données ;
* des recalculs inutiles ;
* des résultats incohérents.

La mise en œuvre devra donc être progressive et accompagnée de tests de compatibilité et d’isolation.

# 16. Stratégie d’implémentation

L’implémentation doit être progressive.

## Étape 1 — Contrats du domaine

Introduire les concepts sans infrastructure distribuée :

* `ArtifactIdentity`
* `ArtifactScope`
* `ArtifactCacheKey`
* `ArtifactFreshness`
* `FreshnessStatus`
* `FreshnessPolicy`
* `ArtifactRequirement`
* `ArtifactResolution`
* `ReuseDecision`
* `ArtifactProvenance`

---

## Étape 2 — Résolution en mémoire

Créer un premier `ArtifactResolver` fonctionnant avec un stockage en mémoire.

Objectifs :

* valider les règles ;
* tester les identités ;
* tester la fraîcheur ;
* tester l’isolation ;
* tester la réutilisation partielle ;
* éviter un choix prématuré de technologie.

---

## Étape 3 — Dépendances et invalidation

Introduire :

* l’enregistrement des dépendances ;
* l’invalidation temporelle ;
* l’invalidation explicite ;
* la propagation ciblée ;
* les événements d’invalidation internes.

---

## Étape 4 — Intégration à AnalysisExecution

Intégrer la résolution au pipeline défini par ADR-021.

Chaque capacité doit exposer :

* ses exigences ;
* sa politique de fraîcheur ;
* ses règles de réutilisation ;
* sa version logique.

---

## Étape 5 — Observabilité

Ajouter des métriques :

* cache hit rate ;
* cache miss rate ;
* artefacts recalculés ;
* réutilisations `STALE` ;
* invalidations ;
* propagations ;
* temps économisé ;
* appels IA évités ;
* erreurs de compatibilité ;
* refus liés à la sécurité.

---

## Étape 6 — Infrastructure distribuée

Redis ou une autre solution ne doit être introduit qu’après validation du modèle métier et de ses besoins réels.

Une combinaison pourra être utilisée :

```text
Mémoire locale
    ↓
Cache distribué
    ↓
Stockage durable pour audit
```

Cette topologie sera traitée dans une décision ultérieure si nécessaire.

---

# 17. Tests requis

L’implémentation doit couvrir au minimum les scénarios suivants :

* même identité et mêmes paramètres produisent la même clé ;
* ordre différent des paramètres produit la même empreinte ;
* changement d’un paramètre significatif modifie la clé ;
* changement de version de capacité modifie la clé ;
* changement de source modifie l’empreinte d’entrée ;
* données publiques réutilisables entre utilisateurs ;
* données privées non réutilisables entre utilisateurs ;
* données de comptes différents strictement isolées ;
* artefact `FRESH` réutilisé ;
* artefact `STALE` accepté selon la politique ;
* artefact `STALE` refusé par une capacité critique ;
* artefact `EXPIRED` non réutilisé ;
* artefact `INVALIDATED` non réutilisé ;
* fraîcheur `UNKNOWN` refusée par défaut ;
* invalidation d’une dépendance propagée ;
* invalidation ciblée sans suppression globale ;
* exécution hybride avec artefacts réutilisés et recalculés ;
* retry ciblé réutilisant les capacités encore valides ;
* résultat IA non réutilisé lorsque le contexte change ;
* résultat IA réutilisé avec provenance explicite ;
* distinction entre `IdempotencyKey` et `ArtifactCacheKey`.

# 18. Hors périmètre

Cet ADR ne définit pas :

* le fournisseur de cache ;
* la topologie Redis ;
* les politiques d’éviction mémoire ;
* la réplication ;
* la haute disponibilité ;
* le format physique exact des clés ;
* le broker d’événements ;
* la persistance durable des artefacts ;
* une bibliothèque commune entre Trading OS et Developer OS.

Ces sujets pourront faire l’objet d’ADR distincts.

# 19. Piste architecturale future

Trading OS et Developer OS font apparaître des concepts transversaux similaires :

* identité d’artefact ;
* portée ;
* provenance ;
* dépendances ;
* fraîcheur ;
* invalidation ;
* cycle de vie ;
* réutilisation.

Une bibliothèque partagée pourrait être envisagée à long terme.

Cette bibliothèque ne devra être créée que si plusieurs implémentations réelles démontrent une abstraction stable et commune.

Elle ne devra pas contenir les modèles métier spécifiques :

* `IntelligenceContext`
* `IntelligenceObservation`
* `ValidatableProposal`
* connaissances de projet ;
* analyses de marché.

Cette piste est conservée comme orientation future, sans engagement d’implémentation dans le cadre d’ADR-022.

# 20. Résumé de la décision

> Market Intelligence utilise un modèle hybride de propriété des caches. Les services producteurs restent propriétaires de leurs données primaires, tandis que Market Intelligence possède les artefacts dérivés qu’il construit.

> Les artefacts sont identifiés par une `ArtifactCacheKey` métier fortement typée, contenant leur identité, leur périmètre, leurs paramètres significatifs et l’empreinte de leurs données d’entrée.

> La fraîcheur est indépendante du TTL et s’évalue selon une `FreshnessPolicy`, les besoins de la capacité et la politique de l’exécution.

> L’invalidation peut être temporelle, événementielle ou propagée depuis une dépendance. Une entrée invalidée n’est pas nécessairement supprimée.

> La réutilisation est orchestrée par un `ArtifactResolver`, qui décide entre réutilisation, réutilisation avec avertissement, recalcul ou rejet.

> L’idempotence des demandes reste distincte de l’identité des artefacts. Une `AnalysisExecution` peut combiner des artefacts réutilisés et recalculés tout en conservant une provenance complète.

> Les observations d’intelligence restent des objets métier et ne sont pas traitées comme de simples entrées de cache.
