# ADR-018 — Modélisation et diffusion du flux Recent Trades

## Statut

Proposé

## Date

2026-07-28

## Contexte

La page `Market Details` de Trading OS affiche désormais :

* le ticker temps réel ;
* l’historique et le flux OHLC ;
* le graphique en chandeliers ;
* le carnet d’ordres temps réel.

La dernière source de données majeure nécessaire pour rendre cette page pleinement exploitable est le flux des transactions récemment exécutées.

Kraken fournit ces transactions sous forme d’événements WebSocket. Ces messages utilisent un contrat propre au fournisseur et peuvent contenir plusieurs transactions dans un même message.

Le frontend Angular ne doit pas dépendre directement des DTO Kraken ni interpréter les particularités de son protocole.

Conformément aux décisions précédentes :

* les contrats Kraken restent confinés dans l’adapter Kraken ;
* les événements de marché sont spécialisés conformément à ADR-016 ;
* les abonnements sont dynamiques conformément à ADR-011 ;
* les transformations déterministes sont réalisées dans le service Java ;
* le frontend utilise des modèles métier stables et des flux réactifs ;
* les données temps réel restent éphémères dans la V1.

Contrairement à l’Order Book, les Recent Trades ne nécessitent pas de reconstruire un état complexe à partir de deltas. Chaque transaction reçue est un événement métier autonome.

Une petite mémoire bornée est cependant nécessaire pour fournir au frontend une liste récente stable, plutôt qu’un événement isolé disparaissant immédiatement.

## Décision

Trading OS introduira un événement métier spécialisé `TradeEvent`.

Les messages Kraken seront mappés côté backend vers un ou plusieurs `TradeEvent`, puis intégrés dans un buffer borné par marché.

Le frontend recevra des snapshots immuables contenant les dernières transactions connues du marché.

Le flux retenu est :

```text
Kraken WebSocket
        ↓
Kraken Trade DTO
        ↓
KrakenTradeMapper
        ↓
TradeEvent
        ↓
RecentTradesStateService
        ↓
RecentTradesSnapshot
        ↓
TradeEventPublisher
        ↓
WebSocket frontend
        ↓
Angular RecentTradesComponent
```

## Modèle métier

### TradeSide

Le côté de la transaction sera représenté par :

```java
public enum TradeSide {
    BUY,
    SELL
}
```

La sémantique du côté doit être documentée dans le mapper Kraken.

`BUY` signifie qu’un ordre acheteur a consommé de la liquidité disponible côté ask.

`SELL` signifie qu’un ordre vendeur a consommé de la liquidité disponible côté bid.

Le frontend ne doit pas déduire le côté à partir du prix ou du carnet d’ordres.

### TradeEvent

Une transaction exécutée sera représentée par :

```java
public record TradeEvent(
        UUID marketId,
        MarketProvider provider,
        String symbol,
        String tradeId,
        TradeSide side,
        BigDecimal price,
        BigDecimal quantity,
        BigDecimal notional,
        Instant occurredAt
) {
}
```

`notional` représente :

```text
price × quantity
```

Ce calcul est déterministe et doit être réalisé côté backend.

Si Kraken ne fournit pas d’identifiant stable pour une transaction, le champ `tradeId` peut être généré de manière déterministe à partir des attributs disponibles ou être remplacé par un identifiant technique interne.

Un identifiant généré ne doit pas être présenté comme un identifiant officiel Kraken.

## Snapshot des transactions récentes

Le frontend recevra un snapshot métier :

```java
public record RecentTradesSnapshot(
        UUID marketId,
        MarketProvider provider,
        String symbol,
        List<TradeEvent> trades,
        Instant generatedAt
) {
}
```

La liste doit être :

* immuable ;
* triée de la transaction la plus récente à la plus ancienne ;
* limitée à une taille maximale configurée ;
* indépendante du DTO Kraken.

## Buffer borné

Le backend conservera un buffer en mémoire pour chaque marché actif.

Une structure interne possible est :

```java
Deque<TradeEvent>
```

La taille maximale recommandée pour la V1 est :

```text
100 transactions
```

Cette limite pourra devenir configurable ultérieurement.

Lorsqu’une nouvelle transaction est reçue :

1. elle est ajoutée en tête ou en fin selon la représentation choisie ;
2. la taille du buffer est vérifiée ;
3. les transactions les plus anciennes sont supprimées si la limite est dépassée ;
4. un nouveau snapshot immuable est produit.

La collection interne mutable ne doit jamais être exposée directement.

## RecentTradesStateService

Un service déterministe dédié sera responsable de :

* créer un buffer pour un marché ;
* ajouter les nouvelles transactions ;
* préserver leur ordre chronologique ;
* éviter les doublons lorsque cela est possible ;
* limiter le nombre de transactions conservées ;
* produire un `RecentTradesSnapshot` immuable ;
* supprimer le buffer au dernier désabonnement.

Ce service ne dépend pas directement des DTO Kraken.

Il manipule uniquement des `TradeEvent`.

## Identité du buffer

Un buffer de transactions récentes est identifié par :

```text
marketId
```

Une clé dédiée peut être introduite si nécessaire :

```java
public record RecentTradesKey(
        UUID marketId
) {
}
```

La profondeur du buffer n’est pas un attribut d’abonnement Kraken dans la V1.

La limite d’affichage est une politique interne Trading OS.

## Contrat d’abonnement

Les abonnements continuent d’utiliser `MarketStreamRequest`.

Exemple :

```json
{
  "type": "TRADES",
  "parameters": null
}
```

Aucun intervalle ou depth n’est nécessaire pour le flux `TRADES`.

La validation métier doit refuser les paramètres incohérents uniquement s’ils rendent le contrat ambigu ou invalide.

## Provider WebSocket Kraken

`KrakenDataStreamProvider` reste responsable de :

* construire la commande d’abonnement au channel Kraken des transactions ;
* recevoir les messages ;
* identifier les messages de transactions ;
* désérialiser les DTO Kraken ;
* mapper chaque entrée vers un `TradeEvent` ;
* transmettre les événements au service d’état récent.

Un message Kraken contenant plusieurs transactions doit produire plusieurs `TradeEvent`.

Le provider ne doit pas exposer directement les DTO Kraken en dehors de l’adapter.

## Mapper Kraken

Un `KrakenTradeMapper` dédié sera introduit.

Il sera responsable de :

* résoudre le marché interne à partir du symbole Kraken ;
* convertir le côté Kraken vers `TradeSide` ;
* convertir les valeurs numériques en `BigDecimal` ;
* calculer le notional ;
* produire un horodatage métier cohérent ;
* gérer ou générer l’identifiant de transaction ;
* rejeter explicitement les données invalides.

Le mapper ne maintient aucun buffer et aucun état métier durable.

## Publication vers le frontend

Un publisher spécialisé sera introduit.

Nom recommandé :

```java
RecentTradesEventPublisher
```

Il expose un flux filtré par marché :

```java
Flux<RecentTradesSnapshot> streamByMarket(
        UUID marketId
);
```

Le publisher diffuse des snapshots complets plutôt que des transactions individuelles.

Cette décision simplifie le frontend :

* aucune accumulation manuelle dans Angular ;
* aucune suppression d’anciens éléments ;
* aucune gestion de doublons côté interface ;
* état immédiatement cohérent après chaque message.

Le `MarketDataWebSocketHandler` sera étendu avec une branche `TRADES`.

Les paramètres nécessaires sont :

```text
marketId
symbol
type=TRADES
```

Le handler sélectionne uniquement le flux correspondant et ne modifie pas les données.

## Fréquence de publication

Pour la V1, chaque lot Kraken valide peut produire un nouveau snapshot.

Si un message contient plusieurs transactions, elles doivent être intégrées dans le buffer avant la publication afin de n’émettre qu’un snapshot cohérent pour le lot complet.

Une stratégie de regroupement ou de limitation pourra être ajoutée ultérieurement si les mesures montrent un débit trop important.

## Ordre et déduplication

Les transactions doivent être triées selon leur `occurredAt`.

Lorsque plusieurs événements possèdent le même timestamp, l’ordre fourni par Kraken doit être préservé autant que possible.

La déduplication doit utiliser en priorité un identifiant stable de transaction.

En l’absence d’identifiant stable, une clé déterministe peut combiner :

```text
marketId
timestamp
price
quantity
side
```

Cette méthode ne garantit pas une unicité parfaite lorsque plusieurs transactions identiques ont lieu au même instant.

La déduplication ne doit donc pas supprimer silencieusement des transactions valides sans preuve suffisante.

## Frontend Angular

Le frontend introduira un modèle compatible avec `RecentTradesSnapshot`.

Le composant `RecentTradesComponent` sera purement présentatif et réactif.

Il affichera au minimum :

```text
Time | Side | Price | Quantity
```

Le notional pourra être ajouté si l’espace disponible le permet.

La transaction la plus récente sera affichée en premier.

Le côté sera représenté visuellement avec des couleurs discrètes :

* BUY : accent positif ;
* SELL : accent négatif.

Le frontend ne doit pas :

* accumuler lui-même les événements ;
* limiter manuellement une liste infinie ;
* calculer le notional ;
* déduire le côté ;
* connaître le protocole Kraken ;
* trier les transactions reçues.

Les données seront consommées avec `Observable` et `async pipe`.

## Cycle de vie

Lors du premier abonnement :

```text
compteur 0 → 1
→ abonnement Kraken TRADES
→ création du buffer
→ diffusion des transactions
```

Lorsqu’un autre consommateur demande le même flux :

```text
compteur N → N + 1
→ aucun nouvel abonnement Kraken
```

Lors du dernier désabonnement :

```text
compteur 1 → 0
→ désabonnement Kraken
→ suppression du buffer
→ arrêt de la diffusion
```

Le cycle de vie reste géré avec `MarketSubscriptionService`.

## État initial

Le flux Kraken peut fournir un snapshot initial ou seulement des mises à jour selon son contrat.

S’il fournit un snapshot, toutes les transactions du snapshot sont intégrées dans le buffer avant publication.

S’il ne fournit que des événements live, le composant démarre avec une liste vide et se remplit progressivement.

Aucun endpoint REST d’historique des trades n’est requis pour la première version.

Une route REST pourra être ajoutée ultérieurement si un historique initial plus riche devient nécessaire.

## Gestion des erreurs

Les cas suivants doivent être gérés explicitement :

* message Kraken invalide ;
* marché introuvable ;
* prix invalide ;
* quantité invalide ou négative ;
* côté inconnu ;
* timestamp invalide ;
* transaction incomplète ;
* erreur d’émission dans le publisher ;
* déconnexion Kraken ;
* buffer absent ou incohérent.

Une transaction invalide ne doit pas empêcher le traitement des autres transactions valides d’un même lot lorsque l’isolation est possible.

## Persistance

Les Recent Trades ne sont pas persistés dans la V1.

Le buffer est un état éphémère en mémoire.

Une persistance future pourra être envisagée pour :

* replay de marché ;
* analyse de flux ;
* détection d’agressivité acheteuse ou vendeuse ;
* footprint et volume profile ;
* backtesting ;
* analyses déterministes ;
* contexte destiné à l’AI Engine.

Cette évolution ne doit pas modifier le contrat frontend principal.

## Analyses futures

Les Recent Trades pourront alimenter ultérieurement des calculs déterministes comme :

* buy volume ;
* sell volume ;
* delta de volume ;
* fréquence des transactions ;
* taille moyenne ;
* détection de transactions importantes ;
* accélération du rythme d’exécution ;
* absorption combinée avec l’Order Book.

Ces calculs devront être implémentés côté Java, conformément à la philosophie Trading OS.

L’AI Engine pourra interpréter les résultats structurés, mais ne doit pas remplacer ces calculs déterministes.

## Tests requis

L’implémentation doit au minimum couvrir :

* mapping d’une transaction BUY ;
* mapping d’une transaction SELL ;
* calcul du notional ;
* ajout d’une transaction au buffer ;
* intégration d’un lot de transactions ;
* ordre de la plus récente à la plus ancienne ;
* limitation du buffer ;
* suppression des transactions les plus anciennes ;
* séparation de deux marchés ;
* gestion d’une transaction invalide ;
* gestion d’un snapshot initial ;
* nettoyage du buffer au dernier désabonnement ;
* publication d’un snapshot immuable.

## Conséquences positives

* Le frontend reste simple et indépendant de Kraken.
* Les transactions sont représentées par un modèle métier stable.
* La mémoire est bornée.
* Les snapshots reçus par Angular sont immédiatement affichables.
* Le modèle pourra alimenter les futures analyses de flux.
* La logique peut être testée sans connexion Kraken réelle.
* Le composant Recent Trades complète naturellement la page `Market Details`.

## Conséquences négatives

* Le backend maintient un buffer supplémentaire en mémoire.
* La diffusion de snapshots complets utilise davantage de bande passante que des événements isolés.
* La déduplication peut être imparfaite sans identifiant stable du fournisseur.
* Une reconnexion Kraken peut faire perdre l’historique éphémère du buffer.
* Une fréquence de transactions élevée pourra nécessiter une limitation future des publications.

## Alternatives rejetées

### Envoyer chaque transaction directement au frontend

Rejeté, car Angular devrait gérer l’accumulation, la limite du buffer, le tri et les doublons.

### Exposer les DTO Kraken

Rejeté, car cela couple le frontend au fournisseur.

### Persister immédiatement toutes les transactions

Rejeté pour la V1 en raison du volume et de la complexité sans bénéfice immédiat.

### Calculer le notional dans Angular

Rejeté, car il s’agit d’un calcul déterministe réutilisable.

### Fusionner `TradeEvent` avec d’autres événements de marché

Rejeté conformément à ADR-016. Chaque type de donnée possède son modèle spécialisé.

## Plan d’implémentation recommandé

1. Créer `TradeSide`.
2. Créer `TradeEvent`.
3. Créer `RecentTradesSnapshot`.
4. Créer les DTO Kraken dédiés aux trades.
5. Implémenter `KrakenTradeMapper`.
6. Implémenter `RecentTradesStateService`.
7. Ajouter les tests du buffer.
8. Ajouter le channel trades dans les commandes Kraken.
9. Étendre le dispatcher WebSocket Kraken.
10. Créer `RecentTradesEventPublisher`.
11. Étendre `MarketDataWebSocketHandler`.
12. Ajouter `streamRecentTrades()` dans Angular.
13. Créer les modèles Angular.
14. Créer `RecentTradesComponent`.
15. Brancher le flux dans `MarketDetail`.
16. Vérifier le cycle subscribe/unsubscribe.
17. Nettoyer les logs temporaires.
18. Exécuter les tests backend et frontend.

## Résultat attendu

La page `Market Details` affiche une liste temps réel, bornée et cohérente des dernières transactions exécutées.

Le frontend reçoit des snapshots métier complets.

L’accumulation, le tri, la limitation, la validation et les calculs déterministes sont centralisés dans le service Java `market-data`.

Avec le graphique, le ticker et l’Order Book, cette fonctionnalité termine le socle principal d’analyse temps réel de la page `Market Details` pour la V1.
