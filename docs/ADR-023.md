ADR-023 — Capability Execution Model

Status: Accepted

Date: 2026-07-29

Decision owners: Trading OS architecture

Scope: Trading Intelligence execution engine

Context

Trading OS doit exécuter des analyses composées de nombreuses capacités déterministes, IA ou hybrides.

Les ADR précédentes ont déjà défini les fondations du système d’analyse, notamment :

le modèle des Artifacts ;

le modèle des Observations ;

le modèle des AnalysisExecution ;

la séparation entre logique métier déterministe, orchestration et traitements IA.

Il reste à formaliser la manière dont les Capabilities sont décrites, découvertes, planifiées, exécutées, surveillées, annulées et coordonnées.

L’objectif de cette ADR est de définir un modèle d’exécution :

déterministe ;

observable ;

résilient ;

parallélisable ;

extensible ;

compatible avec des traitements déterministes, IA et hybrides ;

suffisamment explicite pour être implémenté sans décision d’architecture supplémentaire.

Decision 1 — Capability Definition

Une Capability représente une unité autonome d’analyse métier.

Elle possède :

une identité ;

une version ;

une catégorie ;

des métadonnées immuables ;

des exigences d’entrée ;

une politique d’exécution ;

une politique de retry ;

une logique d’analyse.

Une Capability peut être :

déterministe ;

IA ;

hybride.

Une Capability retourne exclusivement un CapabilityResult.

Une Capability ne persiste jamais directement de données.

Decision 2 — Capability Contract

Chaque Capability suit le contrat logique suivant :

CapabilityContext
↓
Capability
↓
CapabilityResult

La Capability :

ne charge jamais elle-même ses dépendances ;

ne persiste jamais d’Artifacts ;

ne modifie jamais directement une Observation ;

ne communique jamais directement avec Redis ;

n’appelle jamais de repository ;

n’appelle jamais une autre Capability ;

ne décide jamais de son propre ordonnancement ;

ne modifie jamais son propre état d’exécution.

L’ExecutionEngine prépare le contexte, déclenche l’exécution, interprète le résultat et persiste les données produites.

Decision 3 — Capability Metadata

Chaque Capability expose des métadonnées immuables.

Les métadonnées décrivent au minimum :

l’identité de la Capability ;

sa version ;

sa catégorie ;

ses ArtifactRequirements ;

ses contributions potentielles ;

son ExecutionPolicy ;

sa RetryPolicy ;

ses contraintes d’exécution éventuelles.

Les informations spécifiques à une invocation appartiennent exclusivement au CapabilityContext.

Les métadonnées servent à la planification et ne doivent contenir aucun état mutable d’exécution.

Decision 4 — Dependencies Through Artifacts

Les dépendances sont exprimées exclusivement au travers des Artifacts.

Une Capability ne dépend jamais directement d’une autre Capability.

Exemple :

LiquidityCapability
requires:
- MarketSnapshot
- OrderBookSnapshot

L’ExecutionPlanner résout les producteurs potentiels capables de fournir ces Artifacts.

Cette approche garantit :

un couplage faible ;

la possibilité de plusieurs producteurs ;

la réutilisation des Artifacts ;

la substitution de producteurs ;

un graphe d’exécution explicite.

Decision 5 — Capability and CapabilityExecution

Une Capability représente une définition statique.

Une CapabilityExecution représente une invocation précise de cette définition.

Plusieurs CapabilityExecution peuvent donc référencer la même Capability.

Une CapabilityExecution contient au minimum :

son identifiant ;

l’identifiant de la Capability ;

la version de la Capability ;

l’identifiant de l’AnalysisExecution ;

son état ;

son contexte ou une référence vers celui-ci ;

ses timestamps ;

ses métriques ;

sa provenance ;

son résultat éventuel ;

son échec éventuel ;

les informations liées aux tentatives.

Decision 6 — Execution Policy

Chaque Capability déclare une ExecutionPolicy.

Les valeurs initiales sont :

REQUIRED

OPTIONAL

CONDITIONAL

ON_DEMAND

La Capability ne décide jamais si elle doit être exécutée.

L’ExecutionPlanner interprète la politique et décide de la présence de la Capability dans le plan.

Decision 7 — Produced Contributions

Chaque Capability déclare dans ses métadonnées les contributions qu’elle peut produire.

Ces contributions peuvent inclure :

des Artifact types ;

des Observation contribution types ;

des métriques ;

des recommandations ;

d’autres résultats structurés explicitement définis.

L’ExecutionPlanner connaît ainsi les producteurs potentiels avant l’exécution.

Aucune contribution ne doit être découverte implicitement uniquement après exécution.

Decision 8 — CapabilityExecution Lifecycle

Chaque CapabilityExecution suit une machine à états explicite contrôlée exclusivement par l’ExecutionEngine.

States

CREATED
WAITING_FOR_REQUIREMENTS
READY
RUNNING
COMPLETED
FAILED
SKIPPED
CANCELLED
TIMED_OUT

Main transitions

CREATED → WAITING_FOR_REQUIREMENTS
CREATED → READY
CREATED → SKIPPED
CREATED → CANCELLED

WAITING_FOR_REQUIREMENTS → READY
WAITING_FOR_REQUIREMENTS → SKIPPED
WAITING_FOR_REQUIREMENTS → FAILED
WAITING_FOR_REQUIREMENTS → CANCELLED
WAITING_FOR_REQUIREMENTS → TIMED_OUT

READY → RUNNING
READY → SKIPPED
READY → CANCELLED

RUNNING → COMPLETED
RUNNING → FAILED
RUNNING → CANCELLED
RUNNING → TIMED_OUT

Terminal states

COMPLETED
FAILED
SKIPPED
CANCELLED
TIMED_OUT

Les états terminaux sont immuables.

Une Capability ne modifie jamais elle-même l’état de sa CapabilityExecution.

Retry model

Un retry ne réactive jamais une CapabilityExecution terminée.

Chaque nouvelle tentative crée une nouvelle CapabilityExecution.

Les tentatives sont reliées au minimum par :

executionGroupId

attemptNumber

previousAttemptId

Decision 9 — Separation Between Planning and Execution

La planification est séparée de l’exécution.

AnalysisExecution
↓
ExecutionPlanner
↓
ExecutionPlan
↓
ExecutionEngine
↓
CapabilityExecution

ExecutionPlanner

L’ExecutionPlanner :

sélectionne les Capabilities ;

résout les dépendances par Artifacts ;

valide les versions ;

choisit les producteurs ;

détecte les incohérences ;

construit le graphe ;

identifie les nœuds parallélisables ;

documente les décisions de planification.

Il ne lance jamais de Capability.

ExecutionPlan

L’ExecutionPlan est une représentation immuable de la stratégie d’exécution.

Il contient notamment :

les nœuds planifiés ;

les dépendances ;

les contraintes ;

les raisons de sélection ou d’exclusion ;

les producteurs retenus ;

les adaptateurs éventuels ;

les informations nécessaires à l’audit.

ExecutionEngine

L’ExecutionEngine :

exécute le plan ;

applique les transitions d’état ;

déclenche les nœuds prêts ;

applique les retries ;

propage les annulations ;

gère les timeouts ;

collecte les résultats ;

persiste les sorties ;

débloque les nœuds dépendants.

Il ne redéfinit jamais la stratégie établie par le plan.

Decision 10 — Directed Acyclic Execution Graph

L’ExecutionPlanner construit un graphe orienté acyclique, ou DAG.

Les dépendances sont déduites des Artifacts requis et produits.

Une CapabilityExecution devient exécutable lorsque toutes ses dépendances obligatoires sont satisfaites.

Les nœuds indépendants peuvent être exécutés simultanément.

Le parallélisme est donc une propriété naturelle du graphe et non une logique codée dans les Capabilities.

Le Planner doit détecter avant exécution :

les cycles ;

les exigences impossibles à satisfaire ;

les ambiguïtés de producteurs non résolues ;

les incompatibilités de versions ;

les incohérences de cardinalité.

Decision 11 — Failure Propagation Strategy

L’échec d’une CapabilityExecution se propage uniquement aux nœuds dont les exigences ne peuvent plus être satisfaites.

Direct dependants

Un nœud empêché de démarrer à cause d’un Artifact indisponible devient :

SKIPPED
reason = UNSATISFIED_REQUIREMENT

Il n’est pas marqué FAILED, car sa propre logique n’a pas été exécutée.

Independent branches

Les branches indépendantes continuent normalement.

Partial consumers

Un consommateur explicitement conçu pour accepter un contexte partiel peut être exécuté avec une description structurée :

des contributions disponibles ;

des contributions absentes ;

des échecs associés ;

du niveau de complétude.

Un résultat partiel ne doit jamais masquer l’absence de données.

Negative result versus failure

Une Capability qui conclut qu’aucune opportunité n’existe retourne un résultat valide et termine en COMPLETED.

FAILED est réservé aux cas où aucun résultat fiable ne peut être produit.

Alternative producers

L’échec d’un producteur ne rend pas immédiatement une exigence impossible si un autre producteur ou fallback déjà prévu par le plan peut encore produire l’Artifact attendu.

L’Engine n’improvise jamais un fallback absent du plan.

CapabilityFailure

Chaque échec doit être représenté par une structure dédiée, par exemple :

CapabilityFailure
- failureType
- errorCode
- message
- retryable
- failedRequirement
- producerExecutionId
- occurredAt
- diagnostics

Decision 12 — Retry Strategy

Chaque Capability peut déclarer une RetryPolicy, distincte de son ExecutionPolicy.

La RetryPolicy contient au minimum :

l’activation ou non du retry ;

le nombre maximal de tentatives ;

la stratégie de backoff ;

les catégories d’erreurs retryables ;

les délais éventuels ;

les limites éventuelles.

Les stratégies initialement supportées sont :

FIXED

LINEAR

EXPONENTIAL

Les erreurs retryables peuvent inclure :

timeout externe ;

erreur réseau ;

indisponibilité temporaire ;

rate limiting ;

indisponibilité temporaire d’un fournisseur IA.

Les erreurs non retryables peuvent inclure :

violation d’un invariant métier ;

données invalides ;

incompatibilité de schéma ;

erreur déterministe de logique ;

résultat impossible à valider.

La Capability ne se relance jamais elle-même.

L’ExecutionEngine applique la RetryPolicy et crée une nouvelle CapabilityExecution pour chaque tentative.

Decision 13 — Cancellation Strategy

L’annulation d’une AnalysisExecution est :

coopérative ;

hiérarchique ;

traçable.

Le cycle global comprend :

RUNNING
↓
CANCEL_REQUESTED
↓
CANCELLED

CANCEL_REQUESTED signifie que la demande est enregistrée mais que certains traitements peuvent encore être en cours d’arrêt.

CANCELLED signifie qu’aucune exécution active ne peut encore produire de résultat métier pour cette analyse.

Propagation

Lorsqu’une annulation est demandée :

les nœuds CREATED, WAITING_FOR_REQUIREMENTS ou READY deviennent CANCELLED ;

les nœuds RUNNING reçoivent un signal d’annulation coopératif ;

aucun nouveau nœud ne peut être lancé ;

aucun nouveau retry ne peut être créé ;

les retries programmés mais non démarrés sont annulés.

Cancellation token

Les traitements longs doivent pouvoir recevoir un CancellationToken ou un mécanisme équivalent.

La Capability peut interrompre son travail, mais seul l’ExecutionEngine effectue la transition d’état.

Late results

Un résultat reçu après la demande d’annulation est ignoré.

Il ne peut :

ni produire d’Artifact ;

ni modifier une Observation ;

ni débloquer un nœud ;

ni changer l’état global de l’analyse.

Audit

Les résultats déjà validés restent conservés.

L’annulation ne supprime jamais l’historique.

Chaque annulation est représentée par une structure telle que :

CancellationRequest
- requestedAt
- requestedBy
- reason
- source
- correlationId

Les sources initiales peuvent inclure :

USER

SYSTEM

PARENT_EXECUTION

SHUTDOWN

RESOURCE_LIMIT

Decision 14 — No Capability Composition

Une Capability ne peut jamais :

appeler une autre Capability ;

déclencher une autre Capability ;

orchestrer une autre Capability ;

construire un sous-graphe invisible ;

masquer une dépendance d’exécution.

Toute composition appartient exclusivement à l’ExecutionPlanner.

Une analyse complexe est représentée par plusieurs Capabilities reliées par des Artifacts dans le DAG.

Cette règle garantit que :

le graphe observé correspond au graphe réel ;

le parallélisme reste exploitable ;

les retries restent cohérents ;

les annulations restent cohérentes ;

l’observabilité est complète ;

aucune orchestration cachée n’existe.

Decision 15 — Version Compatibility

Les versions des Capabilities et des Artifacts sont indépendantes.

La version d’une Capability identifie son comportement algorithmique.

La version d’un Artifact identifie son contrat de données.

Une Capability peut donc consommer et produire des Artifacts dont les versions ne correspondent pas à sa propre version.

ArtifactRequirement

Chaque exigence d’Artifact déclare au minimum :

ArtifactRequirement
- artifactType
- expectedVersion
- compatibilityMode
- required
- cardinality

Les modes initiaux sont :

EXACT

BACKWARD_COMPATIBLE

Exact compatibility

EXACT exige une correspondance exacte de version.

Backward compatibility

BACKWARD_COMPATIBLE permet une version plus récente uniquement si cette version déclare explicitement préserver le contrat attendu.

Une version supérieure n’est jamais considérée compatible par simple comparaison numérique.

Planning validation

Le Planner valide toutes les compatibilités avant l’exécution.

Si aucun producteur ou adaptateur compatible n’existe, la planification échoue avec une raison structurée telle que :

NO_COMPATIBLE_ARTIFACT_PRODUCER

ArtifactAdapter

Toute conversion entre versions est représentée explicitement par un ArtifactAdapter.

Un ArtifactAdapter :

est déterministe ;

transforme un contrat de données en un autre ;

est visible dans l’ExecutionPlan ;

n’est pas une Capability métier ;

ne doit pas masquer une perte de données ou de sémantique.

Le Planner peut insérer un ArtifactAdapter dans le DAG lorsqu’une conversion autorisée existe.

Consequences

Positive consequences

Cette architecture fournit un moteur :

déterministe ;

fortement découplé ;

observable ;

auditable ;

résilient ;

parallélisable ;

testable ;

extensible ;

compatible avec les analyses déterministes, IA et hybrides ;

adapté à une évolution distribuée future.

Les Capabilities restent de simples unités d’analyse métier.

Toute orchestration est centralisée dans l’ExecutionPlanner et l’ExecutionEngine.

Costs and trade-offs

Cette approche introduit :

un modèle de domaine plus riche ;

un moteur de planification explicite ;

une gestion stricte des états ;

un registre des producteurs ;

une validation des versions ;

une gestion dédiée des retries et annulations ;

davantage de données d’audit.

Cette complexité est acceptée car elle rend explicites des comportements qui seraient autrement cachés, fragiles et difficiles à tester.

Implementation Constraints

L’implémentation doit respecter les contraintes suivantes :

Aucune Capability ne doit accéder directement à un repository.

Aucune Capability ne doit persister directement un Artifact.

Aucune Capability ne doit appeler une autre Capability.

Aucune Capability ne doit modifier sa CapabilityExecution.

L’ExecutionPlanner ne doit lancer aucune exécution.

L’ExecutionEngine ne doit pas reconstruire ou modifier la stratégie du plan.

L’ExecutionPlan doit être immuable après validation.

Toute dépendance doit être visible dans le DAG.

Toute tentative de retry doit créer une nouvelle CapabilityExecution.

Tout résultat tardif après annulation doit être rejeté.

Toute incompatibilité de version doit être détectée avant exécution.

Toute adaptation de version doit être visible dans le plan.

Tout état terminal doit être immuable.

Toute transition d’état invalide doit être rejetée.

Les branches indépendantes doivent pouvoir continuer après un échec local.

Acceptance Criteria

ADR-023 est considérée correctement implémentée lorsque :

un plan peut être construit à partir des métadonnées des Capabilities ;

les producteurs sont résolus par Artifact type et version ;

les cycles et dépendances impossibles sont détectés ;

le DAG peut identifier les nœuds prêts et parallélisables ;

l’Engine exécute le plan sans prendre de décision de planification ;

les transitions d’état sont contrôlées et testées ;

les retries créent de nouvelles tentatives traçables ;

les erreurs locales ne bloquent pas les branches indépendantes ;

les nœuds non exécutables deviennent SKIPPED avec une raison structurée ;

les annulations neutralisent les résultats tardifs ;

les incompatibilités de versions empêchent la planification ;

les ArtifactAdapters apparaissent explicitement dans le plan ;

aucune Capability ne contient de logique d’orchestration cachée.

Final Decision

Trading OS adopte un modèle d’exécution fondé sur :

des Capabilities atomiques ;

des dépendances exprimées par Artifacts ;

un ExecutionPlanner séparé ;

un ExecutionPlan immuable ;

un DAG d’exécution ;

un ExecutionEngine responsable du lifecycle ;

une propagation ciblée des échecs ;

des retries déclaratifs ;

une annulation coopérative ;

une compatibilité de versions explicitement validée.

Cette ADR constitue le contrat architectural de référence pour l’implémentation du moteur de Capabilities.
