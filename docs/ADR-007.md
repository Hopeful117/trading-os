# ADR-007 — Broker Service Responsibilities

- **Status:** Accepted
- **Date:** 2026-07-23

## Context

Trading OS is designed to support multiple brokers while keeping the business domain independent from provider-specific APIs.

Broker APIs differ significantly in terms of:

- authentication;
- account models;
- order execution;
- balances;
- positions;
- trading capabilities.

Embedding broker-specific logic directly inside Trading Core would tightly couple business logic with external providers and significantly complicate future integrations.

## Decision

Trading OS introduces a dedicated Broker Service.

The Broker Service owns all broker integrations and exposes a provider-independent API to the rest of the platform.

Trading Core never communicates directly with broker APIs.

---

## Responsibilities

Broker Service is responsible for:

- broker authentication;
- account synchronization;
- balance retrieval;
- position retrieval;
- order execution;
- order cancellation;
- broker-specific request signing;
- provider-specific DTO mapping.

Business logic remains outside this service.

---

## Provider Abstraction

Every broker implementation must follow a common provider abstraction.

Example:

```
BrokerProvider

├── KrakenProvider
├── BinanceProvider
├── InteractiveBrokersProvider
└── Future providers...
```

Trading Core remains unaware of the underlying broker implementation.

---

## Provider Independence

Provider DTOs remain inside the Broker Service.

Example:

```
KrakenAccountDto

↓

Account

↓

Trading Core
```

Provider-specific objects must never propagate outside the service boundary.

---

## Trading Core Integration

Trading Core consumes Broker Service through dedicated clients.

Typical operations include:

- synchronizing accounts;
- retrieving balances;
- retrieving positions;
- submitting validated orders.

Trading Core remains responsible for deciding whether an order may be executed.

Broker Service is responsible only for executing valid requests.

---

## Order Execution

Broker Service executes orders exactly as requested.

It does not:

- perform risk validation;
- evaluate trading rules;
- interpret market conditions;
- analyse opportunities.

Those responsibilities belong to Trading Core.

---

## Synchronization

Broker synchronization is initiated by Trading Core or scheduled workflows.

Synchronization updates:

- accounts;
- balances;
- positions;
- broker metadata.

Synchronization should remain idempotent whenever possible.

---

## Extensibility

Adding a new broker should require only:

- implementing a new provider adapter;
- mapping provider DTOs;
- registering the provider.

No modification should be required inside Trading Core business logic.

---

## Consequences

Advantages:

- clean separation of concerns;
- broker independence;
- simplified Trading Core;
- easier testing;
- easier future integrations.

Trade-offs:

- additional service communication;
- provider adapter maintenance.

These trade-offs are accepted.

---

## Alternatives Considered

### Broker Logic Inside Trading Core

Rejected.

This would tightly couple business logic with provider APIs and make future integrations difficult.

---

### One Service Per Broker

Rejected.

Although technically possible, it would unnecessarily increase operational complexity during the early stages of Trading OS.

A single Broker Service supporting multiple provider adapters offers a better balance.
