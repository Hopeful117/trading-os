# ADR-019 — Orchestration et responsabilités du Dashboard Trading OS

## Statut

## Date

2026-07-29

## Contexte

Le Dashboard est la vue de synthèse principale de Trading OS.

Contrairement à la page `Market Details`, il ne dépend pas d’un seul domaine technique. Il doit agréger des informations provenant de plusieurs services :

* le **Broker Service**, qui connaît l’état réel du compte chez le broker ;
* le **Market Data Service**, qui fournit les prix et le contexte de marché ;
* le **Trading Core**, qui possède les règles métier, les calculs de risque et la représentation interne des comptes, positions et objectifs ;
* le **frontend Angular**, qui présente les informations à l’utilisateur.

Les principales informations attendues sont notamment :

* balance et equity ;
* PnL journalier ;
* drawdown ;
* risque utilisé et risque restant ;
* positions ouvertes ;
* prix d’entrée et prix courant ;
* PnL non réalisé précis ;
* exposition et risque par position ;
* état du Risk Engine ;
* alertes nécessitant une action ;
* données de performance ;
* synthèse des marchés surveillés.

Sans séparation claire des responsabilités, plusieurs problèmes peuvent apparaître :

* duplication des calculs entre le frontend et les services ;
* dépendance du Trading Core aux contrats spécifiques d’un broker ;
* couplage du Broker Service aux règles métier ;
* transformation du Market Data Service en service utilisateur ;
* appels directs du frontend vers plusieurs services suivis d’une agrégation côté Angular ;
* incohérences entre le PnL affiché, le PnL du broker et le PnL utilisé par le Risk Engine ;
* multiplication des modèles représentant une même position ;
* impossibilité de tracer l’origine et l’heure des données affichées.

Le Dashboard étant une vue utilisateur sensible et dépendante du métier, son contrat final doit être construit et exposé par le Trading Core.

## Décision

Le **Trading Core est l’orchestrateur et le propriétaire du contrat Dashboard**.

Il collecte les données nécessaires auprès du Broker Service et du Market Data Service, applique les règles et calculs métier, puis retourne au frontend un modèle agrégé directement exploitable.

Le frontend ne réalise aucune agrégation interservices.

Le flux principal est :

```text
Angular
   ↓
Trading Core Dashboard API
   ├── Broker Service
   │      └── état du compte et positions broker
   │
   ├── Market Data Service
   │      └── prix et état actuel des marchés
   │
   └── Trading Core
          ├── modèles internes
          ├── calculs de PnL
          ├── calculs d’exposition
          ├── Risk Engine
          ├── règles du compte ou du challenge
          ├── alertes
          └── agrégation Dashboard
```

Le frontend reçoit un seul contrat produit cohérent.

## Principes directeurs

### Le Broker Service rapporte les faits du broker

Le Broker Service est responsable des données externes et sensibles provenant du broker.

### Le Market Data Service rapporte les faits du marché

Le Market Data Service est responsable des prix et données de marché indépendants de l’utilisateur.

### Le Trading Core interprète ces faits dans le contexte utilisateur

Le Trading Core applique les règles métier, calcule le risque, le PnL et construit la vue Dashboard.

### Angular présente les résultats

Le frontend affiche les données déjà calculées et ne devient pas un moteur financier ou un orchestrateur distribué.

## Responsabilités du Broker Service

Le Broker Service est la source d’intégration avec Kraken et les futurs brokers.

Il est responsable de :

* l’authentification auprès du broker ;
* la récupération de la balance ;
* la récupération de l’equity broker lorsqu’elle est fournie ;
* la récupération des positions ouvertes ;
* la récupération des ordres ouverts ;
* la récupération des prix d’entrée broker ;
* la récupération des quantités ;
* la récupération des stop loss et take profit connus du broker ;
* la récupération des PnL broker lorsque le broker les fournit ;
* la récupération des marges et expositions propres au broker ;
* la normalisation des contrats externes vers des DTO internes au Broker Service ;
* la gestion des erreurs, limites et indisponibilités du broker ;
* l’horodatage des données récupérées ;
* la validation du JWT pour les opérations utilisateur.

Le Broker Service ne doit pas :

* calculer les règles Trading OS ;
* appliquer les règles d’un challenge prop firm ;
* décider si une position respecte le risque autorisé ;
* construire le modèle Dashboard ;
* dépendre du frontend ;
* consommer les composants Angular ;
* devenir propriétaire du modèle métier `DashboardSummary` ;
* interpréter les opportunités de marché ;
* appeler directement le Market Data Service pour construire une vue utilisateur.

Le Broker Service expose des faits normalisés, pas une interprétation métier complète.

## Responsabilités du Market Data Service

Le Market Data Service est la source des données de marché indépendantes de l’utilisateur.

Il est responsable de :

* l’identification des marchés ;
* la normalisation des symboles ;
* les derniers prix ticker ;
* les bid et ask ;
* les historiques OHLC ;
* les flux OHLC ;
* les carnets d’ordres ;
* les transactions récentes ;
* l’état de négociabilité du marché ;
* les métriques déterministes de marché ;
* le spread de marché ;
* l’imbalance du carnet ;
* les timestamps et la fraîcheur des données ;
* les flux WebSocket vers les consommateurs de données de marché ;
* la fourniture d’un état courant récupérable par le Trading Core.

Le Market Data Service ne doit pas :

* connaître les comptes utilisateur ;
* connaître les règles de risque d’un utilisateur ;
* connaître les challenges prop firm ;
* calculer le PnL d’une position utilisateur ;
* calculer l’equity d’un compte ;
* construire le Dashboard ;
* stocker des positions broker ;
* dépendre du Broker Service ;
* valider un JWT tant qu’il n’expose que des données publiques de marché.

Pour permettre l’agrégation du Dashboard, le Market Data Service doit pouvoir exposer une représentation courante des prix nécessaires au Trading Core.

Cette représentation peut être fournie par une route REST interne telle que :

```text
GET /internal/markets/prices?marketIds=...
```

ou :

```text
POST /internal/markets/prices/snapshot
```

avec une liste de marchés demandés.

Le contrat exact sera choisi selon les conventions existantes, mais il doit permettre une récupération groupée afin d’éviter un appel réseau par position.

Le résultat contient au minimum :

```java
public record MarketPriceSnapshot(
        UUID marketId,
        String symbol,
        BigDecimal lastPrice,
        BigDecimal bid,
        BigDecimal ask,
        boolean tradable,
        Instant occurredAt
) {
}
```

Le Market Data Service reste propriétaire de ce contrat de donnée de marché.

## Responsabilités du Trading Core

Le Trading Core est le propriétaire du domaine utilisateur et du Dashboard.

Il est responsable de :

* l’identification du compte sélectionné ;
* la représentation métier du compte ;
* la représentation métier des positions ;
* la correspondance entre une position broker et un marché Trading OS ;
* l’appel au Broker Service ;
* l’appel au Market Data Service ;
* l’agrégation des réponses ;
* la validation de la cohérence des données ;
* le calcul du PnL non réalisé de référence Trading OS ;
* le calcul du PnL journalier ;
* le calcul de l’equity de référence ;
* le calcul du drawdown ;
* le calcul de l’exposition ;
* le calcul du risque par position ;
* le calcul du risque total utilisé ;
* le calcul du risque restant ;
* l’application des règles utilisateur ou prop firm ;
* l’exécution du Risk Engine ;
* la création des alertes ;
* la construction de `DashboardSummary` ;
* la traçabilité de la fraîcheur et de la qualité des données ;
* l’exposition de l’API Dashboard au frontend ;
* la validation du JWT et des autorisations utilisateur.

Le Trading Core ne doit pas :

* connaître les DTO bruts Kraken ;
* ouvrir directement une connexion vers Kraken ;
* dupliquer les adapters du Broker Service ;
* dupliquer les adapters du Market Data Service ;
* exposer les DTO Feign externes directement au frontend ;
* déléguer les calculs financiers principaux à Angular ;
* accéder directement aux bases de données d’un autre service.

## Responsabilités du frontend Angular

Angular est responsable de :

* demander le Dashboard au Trading Core ;
* afficher les métriques principales ;
* afficher les positions ouvertes ;
* afficher les valeurs de risque ;
* afficher les alertes ;
* gérer les états de chargement ;
* gérer les états d’erreur ;
* indiquer la fraîcheur des données ;
* déclencher un rafraîchissement ;
* mettre à jour réactivement la vue ;
* appliquer le style et les transformations purement visuelles.

Angular peut effectuer des calculs exclusivement visuels, par exemple :

* largeur d’une barre de progression ;
* classe CSS positive ou négative ;
* formatage monétaire ;
* formatage en pourcentage ;
* ordre d’affichage explicitement autorisé par le contrat.

Angular ne doit pas :

* appeler directement le Broker Service pour construire le Dashboard ;
* appeler directement le Market Data Service pour enrichir les positions ;
* agréger plusieurs réponses de services ;
* calculer le PnL métier de référence ;
* calculer le drawdown ;
* calculer le risque ;
* déterminer un statut `SAFE`, `WARNING` ou `BREACHED` ;
* interpréter les règles du compte ;
* devenir propriétaire de la vérité métier.

## Sens des dépendances

Le sens autorisé des dépendances est :

```text
Angular
   ↓
Trading Core
   ├── Broker Service
   └── Market Data Service
```

Les dépendances suivantes sont interdites pour la construction du Dashboard :

```text
Angular → Broker Service
Angular → Market Data Service
Broker Service → Trading Core
Market Data Service → Trading Core
Broker Service → Market Data Service
Market Data Service → Broker Service
```

Le Gateway peut router les requêtes externes, mais il ne réalise aucune agrégation métier.

## Communication interservices

Les commandes et lectures explicites de la V1 utilisent les mécanismes existants :

* Eureka pour la découverte de services ;
* OpenFeign pour les appels synchrones entre services ;
* Gateway pour l’entrée externe ;
* JWT et Spring Security pour les opérations utilisateur sensibles.

Le Trading Core utilise des clients Feign dédiés :

```text
BrokerServiceClient
MarketDataClient
```

Les DTO Feign sont considérés comme des contrats d’intégration.

Ils sont mappés vers les modèles du Trading Core avant tout calcul ou exposition au frontend.

## Construction du Dashboard

Un service d’orchestration dédié sera introduit dans le Trading Core.

Nom recommandé :

```java
DashboardService
```

ou :

```java
DashboardQueryService
```

Sa responsabilité est de construire une vue de lecture agrégée.

Exemple de flux :

```text
1. Charger le compte Trading OS
2. Récupérer l’état du compte depuis le Broker Service
3. Récupérer les positions broker ouvertes
4. Résoudre les marketId associés aux symboles
5. Récupérer en lot les prix courants depuis Market Data
6. Construire les positions métier enrichies
7. Calculer PnL, equity, exposition et risque
8. Exécuter le Risk Engine
9. Construire les alertes
10. Construire DashboardSummary
11. Retourner la réponse au frontend
```

Le service d’orchestration ne doit pas contenir tous les calculs lui-même.

Il coordonne des services déterministes spécialisés tels que :

```text
PositionValuationService
AccountEquityService
TradingCalculatorService
RiskEngine
TradeAnalyticsService
DashboardAlertService
```

Les services existants doivent être réutilisés avant d’introduire de nouvelles implémentations.

## Contrat Dashboard principal

Le Trading Core expose un contrat agrégé :

```java
public record DashboardSummary(
        AccountDashboardSummary account,
        RiskDashboardSummary risk,
        List<OpenPositionDashboardView> openPositions,
        List<DashboardAlert> alerts,
        List<MarketDashboardView> watchedMarkets,
        DashboardFreshness freshness,
        Instant generatedAt
) {
}
```

Les sections non encore disponibles peuvent être représentées par des listes vides ou des champs optionnels clairement documentés.

Elles ne doivent pas être alimentées par de fausses données.

## AccountDashboardSummary

```java
public record AccountDashboardSummary(
        UUID accountId,
        String accountName,
        String broker,
        String currency,
        BigDecimal balance,
        BigDecimal equity,
        BigDecimal dailyPnl,
        BigDecimal dailyPnlPercentage,
        BigDecimal currentDrawdown,
        BigDecimal currentDrawdownPercentage
) {
}
```

Les montants ne doivent pas être supposés en euros.

La devise vient du compte.

Le frontend utilise cette devise pour le formatage.

## OpenPositionDashboardView

```java
public record OpenPositionDashboardView(
        String positionId,
        UUID accountId,
        UUID marketId,
        String symbol,
        PositionSide side,
        BigDecimal quantity,
        BigDecimal entryPrice,
        BigDecimal currentPrice,
        BigDecimal stopLoss,
        BigDecimal takeProfit,
        BigDecimal unrealizedPnl,
        BigDecimal unrealizedPnlPercentage,
        BigDecimal riskAmount,
        BigDecimal riskPercentage,
        BigDecimal exposure,
        PositionProtectionStatus protectionStatus,
        Instant openedAt,
        Instant priceOccurredAt,
        Instant calculatedAt
) {
}
```

Les champs inconnus du broker peuvent être nuls uniquement si le contrat l’autorise explicitement.

Les valeurs calculées ne doivent pas être nulles silencieusement lorsqu’une donnée obligatoire manque.

Dans ce cas, la qualité de la donnée doit être indiquée.

## RiskDashboardSummary

```java
public record RiskDashboardSummary(
        RiskStatus status,
        BigDecimal usedRiskAmount,
        BigDecimal usedRiskPercentage,
        BigDecimal remainingRiskAmount,
        BigDecimal remainingRiskPercentage,
        BigDecimal dailyLossAmount,
        BigDecimal dailyLossPercentage,
        BigDecimal maximumDailyLossPercentage,
        BigDecimal totalDrawdownAmount,
        BigDecimal totalDrawdownPercentage,
        BigDecimal maximumDrawdownPercentage,
        List<RiskRuleDashboardView> rules
) {
}
```

Le statut global vient du Risk Engine.

Le frontend ne le déduit pas à partir de couleurs ou de seuils locaux.

## DashboardAlert

```java
public record DashboardAlert(
        String code,
        DashboardAlertSeverity severity,
        String title,
        String message,
        UUID marketId,
        String positionId,
        Instant occurredAt
) {
}
```

Les alertes sont déterministes dans la V1.

Exemples :

* position sans stop loss ;
* limite de perte quotidienne proche ;
* limite de drawdown proche ;
* risque maximal atteint ;
* prix de marché indisponible ;
* donnée broker trop ancienne ;
* marché non négociable ;
* position proche du stop loss.

L’AI Engine pourra ultérieurement proposer des alertes ou recommandations distinctes, sans remplacer ces alertes déterministes.

## Source de vérité du PnL

Le broker peut fournir un PnL non réalisé.

Trading OS peut également recalculer ce PnL avec le prix courant fourni par Market Data.

Pour le Dashboard, le Trading Core doit conserver une politique explicite.

Décision V1 :

* le PnL broker peut être conservé comme information externe ;
* le PnL de référence affiché et utilisé par le Risk Engine est calculé par le Trading Core à partir des données normalisées ;
* toute divergence significative entre les deux peut produire une alerte ou une information de diagnostic.

Cette décision garantit que les mêmes calculs sont utilisés pour le Dashboard et le Risk Engine.

## Source de vérité de l’equity

Lorsque le broker fournit une equity fiable et récente, celle-ci est conservée dans l’état broker.

Le Trading Core calcule également une equity de référence :

```text
balance + somme des PnL non réalisés
```

La politique V1 est :

* utiliser l’equity broker si elle est disponible, fraîche et cohérente ;
* sinon utiliser l’equity calculée ;
* indiquer la source dans les métadonnées de fraîcheur ;
* détecter et signaler les divergences importantes.

Le choix final doit rester centralisé dans `AccountEquityService`.

## Fraîcheur et qualité des données

Le Dashboard agrège des données qui ne sont pas nécessairement produites au même instant.

Le contrat inclut donc des métadonnées explicites :

```java
public record DashboardFreshness(
        DashboardDataStatus status,
        Instant brokerDataAt,
        Instant marketDataAt,
        Instant calculatedAt,
        boolean brokerDataStale,
        boolean marketDataStale,
        List<String> warnings
) {
}
```

Statuts possibles :

```java
public enum DashboardDataStatus {
    LIVE,
    DEGRADED,
    STALE,
    UNAVAILABLE
}
```

Le frontend affiche cet état, mais ne le calcule pas.

## Politique temps réel de la V1

La première implémentation du Dashboard utilise un snapshot agrégé REST.

Exemple :

```text
GET /api/v1/dashboard
```

ou :

```text
GET /api/v1/accounts/{accountId}/dashboard
```

Le frontend actualise ce snapshot de manière réactive à une fréquence raisonnable.

Fréquence initiale recommandée :

```text
2 à 5 secondes
```

Cette stratégie fournit un Dashboard proche du temps réel tout en évitant d’introduire immédiatement un nouveau système distribué de streaming entre trois services.

Le frontend utilise un flux RxJS avec :

```text
timer
→ switchMap
→ Dashboard API
→ shareReplay
```

Le rafraîchissement automatique doit être suspendu ou ralenti lorsque l’onglet n’est pas visible si cela devient nécessaire.

## Évolution temps réel future

L’architecture doit permettre ultérieurement :

```text
Broker events
Market Data events
       ↓
Trading Core projection
       ↓
Dashboard WebSocket ou SSE
       ↓
Angular
```

Cette évolution ne doit pas modifier la responsabilité des services.

Même avec une architecture événementielle :

* le Broker Service émet des faits broker ;
* le Market Data Service émet des faits de marché ;
* le Trading Core maintient la projection utilisateur ;
* Angular reçoit toujours un contrat Dashboard construit par le Trading Core.

Le passage à un mode événementiel sera formalisé par une ADR séparée.

## Gestion des indisponibilités

### Broker Service indisponible

Le Trading Core ne fabrique pas de données.

Il peut retourner :

* la dernière donnée connue si une stratégie de cache existe ;
* un Dashboard dégradé avec état explicite ;
* une erreur adaptée si aucun état cohérent n’est disponible.

### Market Data Service indisponible

Les positions restent connues, mais les valorisations dépendantes du prix courant sont marquées comme indisponibles ou obsolètes.

Le Trading Core ne réutilise pas silencieusement un prix trop ancien.

### Donnée partiellement invalide

Une position invalide ne doit pas nécessairement empêcher tout le Dashboard de s’afficher.

Le résultat peut être partiel, avec avertissement explicite.

## Cache

Aucun cache distribué n’est requis dans la première implémentation.

Un cache de courte durée pourra être ajouté dans le Trading Core pour :

* réduire les appels répétés ;
* limiter la charge sur le Broker Service ;
* absorber de brèves indisponibilités ;
* servir plusieurs composants utilisant le même Dashboard.

Un cache ne devient jamais une nouvelle source de vérité.

Sa durée et sa politique d’invalidation devront être explicites.

## Persistance

Le Dashboard lui-même n’est pas persisté.

Les données métier persistées restent dans leurs domaines respectifs :

* comptes, positions et règles dans le Trading Core selon le modèle existant ;
* intégration et identifiants broker dans le Broker Service ;
* données de marché selon les décisions du Market Data Service.

Les snapshots Dashboard sont des vues de lecture calculées.

## Sécurité

Le Dashboard contient des informations financières personnelles.

Par conséquent :

* l’endpoint Dashboard est sécurisé ;
* le Trading Core valide le JWT ;
* l’utilisateur ne peut accéder qu’à ses propres comptes ;
* le Broker Service valide également les appels sensibles selon le mécanisme retenu ;
* les logs ne doivent pas contenir de secrets broker ;
* les montants et positions ne doivent pas être journalisés à haute fréquence ;
* le Market Data Service reste non sécurisé tant qu’il ne sert que des données publiques.

## API frontend

Angular ne reçoit qu’un modèle Dashboard.

Le frontend peut conserver des services dédiés de présentation, mais le point d’entrée métier est unique :

```typescript
findDashboard(accountId: string): Observable<DashboardSummary>
```

Le composant Dashboard doit rester réactif et utiliser `async pipe`.

Les données factices de la maquette sont supprimées dès que les vraies données sont disponibles.

* risque utilisé et risque restant.

### Positions ouvertes

* symbole ;
* sens ;
* quantité ;

* prix courant ;

* PnL en pourcentage ;
* stop loss ;
* take profit ;
* risque ;

### Risk Engine

* statut global ;
* limites ;
* consommation actuelle ;

### Alertes

* éléments nécessitant une attention immédiate.

### Performance

La courbe de performance est ajoutée lorsque le Trading Core dispose d’un historique d’equity fiable.

Elle ne doit pas être simulée.

### Market Intelligence

Ce bloc consomme des vues synthétiques construites à partir de données Market Data déjà disponibles.

Il ne contient pas de fausses recommandations IA.

## Tests requis

L’implémentation doit couvrir au minimum :

* agrégation d’un compte sans position ;
* agrégation d’un compte avec plusieurs positions ;
* récupération groupée des prix ;
* position BUY profitable ;
* position BUY déficitaire ;
* position SELL profitable ;
* position SELL déficitaire ;
* calcul du PnL ;
* calcul de l’equity ;
* calcul du drawdown ;
* calcul de l’exposition ;
* calcul du risque ;
* utilisation du Risk Engine ;
* position sans stop loss ;
* prix de marché absent ;
* données broker obsolètes ;
* données de marché obsolètes ;
* Broker Service indisponible ;
* Market Data Service indisponible ;
* isolation des comptes utilisateur ;
* mapping des DTO Feign ;
* construction de `DashboardSummary`.

Les clients Feign doivent être simulés dans les tests du service d’orchestration.

## Observabilité

Les logs utiles sont :

* début et fin d’une agrégation Dashboard à niveau debug ;
* erreur d’appel interservice ;
* donnée manquante ;
* divergence importante entre données broker et calculs Trading OS ;
* état dégradé ou obsolète ;
* durée excessive de construction.

Les logs ne doivent pas contenir à chaque rafraîchissement :

* toutes les positions complètes ;
* tous les prix ;
* tous les montants utilisateur ;
* les payloads broker bruts.

Des métriques pourront être ajoutées :

* durée d’agrégation ;
* taux d’erreur Broker Service ;
* taux d’erreur Market Data Service ;
* nombre de Dashboards dégradés ;
* âge moyen des données utilisées.

## Conséquences positives

* Les responsabilités sont explicites.
* Le frontend reste simple.
* Le Trading Core conserve la maîtrise du métier.
* Le Broker Service reste indépendant des règles Trading OS.
* Le Market Data Service reste indépendant des utilisateurs.
* Les calculs du Dashboard et du Risk Engine restent cohérents.
* Le contrat frontend est stable.
* L’architecture peut évoluer vers les événements sans changer les propriétaires métier.
* Les sources et timestamps des données restent traçables.

## Conséquences négatives

* Le Trading Core devient un orchestrateur interservices important.
* Le temps de réponse dépend du Broker Service et du Market Data Service.
* La gestion des données partielles et obsolètes augmente la complexité.
* Des DTO d’intégration et des mappers supplémentaires sont nécessaires.
* Le polling V1 génère des appels réguliers.
* Les calculs doivent être rigoureusement testés pour éviter les incohérences financières.

## Alternatives rejetées

### Agréger le Dashboard dans Angular

Rejeté, car cela place la logique métier et l’orchestration distribuée dans le frontend.

### Construire le Dashboard dans le Broker Service

Rejeté, car le Broker Service ne possède ni les règles Trading OS ni le Risk Engine.

### Construire le Dashboard dans le Market Data Service

Rejeté, car le Market Data Service ne connaît pas les utilisateurs ou les comptes.

### Créer immédiatement un Dashboard Service séparé

Rejeté pour la V1.

Le Dashboard est principalement une projection du domaine utilisateur, des positions et du risque. Le Trading Core est donc son propriétaire naturel.

Un service de projection distinct pourra être envisagé uniquement si les besoins de charge, d’indépendance ou de persistance le justifient.

### Autoriser le frontend à calculer le PnL

Rejeté, car le PnL utilisé par l’affichage et le Risk Engine doit provenir de la même logique métier.

### Connecter directement le Trading Core au broker externe

Rejeté, car cela contourne le Broker Service et duplique l’intégration.

### Introduire immédiatement Kafka ou un broker d’événements

Rejeté pour la première version du Dashboard.

La solution REST orchestrée est plus simple à valider. Une architecture événementielle sera ajoutée après preuve du besoin.

## Résultat attendu

Le frontend appelle un endpoint sécurisé du Trading Core et reçoit un Dashboard cohérent.

Le Broker Service fournit les faits liés au compte et aux positions broker.

Le Market Data Service fournit les faits liés aux marchés et aux prix.

Le Trading Core combine ces faits avec ses propres modèles, règles et services déterministes.

Angular affiche le résultat sans reconstruire la logique métier.

Cette séparation devient la règle de référence pour toute future évolution du Dashboard.
